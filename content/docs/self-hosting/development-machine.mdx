title: "Development machine"
description: "A SlopOS virtual machine that keeps its disk between boots and can build, install and run SlopOS from inside itself."
---

`just boot` starts SlopOS in a QEMU virtual machine that you can develop
SlopOS on. It has a disk that keeps what you write between boots, a Rust and
C toolchain that runs on SlopOS (once you have cross-built it), and a git
clone of the checkout you booted from. Inside it you pull the host's commits, build the system, switch the
running machine to the programs you just built, try a new kernel for one boot
and keep it, and push your commits back to the host. You work as an ordinary
person, `user`, and the machine asks you before anything replaces its kernel
or its *base* (the read-only image the system's own programs come from).

An operating system that can build itself is called *self-hosting*. It is
the most practical test of whether a system is complete: a compiler, a
linker, git and a build system together touch almost every part of an OS,
from threads and memory maps to files, pipes and the network. When something
in SlopOS is missing or wrong, a build in the guest tends to find it.

The development machine is a virtual one. A computer you installed SlopOS on
from a medium carrying the toolchain runs the same loop, with the same
commands ([Installing SlopOS](/docs/self-hosting/installing)), and
[Remote control](/docs/self-hosting/remote-control) drives one from your
Linux machine.

## What runs on the host and what runs in the guest

The *host* is your Linux machine, where you ran `just boot`. The *guest* is
SlopOS running inside QEMU. They share no files directly. The guest sees two
disk images that live on the host:

- **The root disk** (`fs/assets/ext4-persist.img` on the host) is an ext4
  filesystem mounted as `/`. The first `just boot` creates it, and later boots
  reuse it, so your home directory, your clone and your build outputs are
  still there next time.
- **The boot disk** (`builddir/boot-disk.img`) is laid out the way SlopOS
  lays out a real disk: the boot loader on the EFI system partition, a boot
  partition holding two kernel slots and the two bases every slot boots, and
  a partition for crash records. The guest installs what it builds onto this
  disk. [Updating SlopOS](/docs/self-hosting/updating) explains the layout.

On the root disk you find:

| Path | What it is |
|------|------------|
| `/src/slopos` | A git clone of your host checkout. Its builds fetch crates from crates.io (and a `tests` build the LLVM sources) as your checkout's do, so the guest needs the host's network the first time |
| `/var/lib/slopos/offered` | The images the host offers this root: the toolchain, `slopos-toolchain` (`rustc`, `cargo`, `clang`, `clang++`, `ld.lld`, `git`, `ssh`, `bash`, `cmake`, `ninja`, `just` and their licence texts), and the apps that live outside the base, `slopos-essentials`. Init installs each at boot, unless the guest has installed a version of it since, and it then shows at `/opt/slopos-toolchain` or `/opt/slopos-essentials`, its commands linked into `/opt/bin` |
| `/home/user` | Your home directory |
| `/etc`, `/var` | The machine's own state, as on any Unix machine |

The system's own programs (`/bin`, `/sbin`, `/lib`, `/usr/bin`, `/usr/share`,
`/etc/ssl`) don't come from the root disk. They come from the base, which
lives on the boot disk and which the kernel mounts read-only over those
directories. So a new base replaces all of them at once, and nothing you write
to the root disk can replace a system program by accident.
[Base system](/docs/architecture/base) explains how that works.

Your search path is `/bin:/sbin:/home/user/.local/bin:/opt/bin`.
The system's tools come first, so a program in your home or in `/opt/bin`
never shadows one of them. A process with no `PATH` at all gets the same list
without your home, `/bin:/sbin:/opt/bin`: the shell exports it
when it starts with none and searches it for `command -p`, the C library's
`execvp` and the coreutils fall back to it, and remote control runs its
commands with it. `/opt/bin` comes last because it holds the commands of the
[packages](/docs/architecture/packages) the machine runs, the toolchain's and
the apps' among them, which so shadow none of the system's tools. Nothing
lands in `/usr/local`: software for everyone is a package, and a program you
build for yourself is a file you
copy into `~/.local` (its `bin`, `lib` and `share`).

The toolchain is cross-built on the host by `just toolchain`, which takes
hours; [Toolchain](/docs/self-hosting/toolchain) explains what it builds. You
can boot without it. The root is then offered only the apps, and the guest
has no `cargo` and no `just`, which is one of the toolchain's programs. A
toolchain directory left by a build that wrote another image format holds no
`slopos-toolchain.pkg`, and `just boot` stops there and says so: run
`just toolchain` again, or remove the directory.

## Who you are in the guest

The machine boots straight to a desktop logged in as `user`, the *first
person*: uid 1000, an administrator, with no password, and the desktop opens a
terminal for you. In the terminal you ran `just boot` from, the serial console
also offers a `slopos login:` prompt, where `user` logs in with an empty
password.

You own your home and the clone at `/src`, so building in the clone needs
nothing special. Changing the system itself
does: writing the boot partition, replacing the running base, restarting the
machine. The programs that do it (`bootctl` among them) ask *privd*, the
privilege broker, to do the work, and before it installs a kernel or a base
privd asks you. On the desktop that is a dialog you click. At the serial
console a question can only be answered by typing your password, and `user`
has none until you set one with `users passwd` from the desktop's terminal; so
install from the desktop.
[Privileged actions](/docs/architecture/privd) explains who may ask for what.

You never need to become root: uid 0 holds no special power in SlopOS
([Users and file permissions](/docs/architecture/users)). For work that needs
more than you hold, such as mounting a disk or reading another person's
files, put `priv` in front of the command (`priv mount <device> <directory>`),
or run `priv -s` for a shell. `priv` runs the command as you, with a fixed
set of extra capabilities (mounting, network and console settings, the
clock, reading the kernel's diagnostics, and passing every file permission
check), after you allow it.
It never reaches the raw disks, the base or any sealed file, and it only runs
commands from directories that only uid 0 can change.

## How source moves between host and guest

Source moves through git, over QEMU's built-in network. The clone in
`/src/slopos` has two remotes that both point at the host:

| Remote | URL | What it reaches |
|--------|-----|-----------------|
| `origin` | `git://10.0.2.4/slopos` | Your host checkout, read-only |
| `host` | `git://10.0.2.4:9419/slopos` | `fs/assets/guest-push.git` on the host, a bare repository that accepts pushes. `git push` uses it by default |

`10.0.2.4` isn't a real machine. QEMU's user-mode network (SLIRP) has a rule
for each of the two ports (a `guestfwd`): it intercepts a connection to that
address and, for each one, starts a `git daemon --inetd` on the host that
serves exactly one repository. So nothing listens on a host port,
and the guest can reach these two repositories and nothing else on your disk.

The clone takes your host's `user.name` and `user.email`, so commits made in
the guest are attributed to you. To bring them into your host checkout, fetch
from the push repository:

```sh
git fetch fs/assets/guest-push.git <branch>
```

The toolchain also carries OpenSSH's `ssh` and `ssh-keygen`, so git in the
guest reaches any server over SSH that the guest can reach on the network,
with a key you make there. `just boot` runs no SSH server for the guest on
your host; the test that climbs the toolchain ladder starts one of its own
(see [below](#how-it-is-tested)).

## A typical session

On the host, boot the machine:

```sh
just boot
```

Before QEMU starts, the recipe reminds you of the loop:

```text
boot: in the guest: cd /src/slopos; git pull; just install; for a kernel, just install-kernel; bootctl reboot
boot: the guest's git push lands in fs/assets/guest-push.git; git fetch fs/assets/guest-push.git <branch> takes it
```

The Wheel of Fate spins (`just boot-fast` skips it), then the desktop comes
up. In a terminal, take the commits you made on the host, then build and
install the userland:

```sh
cd /src/slopos
git pull
just install
```

`just install` builds the kernel, the user programs, the base and the apps'
image, holds the build to the base interface and to the C library's recorded
exports, then hands the base and the kernel to `bootctl base try`, which
asks you to allow it. The running kernel was built from the same tree, so it
serves the new base, and the machine switches to the base straight away,
from memory, writing nothing to the boot disk:

```text
base tried: interface <i>, build tag -; the system runs it now (generation 2), and any reset boots the partition's again
bootctl base commit /src/slopos/builddir/initramfs.cpio keeps it; bootctl base rollback ends the trial
```

The apps' image goes in next, through `pkgctl install`, provided the C
library it was built against is the one now running; if it isn't, the
recipe prints the command that installs it once it is.

A program you start from now on comes from the new base. Programs already
running keep the files they started from until they exit. Init restarts the
services the new base changed. If the desktop's own programs changed, the
desktop keeps running them until you restart it: its system menu then shows
*Restart the desktop to finish updating* and offers *Restart desktop…*.
[Base system](/docs/architecture/base) explains what a switch moves and what
it leaves. When the base works, keep it with the command the output named,
`bootctl base commit /src/slopos/builddir/initramfs.cpio`; until then a
reset brings back the base on the boot disk.

A change to the kernel goes in through a slot instead, because a kernel can't
be swapped under a running machine:

```sh
just install-kernel
```

This builds the kernel, writes it into the slot that isn't the default, and
arms that slot for the next boot only:

```text
install-kernel: bootctl reboot tries slopos-b once; bootctl commit there keeps it
```

Reboot into it. If it works, make it the default:

```sh
bootctl reboot
# ...the new kernel boots...
bootctl commit
```

If the new base needs the new kernel (it names an interface the running
kernel doesn't serve), `just install` alone does both: `bootctl` writes the
base to the boot partition and the kernel into the spare slot, armed to boot
once, and `bootctl reboot` tries the two together.
[Updating SlopOS](/docs/self-hosting/updating) covers the checks `bootctl`
makes and how to roll back either half.

Then commit your change and send it to the host:

```sh
cd /src/slopos
git commit -am 'Fix the thing'
git push
```

On the host, `git fetch fs/assets/guest-push.git <branch>` brings the commit
over.

`just build [VARIANT]` builds the kernel and the base it boots with, without
installing anything. The variant is `release`, `dev`, `tests` (the kernel
with its test suite and the base with the test programs) or `release-tests`.
`build` defaults to `dev`, or `release` when `KERNEL_RELEASE=1`, the same on
both systems; `install` and `install-kernel` default to `release`. The
outputs are in `builddir/` inside the clone: `builddir/kernel-<variant>.elf`
and `builddir/initramfs.cpio` (`builddir/initramfs-tests.cpio` for a tests
variant).

Before you commit, run the same lane you would on the host:

```sh
just precommit
```

It runs `fmt`, `test-host` (on SlopOS without its Go half, and with
`TMPDIR=/var/tmp`, since `/tmp` is memory and some tests write disk images),
`clippy`, `build dev`, `check-gates` (the base interface, `xtask lint` and
the dev kernel's ELF gates) and `libc-exports`.

A build in the guest is graded the same way as one on the host: the checks
on the kernel binary and the test suite must pass. It doesn't have to be
byte-for-byte identical to a host build, and it isn't (panic messages, for
instance, carry slightly different source paths).

### One justfile on both systems

The justfile is the one build interface on the host and in the guest, and
each recipe says where it runs. A build or a gate runs on both. A recipe
that emulates a machine, or needs the host's images or cross-build tools,
refuses on SlopOS in one line before it builds anything:

```text
just boot: runs on a Linux or macOS host; SlopOS builds with just build and puts a build to use with just install and just install-kernel
```

`install` and `install-kernel` refuse anywhere but SlopOS, and point at
`just remote-install` for a paired machine. `just` in the guest uses your
own `CARGO_HOME`, `~/.cargo`. `just setup` there checks that the toolchain
image is the one this tree needs, by its identity
([Toolchain](/docs/self-hosting/toolchain)).

## What survives a reboot, a new session and a reset

| Event | Root disk (`/src`, `/home`, the offered images...) | Boot disk (the kernel slots and the bases) |
|-------|---------------------------------------------|---------------------------------------------|
| Reboot inside the guest (`bootctl reboot`) | Kept | Kept, including what you installed and committed |
| Quit QEMU and run `just boot` again | Kept. The images the host offers are replaced if the host's build of them changed | Rebuilt from the host's build. What the guest installed is gone |
| `just reset root` | Deleted. The next `just boot` makes a fresh root with a new clone | Rebuilt as usual |

This has two consequences. First, a new session always starts on the kernel
and base your host built, so an old experiment never boots by accident.
Second, work you haven't pushed lives only on the root disk, and
`just reset root` deletes it. Commits you already pushed are safe, because the
push repository is outside the root disk.

To copy a single build output off the root disk instead of going through git,
shut the guest down and use:

```sh
just export-file PATH=/src/slopos/builddir/kernel-release.elf OUT=builddir/guest.elf
```

This reads the disk image directly, so the guest must be shut down cleanly. If
the guest was killed mid-write, boot it once so the kernel can finish its
[crash recovery](/docs/architecture/crash-recovery), shut it down, then export.
`just boot` handles the same situation by itself: a root disk left mid-write
boots without the host's usual refresh, so the kernel recovers it first.

## Settings for `just boot`

`just boot` runs the optimized (release) kernel with 6G of memory. The release
kernel is the default because a compiler makes a great many system calls and
page faults, and the debug kernel spends about ten times as long on each. The
memory is sized for linking the kernel with its test suite: SlopOS lets one
process keep at most an eighth of memory pinned for the files it maps, and
that link maps more than an eighth of 4G. A few environment variables change
this:

| Variable | Effect |
|----------|--------|
| `DEV_QEMU_MEM=8G` | Give the guest more memory |
| `KERNEL_RELEASE=0` | Boot the debug kernel |
| `VIDEO=0` | Serial console only, no window |
| `PERSIST_IMAGE_SIZE=2G` | The root disk's minimum size, 512M by default. A larger value grows an existing root disk; the host also grows it whenever free space runs low |
| `TOOLCHAIN_STAGE=<dir>` | Offer the toolchain image in this directory instead of `builddir/slopos-toolchain/image` |

`just boot-fast` is the same machine without the Wheel of Fate, and
`just boot-debug` boots it on the debug kernel, without the wheel, with
QEMU's debugger stub and monitor on Unix sockets in `builddir/` (see
[Debugging with GDB](/docs/development/debugging-gdb-record-replay)).
[QEMU options](/docs/getting-started/qemu-options) lists the rest.

## Limits

- **The guest doesn't rebuild its own compiler.** LLVM and rustc are
  cross-built on the host. Building them in the guest would need Python, tens
  of gigabytes of disk and hours of CPU, and isn't planned.
- **Installs last one QEMU session.** The boot disk is rebuilt from the host's
  build at every `just boot`, so a kernel or base the guest installed is gone
  next time. Commit and push the change instead, and build it on the host.
- **Approvals need the desktop.** Every kernel or base install asks you to
  allow it, and only the desktop can ask a person who has no password.
- **Speed.** With KVM a full system build in the guest takes minutes. Without
  it (QEMU emulating every instruction) it runs about 25 times slower.

## How it is tested

`just test` doesn't need the toolchain. The heavier checks boot a root disk of
their own, rebuilt on every run, shaped like the development root but carrying
a vendored copy of every crate, so no build reads the network. They run their
work as `user`, as you would, because git refuses to work in a clone that
belongs to someone else.

- `just test-toolchain` boots that root twice, with no rebuild between, and
  on each boot `toolchain_test` climbs a ladder of builds:
  `rustc` alone, then cargo with build scripts and procedural macros, a git
  dependency, a crate fetched over TLS, C and C++ with clang, git against the
  host's checkout, `ssh` and git over SSH, a clone of the GitHub repository,
  crates.io, a bash script, a Ninja graph, a CMake project, `just`,
  `cargo fmt` and `cargo clippy`. For the SSH
  rung the host runs `sshd` for each connection the guest opens to
  `10.0.2.4:22`, accepting one key and forcing every session into
  `git-upload-pack` or `git-receive-pack` on two fixed repositories, so the
  guest fetches the checkout and pushes a commit the host then checks. A
  second test, `reboot_clone_test`, clones the workspace to
  `/home/user/clone` and commits there on the first boot, and on the second
  the clone must pass `git fsck --strict` and read back unchanged. The host
  checks the disk with `e2fsck` after each boot.
- `just test-selfhost` has the guest fetch the host's `HEAD`, build the dev
  and tests systems and grade its own build with `just precommit`
  (`selfhost_test`). The host then checks the disk with `e2fsck`, copies the
  guest's kernels and tests base out, confirms the ELF gates on both kernels
  and runs the full test suite on what the guest built
  (`just test-elf ELF=… BASE=…` runs the suite on a kernel and base built
  elsewhere).
- `just test-install-guest` runs the whole session above: build, install the
  base and the kernel, boot them, push a commit the host fetches, commit the
  slot, and roll back from slots that crash.

The last two need a built toolchain and a clean working tree (the guest builds
`HEAD`). `just test-toolchain` runs without one too, but then boots once and
checks only the seeded clone, its vendored crates and the root's free space.
The SSH rung needs `sshd` on the host, and the crates.io and GitHub rungs need
the host to be online. `just bench-selfhost` runs the guest's build
under the kernel's profiler and prints where the time went; it grades
nothing, so it runs on an uncommitted tree too.

## For contributors

### Host trees and seed trees

The host writes into the root image on every `just boot` but
one that finds the image closed mid-write. `scripts/build_fs_image.sh` takes
two kinds of directory and installs both through one `debugfs` session
(`scripts/fs_tree.py`):

- A **host tree** stays the host's. The two images the root is offered are
  host trees, each installed into `/var/lib/slopos/offered`: the toolchain's
  (`builddir/slopos-toolchain/image`, or `TOOLCHAIN_STAGE`) and the apps'
  (`builddir/slopos-essentials`). The shipped and tests roots are offered the
  apps' alone. `FS_HOST_TREES` lists them, each as
  `<host dir>:<guest dir>[:<name>]`. The host records the files it installed
  in a manifest beside the image, `<image>.host/trees/<name>`, where the guest
  cannot reach it. When the host's build changes, the next boot removes
  exactly the files the old manifest named and installs the new ones,
  leaving anything the guest added. If a new file would overwrite one the
  guest created, or one of another kind than the manifest names (a directory
  where it recorded a file), the host refuses before it writes anything,
  warns, leaves the tree alone and tries again next time.
- A **seed tree** (`FS_SEED_TREES`) becomes the guest's once copied.
  `/src/slopos` is one: the host copies it only onto a root that has no
  `/src`.

A change to either must keep three rules:

- **The owner comes from the root's ownership map, never from the host's
  files.** A tree inside a directory the image's owners record gives the
  first person is theirs (uid 1000, here `user`); anywhere else it is uid
  0's. Each entry is writable by that owner alone, whatever modes the host
  directory has.
- **Nothing on the image is trusted.** The guest wrote it. The host reads it
  only through `ls -l` listings of directories, each bound to the file
  record (inode) its parent's listing gave, so a symlink the guest made
  can't redirect an install somewhere else.
- **Every `debugfs` request is checked.** `debugfs` exits 0 whatever
  happened, so any line on its standard error but its version banner stops
  the build, in `build_fs_image.sh` as in `fs_tree.py`.

On every boot, not only one that changed a tree, the host also measures the
root image's free space and grows the image with `resize2fs` whenever less
than the floor is free (`FS_FREE_FLOOR`, which the justfile sets from
`ROOT_FREE_FLOOR`, 16G by default), which is enough for a clean build of the
dev and tests systems and `just precommit` over them. An image is grown for
a tree and the free floor, never for the base: a base past `FS_IMAGE_SIZE`
stops the build at the file that didn't fit. Both roots get a log (journal)
sized for the volume the floor grows them into, not for the size they start
at.

A persistent root made before the toolchain and the apps became images
still holds the old shared trees under `/usr/local` and their manifests,
which no search path names any more, and one made before base interface 16
still holds the store that interface read, in another directory of
`/var/lib/slopos`, which nothing reads now.
`just reset root` drops them.

### The checksums on a writable root

The root image ends in a trailer of per-block checksums
([Checksummed disk images](/docs/architecture/filesystem#checksummed-disk-images))
of the *attested* kind: the host vouches for the blocks it wrote, and a
write by the guest withdraws the claim for the blocks it touches.
`scripts/gen_verity.py` writes the trailer as the last step of every build.
A change there must keep these rules:

- **What the host attested is kept on the host**, in `<image>.host/verity`:
  the bitmap of attested blocks and each block's checksum. The guest can
  write every byte of the image, the trailer included, so the trailer alone
  proves nothing about who wrote a block.
- **The guest's blocks stay un-attested.** Before a kept image is grown or
  refreshed, the host works out which blocks the guest owns: the allocated
  ones that the record doesn't attest with the recorded content still in
  place. Those stay un-attested through the grow and the refresh, and so do
  the blocks `resize2fs` moves them onto.
- **A trailer counts only past the end of the filesystem**, and only when it
  describes exactly that filesystem. Bytes inside the filesystem that look
  like a trailer are the guest's data.
- **Only attested blocks are read.** The script streams the image, so
  sealing a grown root costs what the host wrote and not the image's size.

`just reset root` deletes the image together with its `.host` directory, and
keeps `fs/assets/guest-push.git`.

### The clone and the git peer

`scripts/stage_workspace.sh` makes the clone with `git clone --no-local`
and checks out the branch `HEAD` is on. `--no-local` matters: the clone's
history is then what the checkout's branches and tags reach and nothing
else, so objects you abandoned never reach the guest.

With `--vendored` the script adds three things, so a build in the guest
reads no network: the vendored crates in the clone's ignored
`third_party/vendor`, the LLVM source archive the C++ runtime is built from,
and cargo's offline configuration at `/src/.cargo/config.toml`. That file
sits one directory above the clone on purpose. Cargo reads it for any
directory below `/src`, and the clone's own `.cargo/config.toml` stays as
committed, so `git status` there stays clean. The development root is
seeded without `--vendored`; the tests' root with it.

`scripts/qemu_run.sh` adds the forwarding rules when `GIT_PUSH_REPO` names a
bare repository: one daemon serves the checkout read-only, the other serves
`GIT_PUSH_REPO` and accepts pushes (`receive-pack`). Each daemon is pinned
to its git directory twice, and a change must keep both pins.
`--interpolated-path` answers a request that names a host, which every git
client sends. `--strict-paths` with that one directory as the whole
allowlist refuses a hand-made request that names no host and so never
reaches the template.

`just boot` passes `fs/assets/guest-push.git`. Each test passes a scratch
repository under `builddir/`. `test-toolchain` gives its scratch repository
the checkout's objects as an alternate, so the host offers the checkout's
commits as ones it already has and the guest's push sends one commit, not
the history.

When `GIT_SSH_PEER` also names a directory, a third rule runs
`sshd -i -E <it>/sshd.log -f <it>/sshd_config` for each connection to
`10.0.2.4:22`, as your own host account. Only `test-toolchain` sets it. The
directory is `builddir/ladder-sshd`, the host's half of the SSH fixture
that `scripts/stage_ladder_fixtures.sh` makes fresh for each run. The
configuration there is what keeps this server from being a way onto your
machine, so a change must keep all of it:

- Public-key login only, for the one guest key in its `authorized_keys`,
  with a host key the guest's `known_hosts` names. No passwords, no PAM, no
  forwarding, no terminal.
- A `ForceCommand` that runs `git-upload-pack` on the checkout for
  `ssh://10.0.2.4/checkout`, `git-receive-pack` on `GIT_PUSH_REPO` for
  `ssh://10.0.2.4/push`, and refuses anything else.
- The log goes to the file `-E` names. QEMU hands the command the connection
  as its standard input, output and error, so a line on standard error
  would land in the SSH stream.

### The tests' root and its fixtures

`just test-toolchain`, `test-selfhost`, `test-install-guest` and
`bench-selfhost` boot `fs/assets/ext4-selfhost.img`, which
`just _fs-image-selfhost` rebuilds on every run. It has the development
root's shape and boots with the tests base: the toolchain and apps images
offered, which `utest_install_toolchain` (`toolchain_test --install`) holds
installed before the session's other tests run,
the clone seeded `--vendored`, and at `/home/user/ladder` the fixtures the
ladder fetches from. Those are a bare git repository holding one crate, a
registry of one crate with a freshly made certificate authority and server
identity, and the guest's half of the SSH key pair. Because these checks
bring their own root, `just test` never depends on `just toolchain`: there
the same tests pass by reporting that the root carries no toolchain.

`toolchain_test`, `selfhost_test` and `reboot_clone_test` run as the
session does, uid 1000 holding no gated capability, because git refuses a
repository another uid owns. A test that must run as uid 0, such as
`install_test`, still runs git and `just` in the clone as the session,
through the helpers in `slopos_userland::selfhost`: `just` runs with the
default `PATH`, no `LD_LIBRARY_PATH` and `CARGO_HOME` in the clone's
`builddir/cargo-home`. Use them for any new test that touches the clone.

### What each check holds

`toolchain_test` first holds the toolchain to the image the host built: the
image `/opt/slopos-toolchain` shows must be the one the offered sidecar names,
and `/opt/bin`'s `cargo`, `rustc`, `cc`, `c++`, `ld.lld`, `git` and `just`
must lead into it. So a toolchain that arrived wrong says so there and not
as a link error hours later. It then checks that the clone's vendored crates
are the ones its lockfile names. The ladder follows, each rung using more of
the system than the last:

| Rung | What must work |
|------|----------------|
| 1 | `rustc --version` under `LD_DEBUG=statistics`, which makes the loader report what starting a program of the compiler's size cost, then the version of every other program the toolchain starts with (`cargo`, `rustdoc`, `rustfmt`, `cargo-fmt`, `clippy-driver`, `cargo-clippy`, `clang`, `ld.lld`, `rust-lld`) |
| 2 | `rustc` linking a program through `cc`, and the program running |
| 3 | cargo building a crate with a build script and a procedural macro |
| 4 | cargo fetching a `git = "file:///home/user/ladder/git/greeting.git"` dependency through libgit2 |
| 5 | cargo fetching a crate through libcurl and Mbed TLS from the fixture registry, which the test serves over TLS on loopback. The image's own CA bundle must refuse that server first, or accepting it under the fixture's root proves nothing |
| 6 | clang compiling and linking C and C++ |
| 7 | git reading the seeded clone, where `git status` must be clean since nobody has edited that tree, and `git ls-remote` reaching the host's checkout |
| 8 | `ssh -V`, `ssh-keygen` deriving the fixture key's public half, then git over SSH: `ls-remote` and a fetch of the checkout, a commit on the fetched `HEAD` pushed to the scratch repository, and a command the forced command refuses. The host then holds the pushed ref to the commit the guest printed and that commit's parent to its own `HEAD` |
| 9 | git cloning `https://github.com/SlopLabs/slopos` at depth 1 with the image's CA bundle, after a certificate authority made in the guest has been refused |
| 10 | cargo downloading from crates.io, into an empty cache, every crate the clone's lockfile and the standard library's lockfile pin. The first fetch names no target, because a crate needed only under a condition no target meets is otherwise never downloaded |
| 11 | bash running a script with a pipeline, a background job and a here-document |
| 12 | Ninja running a build graph, then finding nothing left to do |
| 13 | CMake configuring a C project for SlopOS, generating for Ninja and building a program that finds a shared library by its run path |
| 14 | The toolchain being the one the clone needs, by the identity of its pins (see [Toolchain](/docs/self-hosting/toolchain)) |
| 15 | `just` running a justfile (a backtick, a dependency with an argument, a shebang recipe, a failing recipe's status), and the clone's `just boot` refusing to run on SlopOS |
| 16 | `cargo fmt` finding `rustfmt` beside it, `--check` refusing a crate out of form and a plain run rewriting it |
| 17 | `cargo clippy` running `clippy-driver` over a crate, where one of clippy's own lints, denied, fails the build |

Rungs 9 and 10 are the only ones that need the host's internet connection,
as `dns_resolve_test` in the ordinary suite does.

`reboot_clone_test` checks its clone on the second boot with
`git fsck --strict` and then with a status taken over an index whose cached
file times were dropped, which makes git hash every file again. A clean
status is therefore the whole working tree read back from the disk.

`just test-selfhost` boots the optimized tests kernel, the `release-tests`
variant, which has its own allowlists under `scripts/gates/{stack,vector}/`.
`selfhost_test` fetches the host's `HEAD` into the clone and checks it out,
refusing a tree with uncommitted edits because they would be built too. It
runs `just build dev` and `just build tests`, then `just precommit`, and checks the
clone's own branch out again. The kernel builds run with cargo's
`--timings`, so a report is left under the clone's
`builddir/target/cargo-timings`. The host holds the commit the guest printed
to its own `HEAD` before it grades anything.

`just test-install-guest` puts the optimized tests kernel in slot a.
`install_test` finds the clone, takes the host's `HEAD` the same way and
runs `just install tests`, `bootctl base commit` and `just install-kernel tests` under a fresh
build tag. The host then compares slot b's kernel and the current base on
the boot disk, byte for byte, with the files the guest built on the root,
and fetches the commit the guest pushed.

`just bench-selfhost` is the guest half of `test-selfhost` with the kernel's
profiler on (`prof=on`; `BENCH_PROF=` with an empty value turns it off). It
runs only `utest_install_toolchain` and `selfhost_test` (so the builds and `just precommit`) and hands the log to `scripts/prof_report.py`. The
recipe keeps a copy of the C library the boot ran as
`builddir/bench-libc.so`, because time spent in user programs is resolved to
function names against the exact files that ran. Every number in the report
is wall time, so run it with nothing else loading the host.

### Building in the guest

The whole build runs in the guest with the same justfile and scripts the
host uses. The recipes resolve `cargo`, the host's cargo and the toolchain
step by the system they run on (just's `os()`): on Linux and macOS,
`cargo +slopos`, `cargo +<channel>` and `scripts/ensure_toolchain.sh`; on
SlopOS the installed `cargo` and no toolchain step, where
`build_userland.sh`'s standard library stamp is the check. `xtask` is built
natively on either system, so a build on SlopOS is held to the same `xtask
elf` and `xtask programs` gates as one on the host. `scripts/build_kernel.sh`
is POSIX `sh` and needs only `/bin/sh` and the coreutils; the userland and
C++ runtime builds are bash scripts that call cargo, clang, CMake and Ninja.
Keep it that way: a step added to a build script must run with what the
guest has.

The list of programs in a base comes from `scripts/lib/base.sh`, which
both sides read, so host and guest pack the same base. The e2fsprogs programs
the base carries come from the recipes' build on the host and from
`/opt/slopos-toolchain` in the guest. A machine whose base is paired for
[remote control](/docs/self-hosting/remote-control) stays paired: the base
`just` builds there carries the running base's pairing.

A few details of the build exist because of the guest, or break it when
changed:

- **The standard library is checked by a stamp.** Cargo doesn't notice when
  the standard library's sources change under the same compiler version. So
  `build_userland.sh` reads `library/.slopos-std-stamp` from the sysroot it
  runs under and refuses one that isn't the fork this tree pins. The owned
  sysroot on the host carries the stamp, and so does the source the
  installed toolchain keeps under `/opt/slopos-toolchain/lib/rustlib/src`.
- **Panic locations differ.** The guest's cargo reads the standard library
  from that directory, so the paths in a guest kernel's panic messages
  differ from a host build's. Nothing grades them.
- **`compiler_builtins` is built one function per object file.** The
  userland build takes its profile from this workspace, not from the
  standard library's own manifest, so `build_userland.sh` sets this
  explicitly. In fewer objects, linking one function drags in the math
  routines beside it, which are hidden, and their visibility wins over the
  `floor` that `libc.so` exports.
- **The kernel's symbol table comes from `tools/kallsyms`**, a small ELF
  reader built for whichever machine runs the build. It lists what `llvm-nm`
  would, less the `.llvm.<hash>` suffix LLVM adds to a function it shares
  between compilation units. The hash changes with every build, so with the
  suffix kept the embedded table would never settle.
- **The kernel build writes its own empty SafeStack runtime archive** where
  the toolchain carries none (the toolchain image ships one), and passes
  cargo's `trim-paths`, which keeps every absolute path of the checkout out
  of the image.

## Further reading

- [*Git on the Server: Git Daemon*](https://git-scm.com/book/en/v2/Git-on-the-Server-Git-Daemon),
  from the Pro Git book. What `git daemon` serves and why it is meant for a
  trusted network, which is all the guest's remotes are.
- [`git-daemon`](https://git-scm.com/docs/git-daemon), the manual page. The
  `--inetd`, `--strict-paths` and `--interpolated-path` options that pin each
  per-connection daemon to one repository, and why `receive-pack` is off by
  default.
- [*Bootstrapping the compiler*](https://rustc-dev-guide.rust-lang.org/building/bootstrapping/intro.html)
  in the rustc dev guide. How a compiler comes to build itself, the problem one
  level down from an OS building itself.
- [*Operating Systems: Three Easy Pieces*](https://pages.cs.wisc.edu/~remzi/OSTEP/),
  by Remzi and Andrea Arpaci-Dusseau. Free chapters on processes, memory and
  files, the parts of an OS a compiler exercises hardest.
