With the SlopOS toolchain you can build the kernel and its programs on your
Linux machine, and, once you have cross-built it, compile Rust, C and C++
inside SlopOS itself. On the host, `just setup` prepares the Rust half of the
normal build: a copy of the Rust standard library that knows about SlopOS. With
`just toolchain` (hours of CPU, once) you also get `rustc`, `cargo`,
`rustdoc`, `rustfmt`, `clippy`, `clang`, `git`, `ssh`, `cmake`, `ninja`,
`bash`, `just` and the libraries behind them, compiled to run inside SlopOS
and packed into one image, `slopos-toolchain`, which is what the
[development machine](/docs/self-hosting/development-machine) uses to build
SlopOS from inside SlopOS.

None of the techniques here are new. Rust's own build system,
[bootstrap](https://rustc-dev-guide.rust-lang.org/building/bootstrapping/intro.html),
already knows how to build a compiler on one OS that runs on another. LLVM and
clang are designed to be ported to new operating systems. Other systems have
taken the same road: Rust ships ready-made compilers for FreeBSD, and Redox
has a target in Rust whose standard library is prebuilt. SlopOS is further
back than either: Rust has never heard of it, so everything that teaches Rust,
LLVM and C programs about SlopOS lives in this repository as a set of small,
pinned patches.

## Why SlopOS needs its own target

A compiler produces code for a processor *and an operating system*, because
the way a program opens a file, starts a thread or finds its libraries is
different on every OS. Rust names that pair a *target*:
`x86_64-unknown-linux-gnu` is Linux on a 64-bit Intel or AMD processor. When
you `cargo build` on Linux you are building for that target, with a standard
library rustup downloaded ready-made.

Rust has no target for SlopOS, and no ready-made standard library. So SlopOS
needs three things that rustup users never think about:

1. A description of the target: how to call functions, how to link, what the
   OS is called.
2. A standard library that knows how to do files, threads and sockets on
   SlopOS.
3. For the guest to compile anything, a compiler that itself runs on SlopOS.
   That is a much bigger job, because the compiler depends on LLVM, which is
   C++ and expects a C++ standard library and a few dozen other things from
   the OS.

## The two targets

SlopOS has two targets, because the kernel and ordinary programs need very
different things from the compiler:

| Target | Used for | What makes it different |
|--------|----------|-------------------------|
| `x86_64-slos` | The kernel | No operating system underneath (`os: none`), no floating-point registers, no `std` |
| `x86_64-unknown-slopos` | Every program | A Unix-like OS with a C library (slibc), shared libraries and threads |

The program target is described twice: as a JSON file the host build reads,
and built into the forked compiler (see [below](#the-compiler)), which is what
lets a compiler run *on* SlopOS. A check (`just check-rustc-target`) keeps the
two identical, because a disagreement between them compiles fine and quietly
produces programs for a slightly different target.

Because neither target is one Rust ships, cargo builds the standard library
from source for each build, with the unstable `-Zbuild-std` option.

## The owned sysroot

A *sysroot* is the directory a compiler takes its standard library from. With
rustup it lives inside the toolchain directory and you never touch it.
`-Zbuild-std` reads the standard library's *source* from there.

`just setup` makes a sysroot of SlopOS's own in `third_party/rust-slopos` and
registers it with rustup as the toolchain `slopos`, so every build of the
kernel and the programs runs as `cargo +slopos`. It is a copy of a pinned
nightly (hardlinked, so it costs almost no disk), except for the standard
library's sources, which are a real copy with two forks applied: Rust's `std`
and the `libc` crate, both taught about SlopOS. That is why ordinary crates
that use `std::fs`, `std::thread`, `std::process` or `std::net` compile for
SlopOS unchanged.

Nothing is patched in place inside rustup's directories. The forks are kept as
patch files, and the nightly version and a checksum of each patch are pinned
in `toolchain/PIN`. Every build makes the sysroot again when it no longer
matches the pin, and a check fails if one has drifted anyway, so a stale copy
can't silently build the kernel. Running `just setup` again is cheap when
nothing changed.

The sysroot has to be SlopOS's own because of where `-Zbuild-std` looks. It
reads the standard library from the invoking sysroot's `lib/rustlib/src`, and
nothing a workspace can write, a `[patch]` section included, reaches that
directory. So that one directory is a real copy, holding forks of the
`library/` tree of `rust-lang/rust` and of the `rust-lang/libc` crate, and
everything else in the clone is a hardlink.

The forked standard library carries a stamp of the patches it was made from,
and so does the copy inside a cross-built toolchain. A userland build compares
that stamp with the patches in the tree it builds, so a guest whose toolchain
predates a change to the forks stops with a message instead of building the
old library:

```text
build_userland: <sysroot> carries the std fork stamped <old>, not the <new> this tree pins
  On the host, scripts/ensure_toolchain.sh or just toolchain rebuilds it.
```

Before that, a toolchain image is held to its identity
([below](#building-the-toolchain)), which covers every pin and not only the
forks:

```text
build_userland: the toolchain at <sysroot> is <have>; this tree needs <want>, which just toolchain builds on the host
```

## The compiler

A JSON target file is enough to build programs *for* SlopOS on Linux. Building
a compiler that runs *on* SlopOS is different: Rust's bootstrap only builds a
compiler for targets it has built in, so `x86_64-unknown-slopos` has to be
added to rustc itself. SlopOS carries that as three small patches to rustc:

- the target itself;
- telling LLVM's build that SlopOS is a Unix (without that, LLVM's build treats
  it as an unknown platform and leaves out all the Unix code SlopOS needs);
- linking the C++ standard library into the compiler statically, so the
  compiler doesn't depend on one at run time.

A handful of crates that rustc and cargo use (`getrandom`, `errno`, `rustix`,
`nix`, `libloading`, `socket2`, `stacker`) also need to know about SlopOS, and
get small patches of their own. Cargo itself needs none.

Besides `rustc` and `cargo`, the cross-build makes `rustdoc`, `rustfmt` (with
`cargo fmt`) and clippy (with `cargo clippy`); `build.tools` in the
bootstrap configuration names them. rustdoc is what the base-interface gate
reads SlopOS's system call surface through, so a build on SlopOS can run that
gate. The forked standard library names the target in `std::env::consts`
(`OS` is `slopos`, `FAMILY` `unix`, libraries end in `.so`), which programs
such as `just` read to tell one system from another, and its
`env::current_exe()` reads `AT_EXECFN`, the absolute path the kernel opened,
which is how `cargo-fmt` and `cargo-clippy` find `rustfmt` and
`clippy-driver` beside themselves.

`just rustc-src` (`scripts/make_rustc_src.sh`) downloads the pinned nightly's
source (a few hundred megabytes) and applies the patches, into
`third_party/slopos-rustc-src`. This is a second tree, separate from the
sysroot above: the sysroot is a clone of a *built* toolchain and has no
compiler sources to patch. Each tree records the inputs it was made from, so
editing a compiler patch doesn't remake the sysroot, and editing the standard
library's forks doesn't unpack the compiler again. The stamp `just toolchain`
leaves on rustc's bundled LLVM covers the compiler source tarball's checksum
as well as the LLVM port, so moving to a new nightly rebuilds that LLVM even
when the port's patch didn't have to change.

## LLVM and clang

rustc generates machine code through LLVM, which is written in C++. So a rustc
that runs on SlopOS needs LLVM to run on SlopOS too, and since we were porting
LLVM anyway, clang (LLVM's C and C++ compiler) comes with it. The port is
small, because LLVM has very little OS-specific code:

- the two places where LLVM picks code by OS and has no default for a new one;
- teaching LLVM and clang the name SlopOS (an operating system in LLVM's
  `Triple` and a clang target for it), so C code sees `__slopos__` defined;
- a clang driver for SlopOS, which turns `cc a.o -o a` into the full command
  that links a SlopOS program (startup code, the dynamic loader, the C library,
  compiler runtime);
- an entry in LLVM's own copy of `config.guess`, so LLVM's build recognises a
  SlopOS machine when it runs on one.

The port is applied to two copies of LLVM. `toolchain/llvm-rustc/` patches
the LLVM inside rustc's sources, which is what `just toolchain` builds the
guest's LLVM and clang from. `toolchain/llvm/` patches the llvm-project
release the C++ runtime (below) is built from. Only this second copy carries
the `config.guess` entry, because the runtime's build is the one that asks
what machine it runs on, and the guest builds that runtime too.
`just llvm-src` prepares the second copy whole (over a gigabyte on disk) for
the two checks that compile parts of it; `just toolchain` doesn't need it.

That second copy is the pinned release tarball, unpacked by
`scripts/make_slopos_llvm_src.sh` into `third_party/llvm-project-<version>.src`
with the port applied. The C++ runtime is built from the same directory, so
it holds LLVM's `llvm/` and `clang/` as well as the two runtime directories.
`just distclean` removes it and the patched rustc sources.

## The C++ runtime

LLVM needs a C++ standard library, and SlopOS has one: LLVM's own libc++,
built from the llvm-project release `toolchain/cxx/PIN` names. It ships as a
single shared library, `libc++.so` (with a static `libc++.a` beside it), that
also contains the part that handles exceptions. Keeping them
in one file matters because a C++ exception is matched by comparing type
information, and two copies of that machinery in one process can leave an
exception that nobody can catch.

The runtime is built with everything LLVM's sources use (locales, wide
characters, `<filesystem>`, random devices). No program of the shipped base
uses C++, so that base carries no runtime. The tests base and test image do,
beside probes that exercise exceptions across libraries, iostreams and
locales, and so does the cross-built toolchain, so `clang++` in the guest can
link C++ programs. The
compiler itself links its own copy in statically.

The build leaves the runtime in `third_party/slopos-cxx`: the headers,
`third_party/slopos-cxx/lib/libc++.so`, the static archive and both projects'
licence texts. Nothing removes that directory, `just distclean` included,
because its inputs are pinned and rebuilding it takes minutes. The one option
that is switched off is the time-zone database: nothing in LLVM uses it and
SlopOS has no zone data.

A third artifact sits beside `libc.a` and `libc.so` for the same reason the
runtime exists: `libbuiltins.a`, the compiler's helper routines (compiler-rt)
built position independent (`relocation-model=pic`). Code for x86-64 calls
out to them for 128-bit arithmetic, SlopOS has no libgcc to supply them, and a
shared library can't take them from another shared library, because each
hides everything but its own exports.

## Tools on the host

Beyond Rust, QEMU and the disk-image tools
[Quickstart](/docs/getting-started/quickstart) lists, two parts of the build
need tools on your Linux machine: the C++ runtime (and the checks that compile
the LLVM port), and the third-party programs below. One of those programs,
e2fsprogs, is in every
base, so every recipe that packs a base (each ISO, boot disk and test run)
builds it and the C++ runtime first. That is why the first four rows below
are needed even to boot.

| Tool | Why |
|------|-----|
| `clang`, `clang++`, `ld.lld`, `llvm-ar`, all from the same LLVM major version | Building the C++ runtime, the LLVM port and every third-party program. The version must be at least the floor in `toolchain/cxx/PIN` |
| `cmake`, `ninja` | The C++ runtime, and the projects built with CMake (Ninja also for Meson) |
| `make` | The projects built with `./configure` (bash, e2fsprogs, OpenSSH) and OpenSSL |
| `pkg-config` | Every project built with CMake, Meson or `./configure` |
| `meson` | git |
| `perl` | OpenSSL's configuration |
| `git` | Applying the standard library's forks and a project's patch, and staging the clone the guest gets |
| `python3` | Rust's bootstrap, for `just toolchain` |
| `openssl`, `ssh-keygen` | The fixtures the toolchain checks fetch from; `sshd` too for `just test-toolchain` with a toolchain built |

The LLVM version is a minimum, not an exact match, because distributions ship
different versions, and the pinned LLVM *sources* already decide what the
runtime contains. The host compiler only turns them into code. If your default
`clang` is the wrong one, set `CLANG`, `CLANGXX`, `LD_LLD` and `LLVM_AR`.

Two lines in `toolchain/cxx/PIN` say which versions. `clang_major_min` is the
floor: an older compiler is refused, because libc++'s sources use features of
the clang released with them. `clang_major_tested` lists the versions that
have built a passing `just test`. A version above the floor but outside that
list still builds, with a note on standard error, because what decides
whether the runtime works is the C++ probes in the test run and not a version
number.

## Third-party programs

The guest needs more than a compiler. Cargo fetches crates over HTTPS and git
dependencies; the build scripts want bash, CMake and Ninja; git wants an `ssh`
to reach a server; and the system needs tools to format and repair its own
disks. Each of these, and each library behind them, is a *recipe*: a small
file, `toolchain/recipes/<name>/recipe`, that names an upstream release tarball,
its SHA-256 checksum, its licence, a build template (CMake, Meson,
`./configure` or OpenSSL's own) and what it depends on. This is the same shape
as Redox's cookbook.

| Recipe | Builds | What it provides |
|--------|--------|------------------|
| zlib | a library | Compression, for most of the below |
| nghttp2 | a library | HTTP/2 for curl |
| Mbed TLS | libraries | TLS for curl |
| OpenSSL | libraries | TLS for libgit2, and the cryptography libssh2 and OpenSSH use |
| curl | a library | `libcurl`: git's HTTPS transport and cargo's registry client. SlopOS ships its own `/bin/curl` |
| libssh2, libgit2 | libraries | Cargo's git dependencies |
| git | programs | `git` |
| OpenSSH | programs | `ssh`, which git runs for an `ssh://` remote, and `ssh-keygen` for the key it uses |
| CMake, Ninja | programs | C and C++ builds in the guest |
| bash | a program | Scripts that need bash, the userland build among them |
| just | a program | The command runner the tree's justfile is written for, so a recipe means the same on the host and on SlopOS |
| e2fsprogs | programs | `mke2fs`, `e2fsck`, `resize2fs`, `tune2fs`, `debugfs` and `dumpe2fs`, which every base carries at `/sbin` |

`just recipes` builds them on the host into `builddir/slopos-recipes/prefix`
(`just recipes git` builds one and what it depends on), and `just toolchain`
builds them too and puts them in the toolchain image. Tarballs are cached under
`third_party/recipes/`; an offline machine fills that directory first, or
points `<NAME>_URL` (`ZLIB_URL` and so on) at a local copy.
`scripts/build_recipes.sh --fetch-source` fetches and checks the tarballs
without building, and prints where each one is.

### Libraries and programs are built differently

Every library is built shared, and everything is linked with `-z defs`,
which makes the link fail on any function slibc doesn't provide. Without it, a gap
in the C library would only show up on SlopOS, when the library first loads.

A library finds the libraries it needs beside itself (its run path is
`$ORIGIN`), so it works wherever it is copied. A program can't always work
that way: git finds its helper programs, templates and configuration through
the directory it was configured for. So every program is configured for
`/opt/slopos-toolchain`, where the toolchain image shows in the guest, and
looks for its libraries in its `lib/`. An image holds only `bin`, `libexec`,
`lib` and `share`, so every template puts configuration in `share/etc` and
system programs (e2fsprogs's, `sshd`) in `libexec/`. A recipe that builds
only programs installs no headers or libraries, so e2fsprogs's internal
libraries reach neither another recipe nor the sysroot that programs are
built against.

OpenSSH installs everything it builds: the server, `scp`, `sftp` and the agent
arrive beside `ssh` and `ssh-keygen`, though nothing on SlopOS runs them.

### A patch may only teach a project about SlopOS

A recipe may carry a patch, but only one that tells the project SlopOS exists.
If a program needs a function SlopOS doesn't have, the function goes into the C
library or the kernel, once, behaving as POSIX says, so every other program
that calls it works too. Each port left slibc larger:

| Port | What it brought into slibc |
|------|----------------------------|
| git | `<utime.h>`, `<grp.h>`, `mkstemp`, `freopen`, `execl`, `getpass`, `pthread_setcancelstate` |
| bash, CMake, Ninja | `ppoll`, `pselect`, `getloadavg`, `getopt_long`, `ttyname` |
| e2fsprogs | `system`, `popen`, `daemon`, `random`, `<libgen.h>`, `secure_getenv`, `PR_GET_DUMPABLE`, `si_addr`, the block device requests in `<sys/ioctl.h>` and the network interface requests in `<net/if.h>`, which slibc answers from the kernel's network query |
| OpenSSH | DNS lookups through `<resolv.h>` (`res_init`, `res_query` and `dn_expand`, with `<arpa/nameser.h>`), `initgroups`, `getitimer` and `setitimer`, `<paths.h>`, `<netinet/in_systm.h>`, the type-of-service values in `<netinet/ip.h>`, the BSD `timeval` macros, `caddr_t`, `IPPORT_RESERVED`, `IN_LOOPBACKNET` and the `%[` conversion in `scanf`, without which `ssh` rejects every server's greeting |
| just | Linux's whole `_SC_*` and `_PC_*` tables (`sysconf` and `pathconf` still answer only what they know, and `EINVAL` for the rest), the declarations of `getpwnam_r`, `getgrgid_r`, `getgrnam_r`, `getgrouplist` and `initgroups` in the `libc` fork, and `mkfifoat`. just also took the port of `nix` 0.31.3 |

Three of those behave in ways worth knowing. SlopOS has no interval timers,
so `setitimer` can disarm a timer but refuses to arm one, as `alarm` does, and
`getitimer` never reports one armed. `PR_GET_DUMPABLE` reports a program
started with authority its caller lacks (`AT_SECURE`) as not dumpable, as
Linux does for a setuid program. `res_query` asks the nameservers the
kernel's resolver uses, over UDP and then over TCP when the answer was cut
short.

A check (`scripts/check_recipes.sh`) holds patches to that rule mechanically.
A recipe names its patch in a `patch=` line, and the file is called
`NNNN-slopos-<what>.patch`. It may only add (a line it changes must keep its
old text at the start), every change must mention SlopOS, and configure
arguments may not contain code. Today only CMake carries a patch. CMake learns
about SlopOS the way it knows other systems, from a platform description
(`toolchain/cmake/Platform`) that CMake's own recipe carries, so CMake running
in the guest knows the platform too. Under CMake's `Modules/Platform` the
patch may only create those files, byte for byte, so the platform CMake
learns is the one the recipes are configured with. A recipe under a licence this repository
can't hold the text of, such as git's and e2fsprogs's GPL-2.0-only, carries no
patch at all, because a patch quotes upstream's lines as context.

### Licences

Git is licensed GPL-2.0-only, and OpenSSL 3 is Apache-2.0, a licence that
GPL version 2 code can't be combined with. So the curl that git uses gets its
TLS from Mbed TLS, which is licensed `Apache-2.0 OR GPL-2.0-or-later` and so may be used under the GPL instead, and
OpenSSL serves only libgit2 and libssh2, which only cargo loads, and OpenSSH,
which git runs as a separate program. The recipe check enforces this on the
built files: it follows every library a GPL-2.0-only program loads and fails
if one has an incompatible licence, or if a copy of one is linked in.

The C library sits under every program, git included, so it stays
permissive: slibc is `MIT OR Apache-2.0`, and a check
(`scripts/check_libc_license.sh`) fails if any crate it is built from can't be
used under MIT alone.

Distributing a GPL program means offering its source. Every base carries the
e2fsprogs programs, so the install medium carries e2fsprogs's tarball, its
recipe and the scripts that build it; the medium's payload carries every
recipe's tarball in its clone.

## Building the toolchain

```sh
just rustc-src     # the patched compiler sources
just test          # any test build: the toolchain reuses its libraries
just toolchain     # the cross-build: hours of CPU
just boot          # offers the image to the guest's root, where init installs it
```

`just toolchain` runs Rust's bootstrap with Linux as the machine doing the
build and SlopOS as the machine the compiler will run on. Around that it
assembles what the bootstrap doesn't provide: SlopOS's C headers and startup
files, the C++ runtime, the recipes, clang and its support files, `cc` and
`c++` links, copies of `ld.lld` and `llvm-ar`, and every project's licence
text. The result is laid out in `builddir/slopos-toolchain/install` the way
`/opt/slopos-toolchain` shows it, then `scripts/build_package.sh` packs it
into the image `builddir/slopos-toolchain/image/slopos-toolchain.pkg` and
its sidecar `slopos-toolchain.meta`, checking it as an install would. A
toolchain those checks refuse leaves no image, and a failed run never leaves
a half toolchain that `just boot` would offer. `--stage <dir>` also copies
the image directory there, for `TOOLCHAIN_STAGE`. Bootstrap's build
directory lies outside the patched sources, so re-running after a patch
keeps what it has already built, the host's LLVM among it, and rebuilds only
what the patch changes.

The image's release names the toolchain's *identity*: a hash over
`toolchain/PIN`, the standard library and `libc` forks, the compiler patches,
the crate ports, both LLVM ports, the C++ runtime's pin, the recipes and the
shared compiler settings (`tp_toolchain_identity` in
`scripts/lib/toolchain_identity.sh`). Its version is the time of the build.
`build_userland.sh`, and `just setup` on SlopOS, hold a toolchain image to
the identity the tree needs and name that identity when it differs, so a
guest whose toolchain is older than the tree's pins says so before it
builds.

It is expensive: hours of CPU, many gigabytes of disk, and a first run that
downloads the compiler bootstrap starts from. `just check-bootstrap-config` is
the cheap half: it checks the
build plan and a test compile and link without building the compiler.

<Callout type="warning">
`just distclean` removes `builddir/`, and the cross-built toolchain with it.
</Callout>

### Release settings: `--pgo`

`just toolchain --pgo` builds the compiler the way the Rust project builds its
releases: link-time optimization (ThinLTO) and *profile-guided
optimization*, where the compiler is first built with instrumentation, run on
a real workload, and then rebuilt using what was measured. Here the workload
is this repository's kernel build, gathered by `just toolchain-profile` on a
Linux-hosted twin of the same compiler. The result is a faster compiler at the
cost of a much longer build.

It is off by default (`--pgo`, or `SLOPOS_TOOLCHAIN_PGO=1` in the
environment, turns it on), and no compiler that runs on SlopOS has been built
this way yet.

A profile only fits a compiler built the same way as the one that was
measured. So the settings that decide what code the compiler is made of live
in one file, `scripts/lib/rustc_build_settings.sh`, which both builds read:
ThinLTO and one codegen unit for rustc's own crates, and ThinLTO for LLVM.
The SlopOS build and its Linux twin differ in the machine they run on and in
what a cross-build needs, and in nothing that file sets.

`just toolchain-profile` (`scripts/make_toolchain_profile.sh`) does what the
Rust project's release tool, opt-dist, does, in a build directory of its own
(`builddir/slopos-pgo-build`):

1. It builds LLVM with instrumentation and a stage 1 compiler on top of it,
   then runs the workload on that compiler. The workload is the build the
   guest's `selfhost_test` does: `scripts/build_kernel.sh` for the dev kernel
   and then the tests kernel, with the vendored crates.
2. It rebuilds LLVM using that profile, builds an instrumented stage 2
   compiler over it, and runs the workload again.

The two merged profiles land in `builddir/slopos-pgo`. LLVM's is merged by the
host's `llvm-profdata`, because the host's clang compiled the instrumented
LLVM and will compile the SlopOS one with the result. rustc's is merged by the
`llvm-profdata` the build itself produced, because rustc's own LLVM wrote
those records. `just toolchain --pgo` gathers the profiles first when they
are missing or out of date. `just toolchain-profile --optimized-host` goes
one step further and builds the Linux twin with both profiles, which is the
compiler to time a host kernel build with if you want to see what the
profiles buy.

One thing would make a profile from Linux useless on SlopOS. A profile is
keyed by function name, and Rust's function names include a hash that
identifies the crate (rustc calls it the `StableCrateId`). Cargo passes rustc
a `-C metadata` value that feeds that hash, and cargo's value depends on the
target. So the same `core`, from the same sources and the same compiler, has
differently named functions in the Linux build and in the SlopOS one, and a
profile from one matches nothing in the other. Both builds therefore run
every compile through `scripts/rustc_neutral_metadata.sh`, set as cargo's
`RUSTC_WRAPPER`. It replaces cargo's value with a hash of things that don't
depend on the target: the package, its version, the crate's name and types,
whether it is built for the host or the target, and
`__CARGO_DEFAULT_LIB_METADATA`, which bootstrap sets to tell the standard
library's copy of a crate from the compiler's.

## Building without the network

Every dependency is pinned by `Cargo.lock`, which is checked in. `just vendor`
copies every crate the build needs into `third_party/vendor`, including the
ones the standard library pulls in, which cargo can't see from the workspace.
Builds can then point at that directory instead of crates.io and run fully
offline. CI checks that the kernel and programs build this way from an empty
cargo cache, and the guest's test root is seeded with the vendored crates and
the LLVM tarball, so its builds never read the network.

Adding a dependency therefore means a `Cargo.lock` change, a `just vendor`, and
an entry in `NOTICE.md`.

Three downloads are not crates, and each can be pointed at a local copy. The
sysroot needs the pinned `libc` crate: `scripts/make_slopos_sysroot.sh` takes
it from `$CARGO_HOME/registry/cache` when it is already there and only then
falls back to `static.crates.io`, so an offline machine fills that cache
first or sets `LIBC_URL`. The C++ runtime needs the pinned llvm-project
tarball in `third_party/`, or `LLVM_URL`. The recipes need their tarballs, as
[above](#third-party-programs). The sysroot also needs rustup's `rust-src`
component, which `scripts/ensure_toolchain.sh` installs.

## How it is tested

`just test-toolchain` boots a root offered the toolchain image and first
holds the installed toolchain to that image. Then it climbs a ladder, each
rung using more of it: `rustc` alone, then linking through `cc`, cargo with a
build script and a procedural macro, a git dependency through libgit2, a
crate from a registry served over TLS, C and C++ with clang, git against the
host's checkout, `ssh`, `ssh-keygen` and git over SSH to an `sshd` the host
runs, a clone of the GitHub repository, cargo resolving crates.io, a bash
script, a Ninja graph, a CMake project, the toolchain's identity against the
clone's pins, `just` running a justfile, `cargo fmt` formatting a crate and
`cargo clippy` linting one.
[Development machine](/docs/self-hosting/development-machine#how-it-is-tested)
describes the other checks that use the toolchain.

The C++ runtime has three probes of its own on the tests base. `cxx_probe`
loads `libcxxtest.so` at run time and catches an exception thrown inside it,
which fails if the process ends up with two copies of the exception
machinery (the `type_info` a `catch` compares would not be the one thrown).
It then uses the parts LLVM's sources rely on: iostreams, `<iomanip>`,
`std::locale`, `std::to_wstring` and an `<fstream>` read. `cxx_static_probe`
links `libc++.a` and `libc.a` instead of the shared libraries. It is the only
program that uses either archive, and the only one that makes the unwinder
find a program's headers through the `AT_PHDR` value the kernel passes a
static program, since no loader has registered them. `cxx_test` runs them.

## What isn't done

- The toolchain doesn't rebuild itself inside SlopOS. That would need Python
  in the guest, tens of gigabytes of disk and hours of CPU, and isn't planned.
- No compiler built with `--pgo` has run on SlopOS yet.
- bash has no line editing (it would need a terminal database SlopOS doesn't
  have), so the interactive shell is SlopOS's own.

## For contributors

The gates that hold all of this to its pins are described on
[Toolchain gates](/docs/verification/toolchain-gates).

### The sysroot and the compiler sources

The sysroot comes from `scripts/make_slopos_sysroot.sh`, and
`scripts/check_toolchain_pin.sh`, one of the framekernel gates, fails if it
has drifted: a fork cut
against another nightly, a patch edited without updating its checksum, or a
sysroot a broken run left half-patched. Builds use `trim-paths`, so panic
locations don't depend on where the checkout is.

The script must never write into rustup's toolchain. Editing a file through a
hardlink would do exactly that, so after copying `lib/rustlib/src` it checks
that the copied files have a single link before it applies a patch. The libc
patch goes on first, because the std patch points cargo at the libc tree.
The only thing added to `$RUSTUP_HOME` is the `slopos` link. A stamp over
`toolchain/PIN`, the patches under `toolchain/{rust,libc}` and the script
itself makes a second run do nothing.

The compiler's patches are pinned by checksum in `toolchain/compiler/PIN`:

| Patch | Why it exists |
|-------|---------------|
| `toolchain/compiler/0001-slopos-target.patch` | Bootstrap's `--host` resolves a triple through rustc's built-in list, and a JSON file isn't in it. The patch also makes `rustc_llvm` link `c++` for SlopOS, as it does for FreeBSD |
| `toolchain/compiler/0002-bootstrap-cmake-system-name.patch` | Bootstrap names a cross target's `CMAKE_SYSTEM_NAME` by hand. One it doesn't recognise becomes `Generic`, which loses `LLVM_ON_UNIX` and with it every `Unix/*.inc` file the LLVM port patches |
| `toolchain/compiler/0003-bootstrap-static-libcxx.patch` | Bootstrap looks for `libstdc++.a` to link statically. A SlopOS sysroot has `libc++.a` instead |
| `toolchain/llvm-rustc/0001-slopos-support.patch` | The LLVM port, cut against the LLVM that rustc bundles. `just toolchain` applies it when it unpacks that LLVM into the tree |

The built-in target and `targets/x86_64-unknown-slopos.json` must say the
same thing, so a change to one is a change to both.

### The program target

The program target links through `cc`, using clang's SlopOS driver, and
supports unwinding, so build scripts and procedural macros work in the guest.
The system's own programs instead link directly with `rust-lld` and abort on
panic; `scripts/build_userland.sh` passes those flags explicitly.
`just check-clang-driver` holds the driver's link line to the one that script
writes.

In the target description that is `linker-flavor: gnu-cc` and
`no-default-libraries: false`: the driver, not rustc, supplies the startup
object, the interpreter, `-lc` and the compiler runtime. The target also has
run paths. The system's flags are one variable, `SYSTEM_RUSTFLAGS`
(`-C linker=rust-lld -C linker-flavor=ld.lld -C panic=abort`), on every build
line of the script. Because those programs keep `panic = abort`, their linker
script (`userland/userland.ld`) discards `.eh_frame`, so a system program
that starts to need unwinding needs both changed.

### The C++ runtime

`scripts/make_slopos_cxx.sh` builds the runtime, and
`scripts/build_userland.sh --test` is its only caller. It links libc++ and
libc++abi into the one `libc++.so` itself, with `ld.lld`, because clang has
no way to link for an OS it doesn't know.

One compile flag is part of the ABI. `_LIBCPP_PROVIDES_DEFAULT_RUNE_TABLE`
makes libc++ use its own character classification table instead of glibc's
(`__ctype_b_loc()`), and it decides the width and the bits of
`ctype_base::mask`, a type passed by value. A consumer compiled without it
disagrees with the runtime about that type. So the flag is written down once
and everything that compiles C++ asks for it with
`make_slopos_cxx.sh --print-abi-flags` instead of repeating it.

`scripts/cxx_host_tools.sh` is the only place that chooses the host's LLVM.
It prefers the major version of the pinned sources wherever it is installed,
since that is the pairing upstream tests, then the unsuffixed default, then
any other installed version above the floor. All four tools must report the
same major version, so a machine with one version's clang and another's lld
can't link the runtime with a mismatched linker, and the userland build
compiles the C++ probes with the tools that answered. `CLANG`, `CLANGXX`,
`LD_LLD` and `LLVM_AR` are a full override and never fall back, which is how
CI pins itself to a distribution's suffixed names. The host compiler's
version is part of the runtime's stamp, so upgrading it rebuilds the runtime.

### The cross-build

`scripts/bootstrap_slopos_toolchain.sh` writes a `bootstrap.toml` and the
compiler wrappers into `builddir/slopos-toolchain/` and runs `x.py install`
with `--build=x86_64-unknown-linux-gnu --host=x86_64-unknown-slopos`.
Bootstrap's build directory is `builddir/slopos-rustc-build`.
`scripts/make_slopos_cross.sh` assembles the target sysroot (the staged C
library, startup object and `libbuiltins.a`, slibc's headers and the C++
runtime) and the wrappers, `x86_64-unknown-slopos-clang{,++}`, for bootstrap
and for the recipes alike.

Until a clang built from the port runs the cross-build, those wrappers stand
in for its driver. A wrapper names two triples on purpose. It compiles as
SlopOS, because otherwise the preprocessor defines `__linux__` and LLVM takes
its Linux code, such as finding its own executable through `/proc/self/exe`.
It links as Linux, because the host's clang has no SlopOS driver and would
hand a SlopOS link to `gcc`; `--gcc-toolchain` points it at the SlopOS sysroot
so no library of the host's GCC is found. Every SlopOS object in the toolchain links with
`-z pack-relative-relocs` (the compact `DT_RELR` relocation format), which
slibc's loader supports. libc++ is linked
statically into libLLVM, which exports it to clang and the other LLVM programs
so they share one copy (libc++ compares error categories by address), and into
`librustc_driver`. The setting is `llvm.static-libstdcpp`. `llvm.use-libcxx`
is left unset, because it would also make the Linux compiler that bootstrap
builds on the way link libc++. LLVM's shared libraries link with `-Bsymbolic`
and the Rust ones with `-Bsymbolic-functions`, so calls inside a library
don't go through the loader.

`x.py install` ships no clang and no sysroot, so the script completes the
prefix: clang, `libclang-cpp.so` and clang's resource directory, the `cc`
and `c++` links, and the target sysroot itself, its libraries in `lib/` and
its headers in `share/include`. It removes the Linux standard library, which
a compiler running on SlopOS has no use for.

The image carries no `libc.so` or `libc.a`: a program links the running
base's `/lib/libc.so`, which only grows, so what a machine builds runs on its
base and every later one. clang's configuration files make `share` the
sysroot, so the driver's own `<sysroot>/include` and
`<sysroot>/include/c++/v1` name the headers and `-nostdinc++` and
`-nostdlibinc` still drop them; `-B<CFGDIR>/../lib` finds `crt0.o` and
`libbuiltins.a`, and `-L/lib -L<CFGDIR>/../lib` searches the base's `/lib`
first. `scripts/check_bootstrap_config.sh` resolves `libc.so` to the base's,
`builddir/libc.so`, for the same reason.

No link in the image leads out of the directory holding it. `bin/ld.lld` and
`bin/llvm-ar` are copies, and a recipe's link that climbs becomes a copy of
the file it reaches, or a link to a sibling holding that copy (git's names in
`bin/` are one program). The image also ships the empty SafeStack archive
the kernel's target links,
`lib/rustlib/x86_64-slos/lib/librustc-nightly_rt.safestack.a`, since
`build_kernel.sh` writes one only where none is and can't write into an
image.

### Recipes

A recipe is `key=value` lines. `template=` is one of `cmake`, `meson`,
`openssl`, `autotools` (the `./configure` projects) or `cargo`. A recipe that
builds programs lists each in a `program=` line, and one that builds
libraries lists each library's file name. The recipes are configured for
`GUEST_PREFIX=/opt/slopos-toolchain`: the Meson and `./configure` templates
pass it as `--prefix`, since a program finds its own files through the
prefix compiled into it, and bootstrap's `sysconfdir` is `share/etc`. The
CMake template builds for `CMAKE_SYSTEM_NAME=SlopOS`.
`build_recipes.sh --install-programs` copies what a program recipe installed
into the toolchain, and the libraries travel with the target sysroot. Only
the libraries' stamps make `just toolchain` rebuild cargo.

The `cargo` template builds a crates.io `.crate` with `cargo +slopos` for
the target JSON, the standard library from the owned sysroot, linked (and a
build script's C compiled) by the SlopOS compiler wrapper, `--locked` to the
`lock=` file beside the recipe. A package that lock takes with no source is
the `libc` fork or a `toolchain/crates/` port of that name and version,
staged beside the build and patched in for crates.io, and the recipe's stamp
adds the standard library's stamp and the ports. Its `program`s are
`bin/<binary>`. just is the first such recipe. The root workspace excludes
`builddir/`, where the template unpacks the crate.

A `./configure` script tests many things by compiling a program and running
it, which a cross build can't do. Those recipes give the answers as
configure's cache variables (`*_cv_*` values such as `bash_cv_*`), facts about slibc and the kernel,
and keep the link flags in a response file beside the compiler wrappers so
neither `make` nor a shell expands `$ORIGIN`. A recipe's stamp covers its
directory, the build driver, the cross compiler and the versions of the host
tools its template runs, so upgrading the host's CMake rebuilds what CMake
built.

The build driver also fails any build that changes the tree its patches left,
so a project can't edit its own sources while it builds.

### Profiles for `--pgo`

Each profile has a stamp over what it depends on: the stamps of the compiler
tree's sources, the host's clang, the shared settings, the metadata wrapper
and a number in the profile script, `PROFILE_FLOW`. The kernel's sources are
not in it, because a profile a few kernel commits old describes the same
compiler work. Bump `PROFILE_FLOW` when the script's steps, settings or
workload change.

Two caches don't notice what changed, so both scripts clear them by hand.
Cargo doesn't fingerprint a `RUSTC_WRAPPER`, so a build directory's Rust
stages are cleared when the wrapper changes. Bootstrap keys LLVM's stamp on a
commit that a source tarball doesn't carry, so a triple's LLVM and lld are
cleared when their settings, their profile or the host's clang change. A
plain build clears only what a `--pgo` build left behind.

The cc crate forwards rustc's profile flags (`-Cprofile-generate` and
`-Cprofile-use`) to the C compiler. The profile build's C compiler drops
them: the host clang's LLVM is not rustc's, the two write different records
into the same sections, and an instrumented compiler holding both crashes
when it exits.

### Offline builds

`.cargo/vendor.toml` redirects the `crates-io` source to the vendored
directory and sets `net.offline`. It is
passed with `--config` rather than living in `.cargo/config.toml`, because
cargo also runs inside the compiler trees under `third_party/`, whose
dependencies are not vendored, so an
ordinary host build still uses crates.io. `just vendor` covers two lockfiles:
the workspace's and `library/Cargo.lock` in the sysroot, which `-Zbuild-std`
resolves the standard library against. `scripts/check_offline_build.sh
--pins-only`, part of the framekernel gates, checks every locked package
against its vendored checksum; `just check-offline-build` is the CI check,
and it runs cargo `--locked --offline` from an empty `CARGO_HOME`, where a warm
cache can't stand in for a missing crate.
