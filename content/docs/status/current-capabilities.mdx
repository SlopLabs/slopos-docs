As of 2026-10-29, SlopOS commit `fa0f8f79`.

SlopOS boots, runs a desktop for several people with their own accounts,
keeps your files across reboots and crashes, talks to the network over three
kinds of network card, drives USB devices that come and go, installs itself
from a USB stick, and builds and installs a new version of itself without
leaving the machine. This page says what works today, area by area, with a
link to the page that explains each part. The gaps are on [Known
limitations](/docs/status/known-limitations), and the hardware it has run on
is on [Hardware](/docs/status/hardware-requirements).

Each area is graded **Works** (does what the linked page describes, and the
tests check it) or **Works with limits** (works, with a gap the area's
paragraph names).

## Where it runs

QEMU is the main platform: every test runs there, on an emulated PC with
UEFI firmware, NVMe, virtio and USB disks, a virtio network card, a virtio
display and two kinds of USB controller. One real machine, a Lenovo laptop,
runs the system installed on its own NVMe disk, with our Intel Xe display
driver drawing the desktop, its Realtek wired network card online, and USB
keyboards and mice. [Hardware](/docs/status/hardware-requirements) says
exactly what was tried on it and when.

## The kernel

The kernel runs on all CPUs at once and switches between programs on a timer,
so one busy program cannot freeze the rest
([Scheduling and waiting](/docs/architecture/scheduler-wait-protocol)). On a
CPU with Intel's hardware-managed frequency control it lets the hardware pick
the clock, and on a part with performance and efficiency cores it puts a
waking task on the best idle core ([CPU frequency](/docs/architecture/cpu-frequency)).
Programs run in the processor's restricted mode and reach the kernel only
through system calls ([User mode and kernel mode](/docs/architecture/privilege-separation)).
The kernel answers 146 system calls by Linux's numbers and calling convention,
so ported C and Rust code finds the calls it expects, and a call it lacks
fails with `ENOSYS`; 53 more are SlopOS's own, numbered as the *base
interface* the kernel serves (interfaces 10 to 12 at this commit)
([System calls](/docs/architecture/syscalls)).

Processes work the way a Unix programmer expects: `fork`, `exec`, shell
scripts with `#!`, process groups, job control and the full set of signals
([Processes and signals](/docs/architecture/processes)). Memory is handed out
lazily and shared copy-on-write after `fork`, files can be mapped into memory,
and a private mapping that could never be backed is refused when it is made
rather than killed later ([Memory](/docs/architecture/memory)). Each person's
processes, and each process, have limits on what they can hold, and when
memory runs out the kernel kills the process holding the most of what was
missing ([Resource limits](/docs/architecture/resource-accounting)).

When the kernel hits a bug, it can often recover from the panic instead of
freezing; a key combination prints what every CPU and task is doing even when
the desktop is stuck; and a panic that does stop the machine leaves its report
on the boot disk for the next boot to collect
([Diagnosing the kernel](/docs/development/diagnostics)).

## People and permissions

A machine has people, each with an account, a home directory and an optional
password, and some of them are administrators. The desktop logs the first
person in by itself until they turn that off; after that a login screen lists
the people, several can be logged in at once, and each switches to their own
desktop, which locks behind them. A text console has a login prompt too
([Users and file permissions](/docs/architecture/users),
[Sessions and login](/docs/architecture/sessions)).

What a program may do is a set of named capabilities (22 of them) it was
handed when it started, never something its path or its user id earns
([Capabilities](/docs/architecture/authority)). A person's programs hold none
of the powerful ones. When one needs to (to install a kernel, add a person or
power the machine off), it asks a broker, privd, which carries out one of 34
named actions after asking the person in a dialog when the action says so;
`priv` runs a command with more power the same way, as `sudo` would
([Privileged actions](/docs/architecture/privd)).

## Disks and files

The kernel drives NVMe, virtio and USB disks, reads their GPT or MBR
partition tables, and names them under `/dev/disk/by-id`, `by-uuid`,
`by-label` and `by-partuuid` as Linux does
([Disks](/docs/architecture/storage)). The root filesystem is ext4, the same
on-disk format Linux uses, and it lives on a disk, so files survive a reboot;
other ext2, ext3 and ext4 volumes mount beside it
([Filesystem](/docs/architecture/filesystem)). A journal lets a volume come
back intact after a crash or power loss ([Crash recovery](/docs/architecture/crash-recovery)).
Every system carries the e2fsprogs tools (`mke2fs`, `e2fsck`, `resize2fs`,
`tune2fs`, `debugfs`, `dumpe2fs`) to make and repair volumes.

## USB

The kernel drives xHCI USB controllers, the kind every PC of the last decade
has, enumerates devices through hubs, and handles devices plugged in and
pulled out while the system runs. It reads USB keyboards, mice and tablets,
serves USB sticks as disks (a mount on a stick that is pulled turns read-only
rather than taking the system with it), and brings up USB Ethernet adapters as
network cards ([USB](/docs/architecture/usb)). Works with limits: only xHCI
controllers, and only those three kinds of device, have drivers; a USB
audio device, serial adapter or printer does nothing.

## Network

The network stack speaks IPv4, TCP, UDP, DHCP and DNS over QEMU's virtio card,
the Realtek RTL8168h wired card and USB Ethernet adapters, each configured by
DHCP when it appears, and Unix sockets connect local programs. An in-tree TLS
1.3 client lets `curl` fetch pages over HTTPS, and on the development machine
`git` clones over HTTPS and ssh ([Networking](/docs/architecture/networking)).
Works with limits: IPv4 only.

## Programs and the desktop

SlopOS has its own C library, whose list of exported symbols (929 at this
commit) only ever grows, a dynamic loader, a POSIX shell and a multi-call
`coreutils` with the everyday tools (`ls`, `grep`, `sed`, `find`, `tar` and
the rest) ([Userland](/docs/architecture/userland)). The system's own
programs form one read-only *base* that can be replaced while the system runs
([Base system](/docs/architecture/base)); everything else is installed under
`/usr/local` or a person's `~/.local` ([Installed
software](/docs/architecture/software)), and *extensions* add services and
commands with a grant the machine's owner approved
([Extensions](/docs/architecture/extensions)).

The desktop has a compositor with a dock, a menu bar, a system menu and lock
and login screens, all drawn from one theme. Its apps are the terminal, a
text editor, a file manager, an image viewer, the System Monitor, a widget
gallery and the installer's window ([Desktop](/docs/architecture/desktop),
[Windowing](/docs/architecture/userland-windowing)).

## Installing and updating

The live ISO is an install medium: written to a USB stick, it boots the
system from memory, and its installer (a window, or a command with every
answer as a flag) installs SlopOS onto a whole disk, into free space beside
another system, or over an existing partition, sharing the disk's EFI system
partition. The same medium opens a rescue shell on an installed system
([Installing SlopOS](/docs/self-hosting/installing)). Works with limits: an
install from a live system with 512 MiB of memory, the size `just boot-live`
gives it, dies writing the boot slots ([Known
limitations](/docs/status/known-limitations#installing-and-updating)).

An installed system keeps two kernels in two boot slots, so a new kernel that
fails to boot falls back to the one that worked, and two bases, so a new base
can be rolled back. A new base runs at once, without a reboot, when the
running kernel serves it ([Updating SlopOS](/docs/self-hosting/updating)).

## Building itself

Once `just toolchain` has cross-built the compilers, the development machine
carries rustc, cargo, clang, lld, git, bash, CMake, Ninja and OpenSSH. Inside
it, SlopOS pulls new commits over git, builds its kernel, programs and base,
installs the base and runs it at once, installs the kernel into the spare
boot slot, boots into it and pushes commits back
([Development machine](/docs/self-hosting/development-machine)). The laptop
ran the same loop on its own disk. Works with limits: the compilers
themselves are built on the host ([Toolchain](/docs/self-hosting/toolchain)).

A machine on your network can be paired with your development host and
driven from it: commands, files, the kernel log, and new kernels and bases
([Remote control](/docs/self-hosting/remote-control)).

## How it is checked

The QEMU suite plans at least 3,100 tests: that is the floor
`scripts/check_test_count.sh` fails under (`TEST_COUNT_BASELINE`, set to 3,100
on 2026-10-28), counted from what one test boot plans across the kernel and
userland phases. Host-side unit tests run beside it, and longer checks boot
their own machines to cover USB hotplug, installs, updates, remote control and
self-hosting ([Write tests](/docs/development/adding-tests)).

All `unsafe` Rust in the kernel sits in one crate, `slopos-ostd`, which build
gates enforce ([The framekernel](/docs/verification/framekernel)), and
machine-checked proofs cover selected parts of it
([Proofs](/docs/verification/verus-status)). At this commit:

| Measure | Value | Measured with |
|---------|-------|---------------|
| `pub unsafe fn` in `slopos-ostd` | 52 | `grep -rn "pub unsafe fn" slopos-ostd/src` |
| `pub unsafe trait` in `slopos-ostd` | 15 | `grep -rn "pub unsafe trait" slopos-ostd/src` |
| Lines of `unsafe` code over all kernel Rust lines | 0.311 % (1,126 of 362,063, counting the vendored unwinder and DWARF reader) | `just tcb-ratio`; the gates fail above 1 % |

## Programs on every base

Every base carries these programs, listed in `scripts/lib/base.sh`; `init`,
`privd`, `authcheck` and the e2fsprogs tools are in `/sbin`, the rest in
`/bin`:

```text
init privd shell coreutils terminal compositor roulette halt bootctl installer
installer-ui sysmon nmap ip keymap ss nc curl ping oops_smoke cpufreq remoted
kconsole endtask prof tree-install session login extctl users authcheck priv
mke2fs e2fsck resize2fs tune2fs debugfs dumpe2fs
```

`coreutils` answers to these names, each a link to it:

```text
ls cat cp mv rm mkdir rmdir ln touch stat install mktemp basename dirname which
grep sed find xargs sort uniq tr cut head tail wc tee cmp diff patch printf
echo test [ true false yes seq sleep env nproc uname whoami pwd date hexdump
ps tar gzip gunzip zcat sha256sum stty less mount umount
```

The apps (`editor`, `file_manager`, `image_viewer`, `widget_gallery`) are not
in the base: every root holds them under `/usr/local`. The test base adds the
test programs and the shared libraries they load. To try it yourself, start
with the [Quickstart](/docs/getting-started/quickstart).
