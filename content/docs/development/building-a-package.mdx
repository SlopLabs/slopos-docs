title: "Build a package"
description: "Lay out a package, pack and sign it, install it on a SlopOS machine, and check that its daemon and command run."
---

By the end of this page you will have built a package called `hello`,
installed it on a SlopOS machine, and seen its daemon write to its log and its
command run from any shell. You will also have shipped an update and know how
to have a key you trust install updates without anyone being asked. For why
packages work the way they do, read
[Packages](/docs/architecture/packages).

## What you need first

- A SlopOS machine whose root is a disk, on which you are an administrator.
  The [development machine](/docs/self-hosting/development-machine)
  (`just boot`) and a computer you installed SlopOS on both qualify, and the
  first person on either is an administrator. A live boot from the install
  medium does not: packages need a disk root.
- A checkout of SlopOS on the host, to build the package with `just
  package`. You can also pack it on the machine itself with `pkgctl build`,
  which does not sign it; `just package` signs it when you ask.
- To install from the host, the machine [paired](/docs/self-hosting/remote-control)
  with it, so that `just remote` reaches it.
- To sign, `ssh-keygen` on the host.

The example's programs are shell scripts, so nothing needs compiling. A
compiled program must be linked dynamically against the base's `libc.so`
through `/lib/ld-slopos.so.1`, as every program outside the base is. On a
machine with the toolchain installed, `cc -o hellod hellod.c` links one that
way; `just package` and the install both refuse anything else.

## 1. Lay out the tree

A package starts as a directory laid out as it will appear under `/opt/hello`,
plus two files under `.package/`. Make it anywhere on the host, or in your
home on the machine:

```text
hello/
  .package/release
  .package/declare
  bin/hello
  libexec/hellod
```

`.package/release` names the package and its version:

```text
name     hello
version  1
summary  Says hello
```

`.package/declare` says what it asks for: a user of its own, a command on
everyone's `PATH`, and a service that runs as that user:

```text
user
command hello
service hellod
  program /opt/hello/libexec/hellod
```

`bin/hello` is the command:

```sh
#!/bin/sh
echo "Hello from the hello package, version 1."
```

`libexec/hellod` is the daemon. It writes a line when it starts and the date
every minute:

```sh
#!/bin/sh
echo "hellod started"
while true; do
    date
    sleep 60
done
```

Make both executable, or the image will not count them as programs:

```bash
chmod +x hello/bin/hello hello/libexec/hellod
```

The base has no `chmod`, so on the machine make the directories first
(`mkdir -p $HOME/hello/.package $HOME/hello/bin $HOME/hello/libexec`),
write each script somewhere else and copy it into place with `install`,
which makes the copy executable:
`install hellod.sh $HOME/hello/libexec/hellod`.

[Package images](/docs/abi/package-images) lists everything a
declaration can say: more users, state and settings directories, sockets,
privileged actions, apps.

## 2. Pack it

<Tabs items={['On the host', 'On the machine']}>
<Tab value="On the host">

From the SlopOS checkout, with the path to your tree:

```bash
just package ~/hello
```

The recipe builds the userland first if it is not built, so the first run
takes a while. It packs the tree, checks it as an install would against this
build's `libc.so`, and prints what it wrote and the grant a first install will
ask for:

```text
name hello
version 1
image builddir/packages/hello.pkg
root 3f9c2a1b7d4e…
sidecar builddir/packages/hello.meta
grant - unasked - users hello commands hello
```

`hello.pkg` is the image and `hello.meta` its sidecar, which names the
package, its version and the image's root: the digest at the top of the
SHA-256 tree that every block of the image is checked against when the
machine reads it.

</Tab>
<Tab value="On the machine">

Pack it into `/var/tmp`, where the install in step 4 can read it:

```bash
pkgctl build $HOME/hello /var/tmp
```

```text
hello 1: /var/tmp/hello.pkg (root 3f9c2a1b7d4e…) and /var/tmp/hello.meta
```

`pkgctl build` checks the image's shape but not its programs; the install
checks those.

</Tab>
</Tabs>

## 3. Sign it, if a key should vouch for it

Skip this step and every install is a first install: at the machine, an
administrator approves each one, seeing exactly what is granted (the paired
host installs unasked either way). Sign it, and an administrator or the
paired host installs updates signed by the same key with no question, within
limits the owner set for the key.

Decide before the first install. A name's images are one publisher's: the
record keeps the key that signed the first one (or nobody), and every later
image of that name must be signed by the same key, even one a person
approves. Changing publisher means `pkgctl remove` first.

Make an Ed25519 key on the host if you have none for this:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/slopos-package
```

Pack again with `PACKAGE_KEY` naming it:

```bash
PACKAGE_KEY=~/.ssh/slopos-package just package ~/hello
```

The output ends with an extra line, and `builddir/packages/hello.meta.sig`
now lies beside the sidecar:

```text
signed builddir/packages/hello.meta.sig with /home/you/.ssh/slopos-package
```

The machine must trust the key once. `ceiling` names the capabilities its
packages may be granted and `user` what their unasked actions may hold
together, each as names joined by commas, or `-` for none. `hello` asks for
no capability, so `-` will do for both:

<Tabs items={['From the host', 'At the machine']}>
<Tab value="From the host">

```bash
just remote push ~/.ssh/slopos-package.pub /var/tmp/
just remote run -- pkgctl key add /var/tmp/slopos-package.pub ceiling - user -
```

</Tab>
<Tab value="At the machine">

Copy `~/.ssh/slopos-package.pub` to the machine, here to `/var/tmp`,
then:

```bash
pkgctl key add /var/tmp/slopos-package.pub ceiling - user -
```

The terminal prints `pkgctl: waiting for you to allow this on the screen`
and the desktop asks you to allow it. The details under the question show
the command line, with the key's fingerprint and both ceilings. Choose
*Change*.

</Tab>
</Tabs>

```text
SHA256:bbXpuKG6zhzdmnxq256TlqzFBzRl2f6OOg722cYNbU8 trusted with ceiling - and user ceiling -
```

## 4. Install it

<Tabs items={['From the host', 'At the machine']}>
<Tab value="From the host">

```bash
just remote install --package builddir/packages/hello.pkg
```

`just remote` runs `scripts/remote.py install --package`. It refuses a
sidecar that names another image than the one beside it, and otherwise
pushes the image, and the sidecar and signature when they lie
beside it, then runs `pkgctl install-signed` for a signed image or
`pkgctl install` naming the root it pushed for an unsigned one. Either way it
runs unasked, because the paired host may install packages. Among its
output:

```text
remote: pushed builddir/packages/hello.pkg: … bytes, sha256 …, root 3f9c2a1b7d4e…
hello 1 installed; it runs as activation 2
```

followed by `bootctl status` and `pkgctl status`.

</Tab>
<Tab value="At the machine">

Run it from `/var/tmp`. The install runs as uid 0 without the power to
override file permissions, in your directory, so both the image and the
directory must be readable by anyone:

```bash
cd /var/tmp
pkgctl install hello.pkg
```

The terminal prints `pkgctl: waiting for you to allow this on the screen`.
The desktop asks whether to install a package and give it what it asks
for. The details under the question show the command line, which names the
image's root, its signer (`signer nobody`, or the key's fingerprint when
`hello.meta.sig` lies beside the image) and the grant,
`grant - unasked - users hello commands hello`. Choose *Install*. While it
works, one line on the terminal shows what it is doing and how far it got,
then gives way to the result:

```text
hello 1 installed; it runs as activation 2
```

For a signed image, copy `hello.meta` and `hello.meta.sig` beside
`hello.pkg` and run `pkgctl install-signed hello.pkg` instead. It asks no
administrator anything.

</Tab>
</Tabs>

The activation number differs from machine to machine; it counts every image
shown since the boot.

## 5. Check that it runs

At the machine, or with `just remote run -- ...` from the host:

```bash
pkgctl status hello
```

```text
hello: enabled, running, floor 1, signed by nobody
  uids hello=100
  current 1 3f9c2a1b7d4e by the person: grant - unasked - users hello commands hello
```

A signed install names the key's fingerprint instead of `nobody` and
`the person`, and the uid is the lowest free one from 100. The command is on
everyone's `PATH` through a link in `/opt/bin`:

```bash
hello
```

```text
Hello from the hello package, version 1.
```

The daemon's output goes to its log:

```bash
cat /var/log/hello/hellod.log
```

```text
hellod started
```

followed by a line with the date for every minute it has run. The daemon
runs as the user `hello`, and its log belongs to that user, not to you or to
root, although the base's `ls -l` shows no owners to prove it. After a
restart, `pkgctl status hello` still says `running`: init shows every enabled
package again at boot, checking it against its record first.

## 6. Ship an update

Change the command's message to say `version 2`, raise the version in
`.package/release` to 2, and pack it again as in step 2 (with
`PACKAGE_KEY` set if you signed version 1). Install it as in step 4.

A signed update goes in without a question; an unsigned one asks again, as a
first install does. Either way `pkgctl status hello` now shows the new image
as `current` and the old one as `previous`, and `hello` prints the new
message. `hellod` keeps running from the old image: nothing it runs or reads
changed. Change `libexec/hellod` in the next version and init restarts it.

Installing changed bytes under a version number already installed is
refused, so raise the version every time:

```text
pkgctl: hello.pkg: version 1 was installed with other bytes
```

## 7. Roll back, turn off or remove

Each of these asks an administrator at the machine, and runs unasked from the
paired host:

```bash
pkgctl rollback hello
pkgctl disable hello
pkgctl enable hello
pkgctl remove hello
```

`rollback` makes the previous image current again and lowers the version
floor to it, but refuses the version it left to a signed install, so the
next signed update has to be version 3. `disable` takes the
package away from `/opt/hello`, stops its service and removes its command
until `enable`. `remove` takes away its images, its data, settings and log,
and gives up the name: the record keeps only its retired uids, and the next
image of `hello`, from any publisher, goes in as a first install:

```text
hello removed; any publisher's image of it goes in as a first install; its uids are free again
```

If a program still runs as one of its uids, or something they own is left
in a shared directory, the uids stay retired and the message says why; run
`pkgctl remove hello` again once that is gone.

## What usually goes wrong

- **`/.package/declare names /opt/hello/libexec/hellod, which the image
  does not hold`.** The program is missing, or not executable when it was
  packed. Make it executable (`chmod +x` on the host, `install` on the
  machine) and pack again.
- **`outside bin, libexec, lib and share`.** The tree holds something else at
  its top. Only those four directories and `.package` may be there.
- **`a service's log, state and runtime directory are its package's first
  user's, so it declares a user`.** A service, `state` or `runtime` needs a
  `user` line, and so does an action.
- **`statically linked, not against libc.so`** (from `just package`,
  `static, with no PT_INTERP`) or **`binds <name>, which nothing it needs
  exports`.** A compiled program was linked statically, or needs a function
  the machine's `libc.so` does not have. `just package` checks against the
  host build's `libc.so`; a machine running an older base may lack a function
  a newer one has.
- **`version 1 was installed with other bytes`** or **`is older than`**.
  Raise the version.
- **`it is signed by SHA256:…, which the owner does not trust`.** Trust the
  key first (step 3).
- **`it is another publisher's image of hello`.** The installed images were
  signed by another key, or by nobody. Sign with the key that signed them,
  or `pkgctl remove hello` first.
- **`hello is a person's name`.** The package or one of its users has the
  same name as a person on the machine. Rename it in `release`.
- **The install fails reading the image although your session can read
  it.** The install reads it as uid 0 without the power to override file
  permissions. Put the image, and run the command, in a directory everyone
  can read, such as `/var/tmp`.
- **`pkgctl status` says `stopped:` and a reason.** A check at activation
  refused the image, usually because its key was removed or a ceiling
  lowered. Fix the cause and run `pkgctl enable hello`.
- **It installed but `not running`.** The machine booted with
  `packages=off`. The install says so: `packages are off this boot, so
  it is not shown`.
