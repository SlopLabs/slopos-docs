By the end of this page you will have written a test that runs inside the
kernel and one that runs as a program on SlopOS, chosen who that program runs
as, run only those tests, and know how to read what the harness prints when
one fails. The end of the page covers the tests that run on your own machine
without booting anything, the long-running checks, and what CI runs on top of
`just test`.

## What you need first

A working build and a passing `just test`; see
[Quickstart](/docs/getting-started/quickstart). `just test` builds a test
version of the kernel and base, boots them under QEMU, runs every registered
test but the few a host script drives (`FLAG_EXPLICIT`, below), and exits 0 if
all of them passed.

## Choosing where a test goes

Use the cheapest kind of test that can see the behaviour. A test that runs on
your machine takes seconds; one that needs a boot takes minutes.

| Kind | Runs | Use it for |
|------|------|-----------|
| Host test | On your machine, with `cargo test` | Logic that doesn't need the kernel: parsers, protocols, on-disk formats, policy files, layouts |
| Kernel test | Inside the booted kernel | Kernel code, and anything that needs the kernel's memory, tasks or devices |
| Userland test | As a program on the booted system | System calls, libraries, services and the desktop as a real program sees them |

That's why so much of SlopOS sits in small crates whose names end in `-core`
(`ext4-core`, `usb-core`, `priv-core`, `installer-core` and many others):
code there can be tested on the host.

## 1. Write a kernel test

A kernel test is a function that returns `TestResult`, plus one line that
registers it. This one, from `drivers/src/tests/xe_logic_tests.rs`, checks
that the Intel display driver recognises a particular GPU:

```rust
use slopos_testing::{TestResult, assert_eq_test, assert_test, fail, pass};

use crate::xe_logic::platform;

pub fn xe_platform_identifies_target_a7a8() -> TestResult {
    assert_test!(platform::is_intel_vendor(0x8086));
    assert_test!(!platform::is_intel_vendor(0x1234));

    let plat = match platform::identify(0x8086, 0xa7a8) {
        Some(p) => p,
        None => return fail!("a7a8 must identify as a supported display"),
    };
    assert_eq_test!(plat.generation, platform::XeDisplayGen::Gen13);
    assert_eq_test!(plat.display_ip_version(), 13u8);
    assert_test!(plat.uses_skl_universal_plane_regs());
    pass!()
}

slopos_testing::stest!(name = xe_platform_identifies_target_a7a8, suite = xe_logic);
```

`stest!` adds the test to a list the kernel collects when it is built, so you
don't call it from anywhere. The assertion macros return a failure from the
test and log what they saw, rather than panicking. Put the test in the
`tests` module of the crate it tests, in a file listed in that module's
`mod.rs`.

A test's full name is its module path plus the function name:
`slopos_drivers::tests::xe_logic_tests::xe_platform_identifies_target_a7a8`.
That is the name you filter on and the name you'll see in failures.

Tests run in alphabetical order of their module path and then their name,
except that tests named `bootstrap_…` run first, and some tests rely on that
order. The kernel tests run before the boot mounts the root disk, so a kernel
test that creates files writes to a filesystem in memory, which the test
`slopos_fs::tests::test_ext4_aaa_init` sets up; its name puts it ahead of the
filesystem tests that write files. The lock-order tests live in a module
called `zz_lockdep_tests` so that they run last.

Three flags change how a test is treated. Pass them as
`flags = slopos_testing::FLAG_...` in `stest!`:

| Flag | Effect |
|------|--------|
| `FLAG_EXPECTED_PANIC` | The test is supposed to panic; a panic counts as a pass and is marked `EXPECTED_PANIC` |
| `FLAG_UNCAPTURED` | The test's log goes straight to the console instead of being kept for its failure report. Use it for long tests, whose report would otherwise keep only their first few kilobytes of log |
| `FLAG_EXPLICIT` | The test ends the machine or needs the host to do something, so it runs only when a filter names it in full, never through a wildcard |

A kernel test normally runs in the kernel phase, before any program starts.
Add `kind = Userland` to run it in the userland phase instead, sorted among
the userland tests, for a check that needs init and the services up:

```rust
slopos_testing::stest!(name = init_is_told_apart_by_its_task_id, flags = 0, kind = Userland);
```

## 2. Write a userland test

A userland test is a program. On a test boot, init starts a copy of itself
(`/sbin/init --run-tests`) that asks the kernel to run the userland phase,
so init keeps serving while the tests run: privd answers requests and a test
can ask for a desktop. The kernel then starts each registered program in
turn, and the program reports each of its cases to the kernel, which prints
them with the other results. This is
`userland/src/bin/tests/keymap_test.rs`, cut down to two of its five cases:

```rust
use slopos_userland as _;

use slopos_userland::keymap::current_name as current;
use slopos_userland::syscall::keymap::keymap_get_name;

/// The boot default layout is `us`.
fn get_name_returns_default() -> bool {
    current().as_deref() == Some("us")
}

/// A 1-byte buffer gets exactly one byte, never an overrun.
fn get_name_respects_buflen() -> bool {
    let mut one = [0u8; 1];
    let n = keymap_get_name(&mut one);
    n == 1 && one[0] == b'u'
}

fn main() {
    slopos_slibc::test_harness::run(&[
        ("get_name_returns_default", get_name_returns_default),
        ("get_name_respects_buflen", get_name_respects_buflen),
    ]);
}
```

Each case is a function that returns `true` for a pass. `test_harness::run`
runs them in order, reports each one, and exits with the number that failed.
A program's standard error goes straight to the serial console and is not
kept in the test's log, so a case that fails should say why with
`test_harness::note("...")`: the note travels with the case's result and
appears on its line.
`test_harness::run_with_progress` also prints a line as each case starts,
which tells you which case was running if the program hangs.

A new test program needs four small additions so that it is built, put on
the test system, and run:

1. A `[[bin]]` entry in `userland/Cargo.toml`:

   ```toml
   [[bin]]
   name = "keymap_test"
   path = "src/bin/tests/keymap_test.rs"
   ```

2. A `--bin keymap_test` argument, and the matching copy into `builddir/`,
   in `scripts/build_userland.sh`.
3. The name in `BASE_TEST_PROGRAMS` in `scripts/lib/base.sh`, which puts the
   program in the tests base as `/bin/keymap_test`.
4. A registration in `core/src/utests.rs`:

   ```rust
   crate::utest!(name = utest_keymap, bin = "/bin/keymap_test");
   ```

`utest!` also takes `argv = &["keymap_test", "--flag"]` to pass arguments
(one program can be registered several times with different arguments),
`uncaptured`, with the same meaning as the kernel flag above, and `explicit`,
which is `FLAG_EXPLICIT` plus `uncaptured`, for a test a host script drives.

### Choosing who the test runs as

By default a userland test runs as uid 0 holding every capability. That is
the right default for a test of a privileged program, but it hides any check
that an ordinary program would fail. A test of an unprivileged path, or of
what a person can do at their desktop, says so:

```rust
crate::utest!(name = utest_apps, bin = "/bin/apps_test", caps = none, uid = 1000);
crate::utest!(name = utest_mount, bin = "/bin/mount_test", caps = MOUNT);
```

`caps = none` gives the program only the universal capabilities every program
holds; `caps = MOUNT` (any combination of the constants in `slopos_abi::caps`)
adds exactly those. `uid = 1000` runs it as the first person, and the uid is
its gid too. [Capabilities](/docs/architecture/authority) explains what each
capability allows, and [Users and file permissions](/docs/architecture/users)
what a uid does and doesn't.

### Answering the desktop from a test

Some behaviour only exists once a person is at the desktop: privd asking for
consent, the lock screen, a window's keys. A test boot starts no desktop by
itself, so a test that needs one asks init to restart the sessions
(`init_control::ask(Command::RestartSession)`), waits for one to come in
front, then types into it:

- `test_key(keycode, codepoint, pressed)` hands one key to whoever holds the
  keyboard input, as if a keyboard had sent it. It needs the `TestHarness`
  capability and answers `ENOSYS` on any boot that isn't running the tests,
  so no system a person uses has a keyboard a program can type on.
- `userland/src/bin/tests/support/asking.rs` asks privd from a child process
  as a given uid and session, waits until the question is on screen, and then
  runs the function you give it to answer. `tab_and_enter` and `escape` first
  wait out the moment the dialog ignores input after it appears; `key` and
  `type_text` press keys at once, so call `armed` before them. The result is
  a line such as `ran 0` or `denied by the person …`.
- `userland/src/bin/tests/support/sessions.rs` reads the session table and
  waits until a session is in front.

A test program includes either file with `#[path = "support/asking.rs"]`;
`privd_test.rs` is the fullest example. [Privileged actions](/docs/architecture/privd)
describes the dialog the keys answer.

## 3. Run only your tests

`just test` takes an optional filter: one or more patterns, separated by
commas, matched against the full test names. `*` matches anything.

```bash
just test 'slopos_drivers::tests::xe_logic_tests::*'   # one file of kernel tests
just test '*utest_keymap*'                             # one userland test
just test '*ext4_aaa*,slopos_fs::*'                    # the fs tests, and the test that sets them up
```

<Callout type="warning">
The filter is a positional argument. `just test FILTER='slopos_mm::*'` passes
the text `FILTER=slopos_mm::*` through as the pattern, which matches nothing
you meant.
</Callout>

If your kernel tests create or write files, include `'*ext4_aaa*'` in the
filter, so that the test that sets up their in-memory filesystem still runs
ahead of them. Userland tests don't need it: they run on the root disk, which
the boot mounts after the kernel phase.

Other ways to run the suite:

```bash
just test-rerun-failed                         # only the tests that failed last time
just test-verbose 'slopos_mm::*'               # also print the log of tests that passed
just test-quiet                                # print only failures and the summary
just test 'slopos_core::utests::*'             # every userland test program
just test-raw                                  # the raw serial output, unparsed
just test-elf builddir/guest-tests.elf         # the suite on a kernel built elsewhere
```

A pattern matches the whole name, so `'mm::*'` matches nothing: every name
starts with its crate, `slopos_mm::`. Every `utest!` is registered in
`core/src/utests.rs`, which is why `slopos_core::utests::*` selects all the
test programs. Don't use `just test-userland-only` for that: at this commit
its pattern matches no test in either phase, so it runs nothing and the
runner exits 2.

[Building and testing](/docs/getting-started/build-test-recipes) lists every
test recipe. To run a subset in a manual boot rather than through the
harness, pass `tests=on` and a `tests.run=` pattern on the kernel command
line; [Boot options](/docs/abi/boot-options) describes both.

## Reading a failure

The kernel reports results in KTAP, the plain-text test format Linux uses.
Each test produces a line, and a userland test's cases come first, indented,
followed by the program's own line. For example (the raw serial log puts
`KTAP` and a tab in front of each line, left out here):

```
ok 763 - slopos_drivers::tests::xe_logic_tests::xe_platform_identifies_target_a7a8 # time_ms=0
  ok 1 - get_name_returns_default
  ok 2 - get_name_respects_buflen
  ok 3 - load_switches_layout_and_restores
  ok 4 - load_rejects_bad_blob
  ok 5 - read_missing_returns_err
ok 25 - slopos_core::utests::utest_keymap # time_ms=18
```

The two `ok` numbers count separately because kernel tests and userland tests
run in two phases. A case's note, when it set one, follows a `#` on its line.

`just test` reads that stream and shows a progress bar. When a test fails, it
prints a block for it at the end with the phase, the file and line where the
test is registered, how it ended (`Fail`, or a panic), and the log the test
wrote while it ran. That log is where the assertion macros' messages appear, such as
`ASSERT_EQ: the leader's blocked pending set - expected …, got …` or
`TEST FAIL: a7a8 must identify as a supported display`. For a userland test,
the block also lists every case with a pass or fail mark and its note, so you
see which case failed and why even if the program's log was too long to keep.

After every run you did not interrupt, the names of the failed tests are
written to `builddir/last-fail.list`, which is what `just test-rerun-failed`
reads.
[Test output format](/docs/abi/ktap-test-output) documents every line the
kernel emits and the JSON form the harness can write.

## Host tests

```bash
just test-host
```

This runs `cargo test` on the crates that build for your machine: the
`*-core` crates (all but `service-core`), `abi`, `gfx` and `font`, the build
tools that have tests (`initramfs`, `kallsyms`, `extension` and `icons`), and
the kernel's trusted core (`slopos-ostd`). Write these as ordinary Rust `#[test]` functions. The
trusted core's tests are the same ones Miri runs (see below), run natively
here so a broken assertion shows up in seconds. The TLS crate's tests talk to
OpenSSL and `ssh-keygen`, so both must be on your `PATH`.

`just check-tests-host` runs the Go tests of the test harness itself.

## The long-running checks

These recipes take minutes or longer, and all but `check-fs-image` boot
specially prepared machines, sometimes more than once. They are separate
from `just test`; run the ones that cover what you changed.

| Recipe | Checks |
|--------|--------|
| `just test-persist` | A file written and `fsync`ed in one boot is there in the next |
| `just check-fs-image` | The disk the last `just test` wrote passes `e2fsck`, was left at rest (marked clean, with an empty journal), and keeps the ownership map |
| `just test-rude-exit` | A boot that ends abruptly leaves a journal that the host's `e2fsck` replays correctly. [Crash recovery](/docs/architecture/crash-recovery) explains why this matters |
| `just test-usb` | Both of QEMU's USB controller models with sticks, a hub, keyboards, a mouse, a tablet and a network adapter, pulled out and plugged back in while the system runs. [USB](/docs/architecture/usb) |
| `just test-capacity` | A large volume mounts, can be walked, and can be written |
| `just test-install` | On one disk laid out as on real hardware: registering SlopOS with the firmware, installing a kernel into a boot slot, booting it once, committing it, rolling back from slots that crash, and installing and rolling back a base. [Updating SlopOS](/docs/self-hosting/updating) |
| `just test-installer` | The installer, run from a USB stick and from a CD: onto a blank disk, beside another system and over an existing partition, then each installed disk booted on its own, and the rescue shell. [Installing SlopOS](/docs/self-hosting/installing) |
| `just test-remote` | A machine driven through the broker: commands, file transfers, a base and a kernel installed remotely. [Remote control](/docs/self-hosting/remote-control) |
| `just test-toolchain` | The compilers and tools on the self-hosting disk build a series of programs |
| `just test-install-guest` | SlopOS builds its own kernel and base from the current commit, installs and boots them |
| `just test-selfhost` | SlopOS builds itself from the current commit, and the host checks the result |

`test-install-guest`, `test-selfhost` and (unless you set
`INSTALLER_PAYLOAD=0`) `test-installer` need the cross-built toolchain from
`just toolchain`; see [Toolchain](/docs/self-hosting/toolchain).
`test-install-guest` and `test-selfhost` also refuse to start while the
working tree has uncommitted changes, because the guest builds `HEAD`:
commit or stash first.

One more recipe boots the live system but checks nothing: `just ui-shots`
saves a picture of every screen of the desktop, the installer and each app
under `builddir/ui-shots/` for you to look at after a change to how
something looks. The layout checks that do fail live in `appkit_test`, which
`just test` runs.

For the code that the proofs and Miri cover (`slopos-ostd/` and
`verification/`), also run:

```bash
just check-miri     # runs the trusted core's tests under Miri, which detects undefined behaviour
just verify         # checks the Verus proofs
```

[Miri](/docs/verification/kernmiri) and [Proofs](/docs/verification/verus-status)
explain what each one catches.

## What CI runs

A passing `just test` is necessary but not enough. CI runs four jobs in
parallel:

- **ci**: `just fmt`, the full test boot and the checks that follow it, then
  `check-fs-image`, `test-persist`, `test-rude-exit`, `test-usb` and
  `test-toolchain`.
- **gates**: `just test-host`, a kernel build, every check in
  `just check-framekernel-gates`, an offline build from the vendored
  dependencies, a build of the release kernel with its own checks, and the
  codegen-backend and linker checks with the alternatives installed.
- **toolchain**: builds the tests userland and the recipes (the C libraries
  and programs the self-hosted tools need), and checks the C library's
  exports, the C++ runtime, the LLVM port, the clang driver and the
  compiler cross-build against them.
- **ostd-verify**: `just check-miri` and `just verify`.

The checks that follow the test boot hold the line on numbers that should
only move on purpose. All but the authority check read the boot's log; that
one reads the tests kernel itself:

| Check | Fails when |
|-------|-----------|
| Test count | Fewer tests are planned than the baseline in `scripts/check_test_count.sh` |
| Lock order | The lock-order checker (see [Diagnosing the kernel](/docs/development/diagnostics#a-lock-problem)) wasn't active, reported a violation, or went past a limit recorded in `scripts/gates/lockdep/` (how many lock types it registered, or how full its tables are) |
| CPU spread | A CPU that is online can't be given tasks |
| Authority | A system call can reach a power-off or reboot function without being classified `Power` or listed with a reason |

To grade a local run the way CI does, capture the raw log once and run the
checks on it:

```bash
just _build-run-tests
set -o pipefail
builddir/run_tests --raw --no-color 2>&1 | tee builddir/ci-test.log
scripts/check_authority_reachability.sh --variant tests builddir/kernel-tests.elf
scripts/check_test_count.sh       --log builddir/ci-test.log
scripts/check_lockdep_headroom.sh --log builddir/ci-test.log
scripts/check_sched_spread.sh     --log builddir/ci-test.log
```

Two more checks read the same log but aren't CI steps yet:
`check_quota_headroom.sh` (resource accounts stay under their caps) and
`check_fs_throughput.sh` (the filesystem doesn't issue more disk writes per
megabyte than it used to). Run them when you touch resource accounting or the
filesystem's write path. [Safety gates](/docs/verification/tcb-discipline)
lists every check, including the ones that don't read a test log.

## What usually goes wrong

- **You added tests and the baseline stayed where it was.** The test count
  check only fails when the count drops, so nothing makes you raise it, but
  you should: measure the new count with
  `TEST_COUNT_BASELINE=0 scripts/check_test_count.sh` and raise the baseline
  in the script in the same commit, so a later change that deletes your
  tests fails.
- **A lock, quota or throughput check fails after a real change.** A new
  lock, lock ordering or resource account moves a recorded number. Treat the
  failure as a measurement: regenerate the recorded data with the script's
  `--emit-allowlist` option, commit it with your change, and say in the commit
  message what moved it. Never edit `scripts/gates/` by hand to make a run
  pass.
- **A filtered run fails in a test that passes in the full suite.** It is
  probably a kernel test that writes files, and your filter left out
  `*ext4_aaa*`.
- **A userland test passes as uid 0 and the feature fails for a person.**
  The test ran holding every capability. Register it, or a second copy of it
  with an argument, with `caps = none, uid = 1000`.
- **A long test's failure report has no useful log.** The report keeps only
  the start of each test's log. Mark the test uncaptured, print less, or put
  the reason in a case's note.
- **You added an app and `dock_test` or `apps_test` fails.** Both hold a
  fixed list of the apps the system installs: `INSTALLED` in
  `userland/src/bin/tests/dock_test.rs`, and `APPS` and `CASES` in
  `userland/src/bin/tests/apps_test.rs`. Add the new app to each, and to
  `APPS` in `scripts/ui_shots.py` so `just ui-shots` photographs it.
  [Write an app](/docs/development/writing-an-app#6-hold-it-to-the-tests)
  shows the rows.
- **A test that needs the desktop times out.** A test boot starts no session
  until one is asked for; ask init to restart the sessions first and wait for
  one in front.
