description: "What to do when SlopOS hangs, kills a program, panics, runs slowly or reports a lock problem."

When SlopOS hangs, kills a program with an oops, panics, runs slowly or
reports a lock problem, the kernel's own log usually tells you why. For each
of those symptoms, the sections below say what to do, what you'll see and how
to read it. Most of the time you won't need a debugger; when you do,
[Debugging with GDB](/docs/development/debugging-gdb-record-replay) picks up
where this page stops.

## Before you start: where the kernel's output goes

Everything below appears in the kernel log. Under QEMU the log goes to the
serial port, which `just boot` and the other boot recipes print in your
terminal; `just boot-log` saves it to `test_output.log`. On a machine with no
serial port, the kernel can draw the log on screen: press Esc while the boot
screen is showing to toggle it. Once the desktop has drawn its first frame,
Esc belongs to applications again. The on-screen log is drawn from the
kernel's timer, so it keeps working when every program is stuck.

On a machine paired with your host for
[remote control](/docs/self-hosting/remote-control), read the log from the
host instead:

```bash
just remote klog            # the kernel log as it stands
just remote klog --follow   # and whatever it adds from then on
```

Several steps below use boot options. To try one, put it on the command line
of a live boot (the default options are `tests=off root=initramfs`, so keep
them):

```bash
BOOT_CMDLINE='tests=off root=initramfs lockdep=warn' just boot-live
```

`just boot`, which boots the development machine, does not read
`BOOT_CMDLINE`, and neither does an installed system, whose boot entries are
fixed. For those, build the kernel with `SLOPOS_BUILTIN_CMDLINE` set: the
kernel appends those options to whatever the loader gave it and logs
`BOOT: built-in command line appended: …`. [Boot options](/docs/abi/boot-options)
describes every option mentioned here.

## The diagnostic console

The diagnostic console is SlopOS's equivalent of Linux's
[magic SysRq key](https://docs.kernel.org/admin-guide/sysrq.html): you press
a key combination on the machine's own keyboard, and the kernel prints a
report to its log. It is the tool you'll reach for first, because it is
handled where the keyboard's input arrives, ahead of every program, so it
answers when nothing else does.

### How to trigger it

- **From the keyboard.** Press **SysRq** (Alt+PrintScreen) and then, within
  three seconds, one command key. Any keyboard works, PS/2 or USB. Under QEMU,
  if your desktop takes PrintScreen for itself, send the keys from the QEMU
  monitor instead (see
  [Debugging with GDB](/docs/development/debugging-gdb-record-replay) for how
  to open it): `sendkey sysrq`, then `sendkey t`.
- **From a serial line.** Send a BREAK, then the command key.
- **From a program.** `/bin/kconsole` takes command keys as its argument,
  runs each one and prints what it added to the kernel log, for example
  `kconsole tw`. With no argument it runs `h`. It reaches the kernel through
  privd's `org.slopos.kconsole` action, which an administrator and the paired
  agent may run unasked, so `just remote run -- kconsole tp` reads a machine
  nobody is sitting at.

### The command keys

| Key | Prints | Changes the machine |
|-----|--------|---------------------|
| `h` | The list of commands this kernel has, and the permission mask | no |
| `t` | Every task: its state, which CPU it's on, why it's blocked, where it's parked | no |
| `w` | Only the blocked tasks, each with a stack trace | no |
| `x` | Tasks that have exited but haven't been collected, and who should collect each one | no |
| `s` | Scheduler counters, per CPU and in total | no |
| `i` | The kernel's I/O service threads: state and how many rounds each has done | no |
| `k` | The longest stall each CPU has seen, and each CPU spinning on a lock, with the chain of CPUs holding what the next one waits for | no |
| `p` | Asks every other CPU for its registers and what it is running, and prints a stack trace for this one | no |
| `d` | Whether the lock-order checker is active, and how full its tables are | no |
| `m` | Memory: the page allocator, per-CPU caches, the small-object allocator | no |
| `c` | Each CPU's memory-type settings | no |
| `q` | Resource accounts: used, peak, limit and refusals for each kind of resource | no |
| `n` | Network interfaces, addresses, routes and connectivity | no |
| `u` | USB controllers, ports, devices, drivers and transfer queues | no |
| `f` | Framebuffer drawing speed per CPU | no |
| `o` | Writes back the filesystems and powers off | yes |
| `b` | Reboots | yes |

### Why nothing happens

- **The command changes the machine.** `o` and `b` are refused unless you
  boot with `kconsole=0x3`, and the log says
  `kconsole: 'o' (poweroff) refused by policy (kconsole=0x1)`. No program can
  run them at all, whatever the mask: `/bin/kconsole` answers
  `refused: the command may change the machine`.
- **The console is off.** `kconsole=off` turns it off entirely; the default,
  `kconsole=on`, allows the commands that only print.
- **The key came too late.** The trigger stays armed for three seconds
  (`kconsole.arm_ms`). A key no command takes logs a line starting
  `kconsole: no command for`.
- **The serial trigger is off.** `kconsole.serial=off` disarms BREAK.

Nothing a program does can reach a command that changes the machine: the
keys are taken before they reach any program, and a serial BREAK isn't a
byte a program can write. This is narrower than Linux, whose
`/proc/sysrq-trigger` lets an administrator run any command.

## The machine is stuck

**What to do.** First press SysRq and `w`. If the system is up but some
programs are stuck, this shows every blocked task and the stack it's blocked
on, which usually names the thing it's waiting for. `t` shows all tasks, and
`k` shows any CPU spinning on a lock, following the chain of CPUs that hold
what the next one waits for, and says when that chain closes in a circle.

If the console doesn't answer either, the CPU that handles the keyboard is
stuck too. Wait for the watchdog (below), or attach a debugger: boot with
`just boot-debug` and run `just debug-bt` in a second terminal for a stack
trace from every CPU.

**What you'll see.** A *watchdog* runs in the kernel and checks that every
CPU keeps making progress: each CPU watches the next one and checks that its
timer interrupt is still being handled. A CPU that misses about a second's
worth of checks (100 samples by default) is reported:

```
WATCHDOG: cpu 0 made no progress for 3 samples (watcher cpu 1)
WATCHDOG:   not spinning on a tracked lock
NMI: cpu 0 stalled rip=0xffffffff802f6034 <core::ptr::read_volatile::<u64>+0x0x0000000000000024> rsp=0xffffffff81789280 rbp=0xffffffff817892a0 cs=0x0000000000000008
NMI: oops 1 recorded, resuming
```

(This is from the watchdog's own test, which uses a much lower threshold.)

**How to read it.** The first line names the stuck CPU and the CPU that
noticed. The second says whether the stuck CPU is waiting for a lock the
kernel tracks; if it is, the report names the lock and the CPU holding it,
following the chain if that CPU is waiting too. Then the watcher interrupts
the stuck CPU with a signal it can't mask (an *NMI*), and the stuck CPU
prints where it is: `rip=` is the instruction it's running, and the symbol
next to it is the function. Here, it was spinning on a read from device
memory.

A stall that lasts five times the threshold is fatal, and so is a chain of
CPUs waiting on each other in a circle (a deadlock), on the first report.
Under a hypervisor, a CPU that the host didn't schedule looks exactly like a
stuck one, so there the watchdog only reports unless you boot with
`watchdog.panic=on`. A fatal stall ends the machine as a panic does,
leaving a crash record (below) with the message
`NMI watchdog: CPU made no progress, sustained`.

## A program died with an oops

**What to do.** Look in the kernel log for a line starting `panic
recovery:`. To see what one looks like, boot with a test that triggers one
deliberately:

```bash
BOOT_CMDLINE='tests=off root=initramfs panic.recover_smoke=on' just boot-log
grep -E 'panic recovery|SMOKE' test_output.log
```

**What you'll see.** Two deliberate panics, one in a kernel thread and one
in a program's system call, each followed by a line saying the kernel
survived (the order can vary):

```
panic recovery: kthread task=<id> boot/src/early_init.rs:1035:5: panic.recover_smoke: deliberate recoverable kthread panic (oops total=<n>)
PANIC RECOVERY SMOKE: cleanup observed; kernel survived
panic recovery: syscall task=<id> core/src/syscall/test_handlers.rs:156:5: test_panic: deliberate syscall-context panic (panic.recover_smoke) (oops total=<n>)
SYSCALL PANIC SMOKE: task died; kernel survived
```

**How to read it.** A *panic* is the kernel finding itself in a state it
wasn't written to handle. If that happens while the kernel is working on a
program's system call, or in one of its own background threads (other than
a CPU's idle task), SlopOS doesn't take the whole machine down: it stops the
system call and ends the thread that made it, or ends the kernel thread,
releases the locks the failed code held, and carries on. Linux calls this an *oops*.
The line says which kind it was, and gives the task, the source file, line
and column where the panic happened, the panic message, and how many oopses
this boot has had.

An oops is still a kernel bug. Recovery cleans up what Rust's ownership
cleans up, but some state (a counter, a reference count) may now be wrong.
That's why the number is limited: the 100th oops in a boot (by default; set
it with `panic.oops_limit`) is a full panic. To stop at the first one
instead, which is what you want while debugging, boot with
`panic.on_oops=on`. Test runs always do: with `tests=on`, every panic is
fatal. An oops leaves no crash record of its own, but its report goes into
the kernel log, so a later panic's record carries it.

## The kernel panicked

**What you'll see.** Any other panic stops the machine. It prints a block
like this one, from a boot whose setup failed:

```
=== KERNEL PANIC ===
boot/src/early_init.rs:319:9: Boot init step failed
tainted: oops=3
Register snapshot:
RSP: 0xFFFFFFFF81788B60
CR0: 0x0000000080010013
CR2: 0x0000000000000000
CR3: 0x000000001BFC1000
CR4: 0x00000000003406A0
Backtrace (most recent call first):
  #0 rbp=0xffffffff81788c50 rip=0xffffffff80001747 __rustc::rust_begin_unwind+0x27
  #1 rbp=0xffffffff81788c70 rip=0xffffffff8098ba44 core::panicking::panic_fmt+0x74
  #2 rbp=0xffffffff81788ca0 rip=0xffffffff80031f61 slopos_boot::early_init::boot_run_step+0xe1
```

then `Kernel panic: unrecoverable error`, a line saying what became of the
crash record (next section), and the same report on screen.

**How to read it.** Start with the second line: the file, line and message
of the panic. `tainted: oops=3` means the boot had already recovered from
three oopses, so the real cause may be one of those; scroll up for their
`panic recovery:` lines. The registers matter mostly for memory faults: `CR2`
is the address the CPU failed to access. The backtrace lists the calls that
led here, newest first, already translated into function names (the kernel
carries its own symbol table, so you don't need to run anything on the
output). Skip the first frames, which are the panic machinery, and read from
the first function you recognise.

**What to do.** If the panic is reproducible, the backtrace is often enough.
If it isn't, or you need to see variables,
[Debugging with GDB](/docs/development/debugging-gdb-record-replay) shows how
to stop at the panic and how to record a run and step backwards from it.

By default a panicked machine stops on its panic screen so you can read it,
and nothing runs after that. With `panic=reboot` it resets instead,
after holding the screen for ten seconds on real hardware (not under a
hypervisor, whose log you already have). The installer gives an installed
system `panic=reboot` unless you name another command line (`--cmdline`), so
a kernel tried in its spare slot that panics hands the machine back to the
default slot ([Updating SlopOS](/docs/self-hosting/updating)). The
development machine's boot disk leaves it out, so a panic there stays on
screen.

To see a panic on purpose, `panic.fatal_smoke=on` raises one right after
boot.

### The crash record

A machine with no serial port, or one that resets after a panic, would lose
the report. So a fatal panic also writes it to the boot disk, the way Linux's
pstore keeps a panic's log for the next boot. The disk SlopOS was installed
on carries a small *crash partition*, a ring of slots, and each panic writes a
*crash record* into one: a summary, the panic report and the newest lines of
the kernel log. Then the next boot saves it as a file.

1. **At boot, the kernel finds the store.** On the disk Limine loaded the
   kernel from, it claims the crash partition for itself and logs
   `CRASH: records go to <partition> (<n> slots, <n> held)`. The development
   machine's boot disk and every installed disk have one; the live ISO does
   not, and a disk that isn't an NVMe drive keeps no records yet, because the
   record is written through the NVMe driver's own polled queue, which needs
   no interrupts, waits for no lock and allocates no memory.
2. **At the panic, the kernel writes the record** before it waits or resets,
   and says how it went on serial and on the panic screen:
   `crash record: <n> written to <partition> slot <n>`, or
   `crash record: none, the boot disk keeps no crash store`. The lockup the
   watchdog ends (above) writes one too; a kernel stack overflow can't, since
   writing needs the stack that ran out.
3. **At the next boot, init saves it.** Before any service starts, init runs
   `bootctl collect`, which copies each record to
   `/var/log/crash/<index>-<UTC time>-<slot>.txt`, makes the copy durable, and
   only then erases the record. It prints, for example,
   `bootctl: crash record 1 saved to /var/log/crash/000003-20261029T101502Z-b.txt: <panic>`.
   It keeps the newest 64 files and any file a slot names as its last crash,
   and erases nothing while `/var/log/crash` is on no writable disk, so a
   record waits in the partition until a boot can keep it.

A saved record opens with its summary:

```text
SlopOS crash record
kernel: /boot/b/kernel.elf
cmdline: <the kernel's command line>
build: <build tag>
time: <unix seconds>
uptime: <n> ms
cpu: <n>
panic: <file:line:column: message>
```

followed by the panic report and, under `--- kernel log ---`, the log's last
lines. The kernel's path names the slot it came from, so `bootctl status`
shows each slot's last boot and last crash:

```text
slot b: kernel <n> bytes, last boot crashed: /var/log/crash/000003-20261029T101502Z-b.txt
```

Installing a new kernel into a slot clears both. The records themselves are
also files under `/dev/crash`, one per record, named by its sequence number
and ending in `-torn` when its checksum fails (a reset cut it short); reading
or removing one takes the `RawBlock` capability, since a record is the
kernel's state as it died.

## Something is slow

**What to do.** For a quick look at a running system, press SysRq and `s`
for scheduler counters, `w` to see what blocked tasks are waiting on, and `i`
to see whether the kernel's I/O threads are making progress.

For numbers, use the sampling profiler. It is off by default and costs
nearly nothing when off. On a running system, `/bin/prof` starts and stops
it (through privd's `org.slopos.prof`, which an administrator runs unasked):

```sh
prof start
# ... run the slow thing ...
prof report slow > slow.log
prof stop
```

`prof report <label>` prints the report's lines, which start `PROF[<label>]:`,
and `scripts/prof_report.py --label slow slow.log` on the host turns them
into tables. To profile one of the self-hosting checks instead, add `prof=on`
to its command line through `TEST_CMDLINE_EXTRA` (which `test-toolchain` and
`test-selfhost` read, and `just test` does not), and the report comes at the
end of its test run:

```bash
TEST_CMDLINE_EXTRA=prof=on just test-selfhost
```

`just bench-selfhost` does this for you on SlopOS building itself, and
summarises the result with `scripts/prof_report.py`.

**What you'll see.** Lines that start `PROF[<label>]:`, covering:

- per CPU, time spent in programs, in the kernel and idle, how much of the
  time it was busy, and how fast it actually ran;
- the kernel functions where the most samples landed, and the programs
  using the most time;
- time spent in each system call and in page faults;
- where blocked programs were waiting, sampled each time a CPU goes idle;
- calls per futex, how long each context switch keeps interrupts off, and
  how long tasks waited for and held the filesystem's lock and each address
  space's lock;
- disk reads, writes and flushes, with the time they took.

**How to read it.** Start with the per-CPU split. Mostly idle while the work
is slow means tasks are waiting, so read the "where blocked programs were
waiting" lines. Mostly kernel time means look at the hottest kernel
functions and the system call times.

A CPU that runs slower than it should is the other usual cause, especially
on a laptop. `cpufreq run -- <command>` runs a command and then prints, per
CPU and per kind of core, how long it was busy and its effective clock
speed, the package temperature and what limited the speed, ending with one
`CPUFREQ[run]:` line to compare between runs.
[CPU frequency](/docs/architecture/cpu-frequency) explains the numbers.

## A lock problem

A *lock* lets one CPU at a time use a piece of shared data. Two CPUs that
each hold one lock and wait for the other's will wait forever. The kernel
prevents this with a *lock-order checker*, modelled on Linux's
[lockdep](https://docs.kernel.org/locking/lockdep-design.html): every time
code takes a lock while holding another, the checker records that order, and
if anything ever takes the same two kinds of lock in the opposite order, it
reports it, even if the two never collided at run time.

**What you'll see.** By default the first violation panics, so it shows up as
a kernel panic whose message starts `LOCK DEPENDENCY CYCLE`. Before that the
log has the full report:

```
LOCKDEP: dependency cycle
  acquiring  <lock> (<file:line>) level <n>  inst <address>
  while held (outermost first):
    …
  existing path (<n> hops):
    -> <lock> (<file:line>)
    …
```

**How to read it.** "Acquiring" is the lock that would close the circle and
where it was taken. "While held" is what this CPU already held. "Existing
path" is the order the checker saw earlier, which this acquisition
contradicts. One of the two orders is wrong; fix the code so both places
take the locks in the same order.

**What to do.** A single violation stops the boot, so if you suspect more
than one, boot with `lockdep=warn`: the checker reports each problem once and
carries on, so one boot lists them all. SysRq `d` shows how full the checker's
tables are. The kernel also prints a summary line at boot and after each test
phase:

```
LOCKDEP[boot]: ACTIVE classes=<n>/<max> (<n>%) edges=<n>/<max> chains=<n>/<max> declared=<n>/<n> held_max=<n>/<max> held_drops=0 chain_hit=<n> chain_miss=<n> violations=0 reports=0 collisions=0 leaked=0 mode=Panic
```

CI reads those lines and fails if there's a violation or the tables grow past
their recorded limits; see [Write tests](/docs/development/adding-tests#what-ci-runs).

A hang where a CPU is spinning on a lock shows up as a watchdog report
instead, with the lock and its holder named; see
[The machine is stuck](#the-machine-is-stuck).

## Other switches

- `boot.debug=on` raises the kernel log to debug level for the whole boot.
  `just test` sets it.
- `tp.debug` turns on touchpad diagnostics, and a check for tasks left
  asleep by a missed wake-up.
- `usb=report` logs each USB controller's capabilities, protocols and ports
  and leaves the controller to the firmware; [USB](/docs/architecture/usb)
  covers the rest.
- `LD_DEBUG`, an environment variable rather than a boot option, makes the
  dynamic loader trace what it loads; see [Userland](/docs/architecture/userland).

Read next: [Debugging with GDB](/docs/development/debugging-gdb-record-replay)
for stopping the kernel and inspecting it, and the Linux documentation on
[lockup detectors](https://docs.kernel.org/admin-guide/lockup-watchdogs.html),
[bug hunting](https://docs.kernel.org/admin-guide/bug-hunting.html) and
[pstore/blk](https://docs.kernel.org/admin-guide/pstore-blk.html), which
explain the same kinds of report, and the same idea of a panic log kept on a
disk, on Linux.
