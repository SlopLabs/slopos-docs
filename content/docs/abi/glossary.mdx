---
title: "Glossary"
description: "The words SlopOS uses for its own ideas, what each means, and where it is explained."
---

The terms below are the ones SlopOS gives its own ideas, in the sense the
source tree uses them. Each entry says what the term means, what other
systems call the nearest thing where there is one, and which page explains
it. Words with their usual Unix meaning (process, file descriptor, inode,
mount) are not listed.

| Term | Meaning | Elsewhere | Explained in |
|---|---|---|---|
| Accounts record | The sealed store in `/var/lib/slopos/accounts` that lists the people: each one's uid, name, home, whether they administer the machine and their password's hash, and whom the desktop logs in by itself. `/etc/passwd`, `/etc/group` and `/etc/shadow` are written from it and from the extensions' records | `/etc/passwd` and `/etc/shadow` on Linux | [Users and file permissions](/docs/architecture/users#the-accounts-record) |
| Action | A named thing privd will do on request, such as `org.slopos.power.reboot`: the program it runs, the arguments it accepts, the capabilities it gets and who may ask for it | A polkit action | [Privileged actions](/docs/architecture/privd), [privd actions](/docs/abi/privd-actions) |
| Activation | One extension image shown read-only at `/opt/<name>`. Replacing it makes a new activation; the old one is freed once nothing uses it | A mounted system extension | [Extensions](/docs/architecture/extensions) |
| Administrator | A person the accounts record marks as one, and so a member of the `admin` group. privd's `admin` principal names them; the kernel grants them nothing | A member of `wheel` or `sudo` | [Users and file permissions](/docs/architecture/users) |
| App | A program with a window, usually with an entry in the dock. The base carries a few (the terminal, the System Monitor, the installer window); the apps shipped outside it (editor, file manager, image viewer, widget gallery, which has no dock entry) live in a tree under `/usr/local` | Desktop application | [Desktop](/docs/architecture/desktop), [Installed software](/docs/architecture/software) |
| App entry | A `share/slopos/apps/<id>.app` file naming an app's id, name, program and icon, which the dock reads | A `.desktop` file | [Installed software](/docs/architecture/software) |
| Base | The read-only userland image: `/bin`, `/sbin`, `/lib`, `/usr/bin`, `/usr/share` and `/etc/ssl`, packed as one archive and mounted over the root at boot | The read-only `/usr` of an image-based system | [Base system](/docs/architecture/base) |
| Base interface | The number naming the private call surface a base was built against. A kernel serves a range of them and boots only a base inside it | | [Base system](/docs/architecture/base), [Interfaces and stability](/docs/abi/interfaces) |
| Boot partition | The FAT32 partition holding the kernel slots and the two bases, `current` and `previous` | `/boot` | [Updating SlopOS](/docs/self-hosting/updating) |
| Broker | The program on the developer's host (`scripts/remote.py serve`) that a paired machine dials and that hands it commands | | [Remote control](/docs/self-hosting/remote-control) |
| Capability | A named power, such as `Power` or `Mount`, held as one bit of a process's capability mask. A uid grants none | A Linux capability (`CAP_SYS_BOOT`) | [Capabilities](/docs/architecture/authority) |
| Ceiling | The most a grant may include: the base's list for extensions, a signing key's list, or `REQUESTER_CEILING` for an action that runs as the person who asked, as `priv` does | A bounding set | [Extensions](/docs/architecture/extensions), [Privileged actions](/docs/architecture/privd) |
| Claim | A block device's record of who is using it: a write claim is exclusive, read claims share. Mounts and raw writes take one | Exclusive open of a block device | [Disks](/docs/architecture/storage) |
| Commit (a slot) | Making the kernel that booted this time the default, after a one-shot boot proved it | Marking a boot entry good | [Updating SlopOS](/docs/self-hosting/updating) |
| Consent dialog | The question the desktop shows when privd needs a person to allow an action, with a click or a password | A polkit authentication agent, UAC prompt | [Privileged actions](/docs/architecture/privd), [Desktop](/docs/architecture/desktop) |
| Crash partition | A small partition on the boot disk where a panicking kernel writes a crash record | pstore backend | [Diagnosing the kernel](/docs/development/diagnostics) |
| Crash record | The panic report and the tail of the kernel log, written to the crash partition as the kernel dies and copied to `/var/log/crash/` at the next boot | A pstore or ramoops record | [Diagnosing the kernel](/docs/development/diagnostics) |
| Credentials | A process's real, effective and saved uid and gid and its supplementary groups. They say who a process is, never what it may do beyond file permissions and whom it may signal | Linux `struct cred` | [Users and file permissions](/docs/architecture/users) |
| Current, previous | The two bases on the boot partition. Every slot boots current; previous is the one that ran before it, which a kernel that can't serve current boots instead and which `bootctl base rollback` makes current again |  | [Base system](/docs/architecture/base#where-the-base-lives-on-disk) |
| Delegate | To hand a child, when spawning it, some of the capabilities the parent holds. A child never gets more than its parent | | [Capabilities](/docs/architecture/authority) |
| Diagnostic console | Keys pressed on the physical keyboard (Alt+PrintScreen, then a command key) or a serial BREAK that make the kernel print its state | Magic SysRq | [Diagnosing the kernel](/docs/development/diagnostics) |
| Extension | Software installed as a signed or approved image, shown read-only at `/opt/<name>`, whose services run as users of its own and whose powers are its grant | A systemd system extension | [Extensions](/docs/architecture/extensions) |
| First person | The person with uid 1000, named `user` unless the installer was told otherwise. They hold the workspace at `/src` and cannot be removed | The first user an installer creates | [Users and file permissions](/docs/architecture/users) |
| First user (of an extension) | The user an extension's first `user` line declares. It owns the extension's log, state and runtime directories, and the mechanisms of the extension's actions run as it. Not the first person | | [Extension images](/docs/abi/extension-images#declarations) |
| Framekernel | A kernel in which one trusted crate holds every line of `unsafe` code and all others are forbidden it | (Asterinas's term) | [The framekernel](/docs/verification/framekernel) |
| Gated capability | Any capability except the three universal ones; holding one makes a program start in secure mode | | [Capabilities](/docs/architecture/authority) |
| Generation | One base as served while the system runs. The base booted is generation 1; each live replacement is the next. Also one numbered copy of a sealed store's file (the accounts record, an extension's record, the trusted keys), of which the newest sealed one is believed | | [Base system](/docs/architecture/base), [Users and file permissions](/docs/architecture/users#the-accounts-record) |
| Grant | What an extension may hold and do: capabilities, actions people reach unasked, users and commands. A person approves it at a first install; a signed install takes it unasked within the signing key's ceilings | | [Extensions](/docs/architecture/extensions) |
| Greeter | The login screen, run by the compositor as the base's `greeter` user (uid 50) | A display manager's greeter | [Sessions and login](/docs/architecture/sessions) |
| In front, behind | Whether a graphical session holds the screen and the input now. A desktop behind is locked | Active and inactive sessions | [Sessions and login](/docs/architecture/sessions) |
| Install medium | The live ISO, on a CD or a USB stick, that boots SlopOS from RAM and carries the installer | Installation media | [Installing SlopOS](/docs/self-hosting/installing) |
| Kept directory | A directory the kernel holds in place once the root and the `mount=` volumes are up (`/etc`, `/var/lib/slopos` and the stores under it): it cannot be renamed or removed, nothing may be mounted at, above or beneath it, and the volume holding it cannot be unmounted | | [Filesystem](/docs/architecture/filesystem#directories-the-kernel-keeps-in-place) |
| KTAP | The line format the test harness prints results in | (Linux's kernel test format) | [Test output format](/docs/abi/ktap-test-output) |
| Level | How much privd asks of a person before it runs an action for them: nothing, `confirm` (a click at their own desktop, their password elsewhere), `password` (their own password) or `alone` (for `user`: nothing for an administrator or while nobody else is logged in, and otherwise an administrator's password; for `greeter`: nothing while nobody is logged in, and otherwise refused) | polkit's `yes`, `auth_self`, `auth_admin` | [Privileged actions](/docs/architecture/privd#who-may-ask-and-what-they-must-do) |
| Live boot | A boot from the install medium onto a root in RAM, so nothing done there is saved. Its desktop opens the installer's welcome page | A live CD session | [Installing SlopOS](/docs/self-hosting/installing#starting-the-computer-from-it) |
| Lock screen | What a desktop shows while it is locked: the time, the person's name and a field for their password. The desktop's own compositor draws it | A screen locker | [Sessions and login](/docs/architecture/sessions#locking-and-unlocking) |
| Login screen | The screen that lists the people and asks the chosen one for their password, shown at boot when nobody is logged in automatically, on *Switch user…* and after logging out. The compositor runs it as the `greeter` user | A display manager's login screen | [Sessions and login](/docs/architecture/sessions#logging-in-at-the-login-screen) |
| Login tag | A number every process carries and passes to its children, naming the session, or the system service, it belongs to. Only a `SetId` holder gives a new process another one | Linux's audit session id | [Sessions and login](/docs/architecture/sessions#login-tags) |
| Manifest | The list of what a base, an extension image or a tree holds, which an install, an update or a replacement reads to know what is there. A base and an image carry theirs inside them; a tree's is kept under `/var/lib/slopos/trees`, or under `~/.local/share/slopos/trees` for a tree in a person's home | | [Base system](/docs/architecture/base), [Extension images](/docs/abi/extension-images#extensionmanifest), [Installed software](/docs/architecture/software) |
| Mechanism | The program privd starts to carry out an action, with the action's capabilities | A polkit mechanism | [Privileged actions](/docs/architecture/privd) |
| OSTD | `slopos-ostd`, the one kernel crate allowed `unsafe`. SlopOS reads the name as Operating System Trusted Domain; Asterinas, where it comes from, as Operating System Standard Library | | [The trusted core](/docs/verification/ostd-trusted-core) |
| Ownership map | Which directories of a root belong to uid 0 and which to the first person, with their modes. The image builders, the installer and init lay every root out by it, and `/var/lib/slopos/owners` records the trees the first person holds |  | [Users and file permissions](/docs/architecture/users#who-owns-what-on-a-disk) |
| Paired agent | `remoted` on a machine whose base carries a pairing with a broker. privd's `paired` principal | | [Remote control](/docs/self-hosting/remote-control) |
| Pairing | The broker's address, certificate authority and token, packed into a base at `/usr/share/slopos/remote/`. `remoted` dials the broker it names and reads it from nowhere else, so no program can point the agent at another broker | | [Remote control](/docs/self-hosting/remote-control) |
| Payload | The partition on an install medium that holds the toolchain and the source, installed alongside SlopOS | | [Installing SlopOS](/docs/self-hosting/installing) |
| Person | A human with an account in the accounts record, uid 1000 to 59999 | A regular user | [Users and file permissions](/docs/architecture/users) |
| Pinned mount | A mount that `umount` refuses and under which nothing else may be mounted, as the base's directories are | | [Base system](/docs/architecture/base#how-the-base-appears-in-the-file-tree), [Filesystem](/docs/architecture/filesystem) |
| Principal | Who an `allow` line in privd's policy names: `root`, `user`, `admin`, `greeter`, `paired` or a `program` | polkit's subject | [Privileged actions](/docs/architecture/privd) |
| privd | The privilege broker: the service that runs actions on behalf of programs that may not do them, asking the person first when the policy says so | polkitd | [Privileged actions](/docs/architecture/privd) |
| Requester | The program that asks privd for an action | polkit's subject process | [Privileged actions](/docs/architecture/privd) |
| Rescue shell | A shell holding every delegable capability, started from the install medium to repair an installed system | A recovery shell | [Installing SlopOS](/docs/self-hosting/installing) |
| Safety gate | A script that fails the build or CI when the source tree, the compiled kernel, the built userland or a test run breaks one of the tree's rules, such as `unsafe` code outside the trusted core or a kernel stack frame over 2 KiB |  | [Safety gates](/docs/verification/tcb-discipline), [Interfaces and stability](/docs/abi/interfaces) |
| Seal | A file or directory marked immutable, which only a `Seal` holder can mark or unmark. Every file of the base is sealed | The immutable attribute (`chattr +i`) | [Filesystem](/docs/architecture/filesystem#sealed-files) |
| Seat | Either of the two things one process holds at a time: the screen, or the stream of input events. Init hands both from session to session | A logind seat | [Sessions and login](/docs/architecture/sessions#how-the-seat-moves-between-sessions), [Windowing](/docs/architecture/userland-windowing) |
| Secure mode | How a program starts when it holds a gated capability or runs with ids other than its spawner's real ones (`AT_SECURE`): the loader ignores `LD_LIBRARY_PATH` and `$ORIGIN` and searches no library directory a person can write | Linux's secure-execution mode for setuid programs | [Capabilities](/docs/architecture/authority#how-a-process-gets-its-capabilities) |
| Session | A person's desktop, the login screen, or a shell a console login started, each with its own login tag. `remoted` also runs in a background session of the person it runs as | A logind session | [Sessions and login](/docs/architecture/sessions) |
| Sidecar | The three-line file beside an extension image naming its extension, version and root. A trusted key signs it, which lets `extctl install-signed` install the image unasked | | [Extension images](/docs/abi/extension-images#sidecar) |
| slibc | SlopOS's C library, `libc.so`, written in Rust | glibc, musl | [Userland](/docs/architecture/userland) |
| SlopRing | SlopOS's submission and completion ring for asynchronous I/O | io_uring | [SlopRing](/docs/abi/slopring) |
| Slot | A directory on the boot partition holding one kernel, `/boot/a` or `/boot/b`. The loader offers each as an entry, `slopos-a` and `slopos-b` | An A/B partition | [Updating SlopOS](/docs/self-hosting/updating) |
| Spare slot | The slot whose kernel is not the default, where a new kernel is installed to be tried | The inactive slot | [Updating SlopOS](/docs/self-hosting/updating) |
| Standard user | A person the accounts record does not mark an administrator. privd's `user` principal matches them; `admin` does not | A standard account | [Users and file permissions](/docs/architecture/users) |
| Test boot | A boot with `tests=on`: the kernel runs its tests, then a copy of init runs the userland tests. It runs no Wheel of Fate and starts no session unless a test asks for one or a test fails |  | [Init and services](/docs/architecture/init#test-boots) |
| Tree | A set of files installed under `/usr/local` or `~/.local` together with a manifest, such as the toolchain or the apps | A package | [Installed software](/docs/architecture/software) |
| Universal capability | `ConsoleIo`, `ClipboardGlobal` and `Fate`, which every program holds unless it or its spawner dropped them, and keeps across `exec` | | [Capabilities](/docs/architecture/authority) |
| User | Any account in the uid sense: a person, uid 0, one of the base's own users such as `greeter` (uids 1 to 99), one of an extension's own users (uids 100 to 999), or `nobody` (65534) | A Unix user | [Users and file permissions](/docs/architecture/users) |
| Version floor | The lowest version of an extension its record lets in: the highest version installed, lowered by a rollback to the version it made current. The floor's own version with other bytes is refused too | | [Extensions](/docs/architecture/extensions) |
| Wheel of Fate | The roulette spin at every interactive boot: the kernel draws an odd or an even fate, `/bin/roulette` shows it, and an even one restarts the machine. `roulette=skip` leaves it out, and a test boot does not run it |  | [Boot](/docs/architecture/boot#the-wheel-of-fate) |
