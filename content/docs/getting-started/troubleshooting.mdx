---
title: "Troubleshooting"
description: "What to do when setup, the build, a boot or the tests go wrong."
---

Each section below starts from what you see, says why it happens, and gives
the fix. Most problems on a first run are a missing host tool or a download
that could not complete.

## `just setup` stops before finishing

| Message | Cause | Fix |
|---------|-------|-----|
| `rustup is required to install the pinned nightly toolchain` | rustup is not on `PATH` | Install rustup, then rerun `just setup` |
| ``ensure_go: `go` not found in PATH`` or `ensure_go: found go X; need >= 1.22` | `just setup` checks Go but does not install it | Install Go 1.22 or later, then rerun `just setup` |
| ``ensure_go: `go mod download` failed in tools/run_tests`` | The Go modules of the test runner could not be downloaded | Check network access, or fill the Go module cache from another machine |
| `toolchain <channel> has no rust-src component` | The pinned nightly lacks its standard library sources | `rustup component add rust-src --toolchain <channel>`, then rerun `just setup` |
| `cp -al failed` | The `slopos` toolchain is a hard-link copy of the pinned nightly, and the checkout is on another filesystem than `$RUSTUP_HOME` | Put the checkout on the same filesystem as `~/.rustup`, or point `RUSTUP_HOME` at one that is |

## Downloads fail or you are offline

The build downloads a few pinned inputs on first use and checks each against
a pinned SHA-256 sum. Each has an override, so you can point it at a mirror
or a local copy:

| Input | Cached at | Override |
|-------|-----------|----------|
| Limine boot loader | `third_party/limine/` | Unpack the pinned release there, or set `LIMINE_URL`. `LIMINE_VERSION` and `LIMINE_TARBALL_SHA256` (empty skips the check) change the pin |
| OVMF firmware for the live ISO | `third_party/ovmf/` | `OVMF_BASE_URL`, a mirror of the pinned edk2 nightly |
| OVMF firmware for boot disks | `third_party/ovmf-nv/` | `OVMF_NV_PKG_URL`, a copy of the pinned `edk2-ovmf` package |
| `libc` crate for the `slopos` toolchain | `$CARGO_HOME/registry/cache` | Fill the cargo cache, or set `LIBC_URL` |
| `llvm-project` sources, for the C++ runtime that building any base needs | `third_party/llvm-project-<version>.src.tar.xz` | Place the pinned tarball there, or set `LLVM_URL` |
| Source tarballs of the programs ported to SlopOS (e2fsprogs for every base; the rest for `just recipes`) | `third_party/recipes/<name>-<version>.<ext>` | Place the pinned tarball there, or set `<NAME>_URL`, such as `E2FSPROGS_URL` |

A different Limine release in `third_party/limine` is replaced with the
pinned one, but a different release in a directory `LIMINE_DIR` names stops
the build, and so does any Limine directory that is only partly filled:
remove it or complete it.

## The build says a host tool is missing

| Message | Install |
|---------|---------|
| `build_recipes: make is required to build e2fsprogs` or `build_recipes: pkg-config is required to build e2fsprogs` | `make` and `pkg-config` (`pkgconf` on Arch) |
| `build_bootdisk: missing host tools:` followed by any of `sfdisk mkfs.fat mmd mcopy truncate dd` | util-linux or fdisk (`sfdisk`), dosfstools (`mkfs.fat`), mtools (`mmd`, `mcopy`), coreutils (`truncate`, `dd`) |
| `make_slopos_cxx: cmake is required to build the C++ runtime`, or the same for `ninja` | CMake and Ninja (`ninja-build` on Debian) |
| `mke2fs is required` or `debugfs is required` | e2fsprogs |
| `resize2fs is not installed, so the image cannot be grown` | e2fsprogs |
| `gen_verity: python3 is required` | Python 3 |
| `qemu_run.sh: GIT_SSH_PEER needs sshd on PATH or at /usr/sbin/sshd` | OpenSSH's server; only `just test-toolchain` asks for it, once a toolchain is built |

The boot-disk tools are needed by `just boot` and the checks that build a boot
disk; the live ISO does not need them.

## The build cannot find LLVM

Every base carries programs cross-compiled for SlopOS with your clang, and
the cross compiler that builds them needs SlopOS's C++ runtime, which is
built from pinned LLVM sources. Building them needs `clang`, `clang++`,
`ld.lld` and `llvm-ar` that all report the same LLVM version, 18 or later,
plus `cmake` and `ninja`. So `just boot-live` and
`just boot` need them as much as `just test` does. The build looks for version
18 first (`clang-18`, `/usr/lib/llvm-18/bin`, `/usr/lib64/llvm18/bin`), then
the unversioned tools, then any newer installed version.

| Message | Fix |
|---------|-----|
| `no LLVM >= 18 toolchain found` | Install clang, lld, llvm, cmake and ninja from your distribution |
| `the named toolchain is not one usable LLVM >= 18` | The tools named by `CLANG`, `CLANGXX`, `LD_LLD` or `LLVM_AR` are missing or report different versions; correct those variables |
| `note: LLVM N is outside toolchain/cxx/PIN's tested majors` | Only a note: the build continues, and the C++ tests in `just test` show whether that version works |

Set `CLANG`, `CLANGXX`, `LD_LLD` and `LLVM_AR` to choose the tools yourself,
for example a distribution's `-18` binaries. Upgrading the host compiler
rebuilds the runtime on the next run.

## Your persistent root is missing after an update

The development machine's disk used to be `fs/assets/ext2-persist.img`. Since
2026-10-28 it is `fs/assets/ext4-persist.img`, and a `just boot` that finds no
file of that name builds a fresh one. If you have the old file, rename it and
its two side files before you boot:

```bash
for f in fs/assets/ext2-persist.img fs/assets/ext2-persist.img.stamp fs/assets/ext2-persist.img.host; do
  [ -e "$f" ] && mv "$f" "${f/ext2-persist/ext4-persist}"
done
```

If a `just boot` already built a fresh `ext4-persist.img`, move that one aside
first. The next `just boot` then updates the old disk as usual, or stops with
one of the messages in the next section.

## The build refuses to touch the persistent root

`just boot` stops with a message that starts `preserve:`:

```text
preserve: the image is damaged, or a boot left it dirty (see above)
  fs/assets/ext4-persist.img holds whatever the guest wrote, so this build stops here.
  Fix it:     e2fsck -fy 'fs/assets/ext4-persist.img'
  Discard it: rm -f 'fs/assets/ext4-persist.img' 'fs/assets/ext4-persist.img.stamp'
```

The development machine's disk holds whatever you did inside it, so the build
never deletes it. Before each boot it updates the programs on that disk, and
it stops when it cannot do that safely: the image is damaged or was not shut
down cleanly, it cannot be grown, it falls short of the ext4 features every
SlopOS volume has, or it carries a kind of integrity trailer the build would
not keep.

To keep your work, run the `Fix it:` command when there is one. `e2fsck -fy`
repairs the filesystem, and may throw away what it cannot repair. When the
message names `just reset root` instead, or the repair did not help, start
over:

```bash
just reset root
just boot
```

The next boot builds a fresh disk with a new clone of `HEAD` at
`/src/slopos`. Commits the guest already pushed are kept in
`fs/assets/guest-push.git`.

A disk that QEMU closed in the middle of a write is not refused. `just boot`
prints `was closed mid-write; booting it unrefreshed so its journal replays`
and boots it as it is, so the kernel can finish the interrupted writes. The
next `just boot` after a clean shutdown updates it as usual. [Crash
recovery](/docs/architecture/crash-recovery) explains the journal.

## Files you write in the guest disappear after a reboot

The root filesystem came up read-only. When the kernel finds a journal on the
disk that it cannot replay safely, it mounts the disk read-only and leaves the
repair to `e2fsck`. A read-only disk cannot be the root, so the system runs
with its root in memory instead, as the live ISO does, and mounts the real
disk at `/mnt`.
Everything looks normal, but nothing written to `/` is kept.

Shut the guest down, then check and repair the disk on the host:

```bash
just check-fs-image fs/assets/ext4-persist.img
e2fsck -fy fs/assets/ext4-persist.img
```

If the repair loses what you needed, `just reset root` gives you a fresh disk.

A write under `/bin`, `/sbin`, `/lib`, `/usr/bin`, `/usr/share` or `/etc/ssl`
fails on every boot, which is a different thing: those directories belong to
the read-only base. Software you add goes under `/usr/local` or `~/.local`
([Installed software](/docs/architecture/software)).

## A command says it needs your password

```text
This needs your password, and you haven't set one.
```

Commands that install or change the system (`bootctl install`,
`scripts/selfhost.sh install`, `users add` and others) ask the person at the
machine first. At the
desktop that is a dialog, which the first person, who has no password, answers
with a click. At a text console, such as the serial console `VIDEO=0` gives
you, the only answer is a password, so a person without one is refused. Run
the command from the terminal on the desktop instead, or set a password there
with `users passwd` and then use it at the console. [Privileged
actions](/docs/architecture/privd) explains who is asked and how.

## Boot keeps restarting at the Wheel of Fate

This is the Wheel of Fate doing its job: an even number restarts the machine
and the wheel spins again. Skip it:

```bash
ROULETTE=0 just boot-live
just boot-fast
```

Test boots never spin it.

## A long check stops before it boots

| Message | Fix |
|---------|-----|
| `FAIL: no toolchain at builddir/slopos-toolchain/install — run just toolchain` | `just test-selfhost`, `test-install-guest`, `bench-selfhost` and `test-installer` need the cross-built toolchain: run `just toolchain`, or for `test-installer` set `INSTALLER_PAYLOAD=0` |
| A `FAIL:` line ending `commit or stash first` | `just test-selfhost` and `test-install-guest` build `HEAD` in the guest, so the working tree must have no uncommitted changes |

## QEMU stops with "the git peer cannot serve the path"

`just boot` serves your checkout to the guest with `git daemon`, which QEMU
starts from a command line that it splits on commas and spaces. So the wrapper
refuses a checkout path, or a `GIT_PUSH_REPO` path, that contains a comma,
`%`, a quote, a backslash or whitespace. Move the checkout to a plain path.
The wrapper also needs `git` on `PATH`.

## QEMU stops with "echo peer command '/bin/cat' is not executable"

The network tests talk to an echo service that QEMU runs with `/bin/cat`. On a
host without `/bin/cat`, point `ECHO_PEER_CMD` at `cat`:

```bash
ECHO_PEER_CMD="$(command -v cat)" just boot
```

## The boot prints "No hardware acceleration"

QEMU could not use a hypervisor: on Linux `/dev/kvm` is missing or you cannot
read and write it, or on macOS QEMU has no HVF. The system still runs, more
slowly, by emulating the CPU. On Linux, add yourself to the group that owns
`/dev/kvm` (usually `kvm`) and log in again.

Recording a run for replay (`just rr-record`) always emulates, on one CPU.

## No QEMU window opens, or the display is wrong

See which display backends your QEMU has, then pick one:

```bash
qemu-system-x86_64 -display help
QEMU_DISPLAY=sdl just boot-fast
QEMU_DISPLAY=gtk just boot-fast
```

`VIDEO=0` avoids the window entirely and puts the console in your terminal,
where you log in as `user` with an empty password.

If the wrapper warns that it `can't instantiate 'virtio-vga'`, your QEMU lacks
its virtio-gpu display modules, and SlopOS falls back to a plain framebuffer.
On Arch and CachyOS install `qemu-hw-display-virtio-gpu` and
`qemu-hw-display-virtio-gpu-pci`.

## The boot hangs or the screen stays blank

During the boot the screen shows only the logo and the ring. Press Esc to see
the kernel's log in its place (`== SlopOS kernel log == (ESC toggles)`), and
Esc again to go back. Or boot the live ISO without a window and read what the
kernel printed:

```bash
just boot-log
tail -n 120 test_output.log
```

For more detail, skip the wheel and turn on debug logging:

```bash
ROULETTE=0 DEBUG=1 just boot
ROULETTE=0 DEBUG=1 just boot-log
```

If a running system stops responding, press SysRq (Alt+PrintScreen) in the
QEMU window, or send a serial BREAK, then a command key: `h` lists the
commands and `t` prints every task. If even that gets no answer, boot with
`just boot-debug` and run `just debug-bt` in another terminal; it writes every
CPU's backtrace to `builddir/freeze-gdb.log`. [Diagnosing the
kernel](/docs/development/diagnostics) covers both, and what a panic leaves
behind on a boot disk.

## Tests fail

Start with the runner's own options; filters are positional:

```bash
just test-rerun-failed
just test-verbose 'slopos_mm::*'
just test-raw
```

A filtered run whose tests create files must include `'*ext4_aaa*'`, because
that test mounts the test disk for the tests after it.

If a failure looks like memory corruption and still happens on one emulated
CPU, record the run and replay it under GDB:

```bash
just rr-record
just rr-replay
```

GDB then waits at the start of the recording. Set the breakpoints and the
watchpoint by hand, as [Go backwards from a
crash](/docs/development/debugging-gdb-record-replay#go-backwards-from-a-crash)
shows, and run backwards to the instruction that wrote the bad value.
`just rr-gdb <address>` is meant to do this unattended but does not work at
this commit: it never stops at the fault.

[Building and testing](/docs/getting-started/build-test-recipes#run-the-tests)
explains the runner's output.
