This page shows you how to build SlopOS, where the results go, and how to run
the test suite and read what it tells you. It ends with every recipe the
repository has. It assumes you have run `just setup` from the
[Quickstart](/docs/getting-started/quickstart).

## How the build fits together

Every command goes through `just`, a command runner. The file `justfile` at the
root of the repository defines named *recipes*, and `just <recipe>` runs one.
`just --list` prints them all with a line on each.

A bootable SlopOS is made of these parts:

1. **The kernel**, one ELF file.
2. **The base**: the system's own programs (the shell, init, the desktop, the
   coreutils, the installer, the e2fsprogs tools and the rest), packed into a
   read-only archive the boot loader loads beside the kernel. Every kernel
   boots a base; [Base system](/docs/architecture/base) explains why the two
   are separate.
3. **The apps**: the editor, file manager, image viewer and widget gallery,
   which live outside the base and are installed under `/usr/local` on every
   root ([Installed software](/docs/architecture/software)).
4. **A root disk image**, when the system keeps files: a file holding an ext4
   filesystem, the same format Linux uses, which QEMU presents to the virtual
   machine as a disk.

The boot recipes then wrap these into something firmware can start: a CD
image (ISO) for the live system, or a boot disk for the development machine.
You rarely run the steps by hand, because each boot and test recipe builds
what it needs first.

| Command | What it produces |
|---------|------------------|
| `just build` | The programs and apps, the verified image `fs/assets/ext4.img`, and the kernel `builddir/kernel-dev.elf` |
| `just iso` | The live ISO `builddir/slop.iso`: the kernel, the base `builddir/initramfs.cpio` and the install medium `builddir/install.cpio` |
| `just boot-live` | Builds the ISO, then boots it |
| `just boot` | The optimised kernel `builddir/kernel-release.elf`, the base, the boot disk `builddir/boot-disk.img` and the persistent root `fs/assets/ext4-persist.img`, then boots them |
| `just test` | The tests kernel `builddir/kernel-tests.elf`, the tests base `builddir/initramfs-tests.cpio`, `builddir/slop-tests.iso` and the test root `fs/assets/ext4-tests.img`, then runs them |

Compiler output goes under `builddir/target`. Downloaded inputs are cached
under `third_party/`: the Limine boot loader, the OVMF firmware, the LLVM
sources the C++ runtime is built from, and the source tarballs of the C
programs and libraries built for SlopOS (`third_party/recipes/`).

Building any base needs the host's LLVM toolchain, because every base carries
the e2fsprogs tools, cross-compiled with clang, and the cross compiler that
builds them needs the C++ runtime, which the build makes first with clang,
CMake and Ninja. Every kernel build ends by running checks on the finished ELF
(for example, that no function's stack frame is too large), so a build can
still fail after the compiler has succeeded. [Safety
gates](/docs/verification/tcb-discipline) lists them.

### Optimised and debug kernels

The *dev* kernel is built quickly, with symbols, and is what `just build`,
`just boot-live` and the debugger recipes use. The *release* kernel is
optimised, and `just boot` uses it because the development machine runs a
compiler. `KERNEL_RELEASE=1` selects the release kernel for most recipes, and
`KERNEL_RELEASE=0 just boot` boots the dev kernel instead; [QEMU
options](/docs/getting-started/qemu-options#recipe-variables) names the
checks that choose their own. The test suite
uses a *tests* kernel, which has the test harness compiled in and comes in
the same two builds (`kernel-tests.elf` and `kernel-release-tests.elf`).
`PAYLOAD=1 just iso` builds the release kernel instead, since a system
installed from that medium builds itself.

### Passing options to a recipe

Settings such as `ROULETTE=0` (skip the Wheel of Fate), `DEBUG=1` (more kernel
logging) and `VIDEO=0` (no window) are environment variables, so they go
before `just`:

```bash
ROULETTE=0 DEBUG=1 just boot
```

A recipe's own arguments go after its name and are positional. Write
`just test 'slopos_mm::*'`, not `just test FILTER='slopos_mm::*'`: the second
form passes the text `FILTER=slopos_mm::*` as the filter, which matches
nothing. One setting, `ports`, is a justfile variable and goes between `just`
and the recipe:

```bash
just ports=7777,8080 boot
```

[QEMU options](/docs/getting-started/qemu-options) lists every environment
variable the boot recipes read.

## Run the tests

### 1. Run the whole suite

```bash
just test
```

This builds a kernel with the test harness compiled in, boots it in QEMU with
no window, and runs every kernel test and then every userland test, leaving
out only the few a host script has to drive. A progress bar shows how far it
is. When QEMU exits, the runner prints a summary and exits 0 if every test
passed and 1 if any failed. It exits 2 when the run proves nothing: QEMU
never reached the test harness, or the harness planned no tests although
nothing filtered them. It exits 64 when it could not start a run at all, for
example because the build failed. Each run starts from a freshly built test
disk, so no run depends on what the last one wrote.

### 2. Read a failure

For each failing test the runner prints its name (`<module>::<test>`) and the
kernel log lines the test produced while it ran, which is usually where the
reason is. Passing tests' logs are hidden; `just test-verbose` shows them too.

After every run you did not interrupt, the names of the failed tests are in
`builddir/last-fail.list`, and this reruns only those:

```bash
just test-rerun-failed
```

If the summary looks wrong, `just test-raw` prints exactly what came out of
the virtual machine's serial port: the test results in KTAP, the plain-text
format Linux's kernel tests use, mixed with the kernel log. [Test output
format](/docs/abi/ktap-test-output) describes it.

### 3. Run some of the tests

Pass a glob, a pattern where `*` matches anything, as the first argument. It
is matched against each test's `<module>::<test>` name. Separate several
globs with commas:

```bash
just test 'slopos_mm::*'
just test '*ext4_aaa*,slopos_fs::*'
```

A filtered run whose kernel tests create files must include `'*ext4_aaa*'`.
The kernel tests run before the boot mounts the root disk, so they write to a
filesystem in memory, and that test, which sorts ahead of the filesystem
tests, is the one that sets it up. Userland tests run on the root disk and
don't need it.

`just test-verbose` and `just test-quiet` take the same glob.

### Tests that run on your machine

```bash
just test-host
```

This runs the unit tests of the parts of SlopOS that are plain logic (the
filesystem, network, TLS, USB and HID cores, the installer's and privd's
logic, the boot disk layout, the theme, the shell and others) as ordinary
programs on your machine, with no QEMU. It is the fastest way to check a
change to one of those parts. The TLS tests talk to `openssl` and
`ssh-keygen`, so both must be on `PATH`. [Write
tests](/docs/development/adding-tests) explains where a new test belongs.

### The longer checks

`just test` is one boot. The checks below each boot a machine of their own,
because what they test spans reboots, needs devices plugged in and pulled out,
or takes hours. CI runs `test-persist`, `test-rude-exit`, `test-usb` and
`test-toolchain` (which, with no toolchain built, checks only the clone on the
self-hosting root) after every test run; the others are run by hand.

| Check | What it needs beyond `just test` |
|-------|----------------------------------|
| `just test-persist`, `test-rude-exit`, `test-usb` | Nothing |
| `just test-install`, `test-remote` | The boot-disk tools: dosfstools, mtools, `sfdisk` and zstd; `test-remote` also `openssl`, to make the broker's keys |
| `just test-installer` | The boot-disk tools, and `just toolchain` first, or `INSTALLER_PAYLOAD=0` to install without the toolchain |
| `just test-toolchain` | `git`, `openssl` and `ssh-keygen` to stage its fixtures; with a toolchain built, also `sshd` (on `PATH` or at `/usr/sbin/sshd`) and internet access for the rungs that reach GitHub and crates.io |
| `just test-selfhost`, `test-install-guest`, `bench-selfhost` | `just toolchain` first, and what `test-toolchain` needs to stage its fixtures; `test-install-guest` also the boot-disk tools. The first two refuse a working tree with uncommitted changes, because the guest builds `HEAD` |

Each says what it is waiting for and where its log is. [Write
tests](/docs/development/adding-tests) describes what each one grades.

## What usually goes wrong

- The first boot or test run stops with a message about LLVM: the base
  carries programs built with LLVM 18 or later, and your machine has none it
  can use. See
  [Troubleshooting](/docs/getting-started/troubleshooting#the-build-cannot-find-llvm).
- A filtered run fails on file operations: add `'*ext4_aaa*'` to the filter.
- A framekernel gate complains that the kernel ELF or `builddir/libc.so` is
  missing: run `just build` first.

## All recipes

The `justfile` is the authoritative list; `just --list` prints it with each
recipe's own description.

### Setup and build

| Recipe | What it does |
|--------|--------------|
| `just setup` | Install the pinned Rust nightly, build the `slopos` toolchain, check Go 1.22 or later, fetch the Go modules, validate the workspace |
| `just build` | Build the programs and apps, `fs/assets/ext4.img` and `builddir/kernel-dev.elf` |
| `just build-kernel-only` | Build the kernel ELF without the programs or the image |
| `just iso` | Build `builddir/slop.iso` with `BOOT_CMDLINE` as its kernel command line. `PAYLOAD=1` adds the toolchain and a clone of `HEAD` in a partition the installer copies from; `REMOTE=1` packs a base paired with this host's remote-control broker |
| `just extension <dir>` | Pack the extension laid out in `<dir>` into `builddir/extensions/<name>.ext` and its sidecar, signed when `EXTENSION_KEY` names a key ([Package an extension](/docs/development/packaging-an-extension)) |
| `just icons` | Render the shipped app icons at 64 and 128 pixels |
| `just clean` | Remove compiler output under `builddir/target`, the `builddir/kernel-*.elf` files and the gates' probe builds under `builddir/gates` |
| `just distclean` | `clean`, then remove `builddir/`, `test_output.log`, `fs/assets/ext4.img`, `fs/assets/ext4-tests.img` and the extracted llvm-project, rustc and vendored-crate trees under `third_party/`. Leaves the persistent root, the self-hosting and capacity images and `fs/assets/guest-push.git` alone |

### Boot

| Recipe | What it does |
|--------|--------------|
| `just boot` | The development machine: release kernel and base on an A/B boot disk, persistent root, 6 GiB of memory, Wheel of Fate first |
| `just boot-fast` | `just boot` with `ROULETTE=0` |
| `just boot-debug` | `just boot-fast` on the dev kernel with QEMU's GDB stub on port 1234 and a monitor socket |
| `just boot-live` | The live ISO from memory, no disk; Wheel of Fate unless `ROULETTE=0` |
| `just boot-log` | The live ISO with no window for `BOOT_LOG_TIMEOUT` seconds (default 15), log in `test_output.log`; fails unless `/sbin/init` started |
| `just ui-shots [scene...]` | Boot the live ISO and save a PNG of every installer page, the desktop's surfaces and each app under `builddir/ui-shots/`; names scenes to take only those, `--no-install` stops the installer at its review page |
| `just show-qemu-resolution` | Print the screen size the QEMU wrapper would detect |

`boot-fast` and `boot-debug` start `just boot` again inside themselves, and a
`ports=` setting does not reach that inner run. To forward ports without the
wheel, use `ROULETTE=0 just ports=7777 boot`.

### Persistent root

| Recipe | What it does |
|--------|--------------|
| `just reset root` | Delete `fs/assets/ext4-persist.img` and its side files (`.stamp`, `.host`), so the next `just boot` builds a fresh root with a new clone of `HEAD`. What the guest wrote and did not push is lost; `fs/assets/guest-push.git` is kept |
| `just export-file PATH=<guest path> OUT=<host path> [IMAGE=<image>]` | Copy one file off the persistent root (or another image) after the guest has shut down |

`just boot` rebuilds `builddir/boot-disk.img` on every run, so a kernel or
base the guest installed survives guest reboots but not the next `just boot`.
[Updating SlopOS](/docs/self-hosting/updating) covers boot slots and bases.

### Tests

| Recipe | What it does |
|--------|--------------|
| `just test ['glob']` | Build and run the QEMU test suite, or the tests matching the glob |
| `just test-rerun-failed` | Rerun the tests listed in `builddir/last-fail.list` |
| `just test-verbose ['glob']` | Also print the kernel log of every passing test |
| `just test-quiet ['glob']` | Print only failures and the summary |
| `just test-raw` | Pass QEMU's output through unchanged, KTAP and kernel log mixed |
| `just test-json <path>` | Also write one JSON event per line to `<path>`, replacing what it held |
| `just test-userland-only` | Runs no tests at this commit. It boots the tests ISO with `tests.run=__userland_only__`, a pattern that names no test, and the harness applies `tests.run` to the userland phase as well as the kernel phase, so both plan nothing and the runner exits 2. To run every userland test program and no kernel test, filter by module: `just test 'slopos_core::utests::*'` |
| `just test-elf [ELF=]<kernel> [BASE=<base.cpio>] ['glob']` | Run the suite on a tests kernel and base built elsewhere, such as inside the guest |
| `just test-host` | Unit tests of the pure-logic crates and of `slopos-ostd`, on the host, no QEMU |
| `just check-tests-host` | Unit tests of the Go test runner |
| `just check-test-count` | Fail if `just test` plans fewer tests than `TEST_COUNT_BASELINE` |
| `just test-persist` | Two boots of one image: write and `fsync`, power off, boot again and read it back |
| `just test-rude-exit` | A boot commits a file to the root's journal and dies holding it; the host's `e2fsck` must replay it |
| `just test-usb` | Boot with both of QEMU's USB controllers, plug and pull sticks, keyboards, pointers, a hub and a USB network adapter through QEMU's control socket, and check that every device comes and goes cleanly |
| `just test-capacity` | Mount and write a 16 GiB volume (built once, then kept), and grade the cost |
| `just test-install` | On one disk laid out as on a real machine: register SlopOS's firmware boot entry, install a kernel into a boot slot, try it, commit it, roll back slots that panic, install and roll back bases, and check the EFI system partition was left unchanged |
| `just test-installer [disk...]` | Install from the ISO on an emulated USB stick onto a blank disk, beside another system and over an existing partition, and from a CD onto a blank disk; boot each, build the system there (the CD's install, which has no toolchain, clones a slot instead) and commit it; check and roll back the blank disk from the rescue shell, and reinstall it keeping its root. Names a subset: `blank`, `foreign`, `reuse`, `optical` |
| `just test-install-guest` | The guest builds a kernel and base from `HEAD`, installs them, boots them, pushes a commit back, commits the slot and rolls back a slot that panics |
| `just test-remote` | Boot an installed machine paired with a broker on this host and drive it through `scripts/remote.py`: commands, files, the kernel log, a base and a kernel installed, power-off |
| `just test-toolchain` | Run the toolchain checks on the self-hosting root, over two boots; with no toolchain built, one boot that checks only the clone |
| `just test-selfhost` | The guest builds the dev and tests systems; the host checks the result and runs the suite on the guest's kernel and base |
| `just bench-selfhost` | Profile the guest's build of `HEAD` and summarise where the time went (log in `builddir/bench-selfhost.log`) |

### Filesystem and boot-log checks

| Recipe | What it does |
|--------|--------------|
| `just check-fs-image [--map] [image]` | Hold an image, by default the test image, to `e2fsck -fn` and to being at rest (clean, nothing to replay); with `--map`, or when it names no image, also to the ownership map |
| `just check-fs-throughput` | Fail if a write costs more transactions or device requests per MiB than recorded |
| `just check-quota-headroom` | Fail if a resource account's peak passes its recorded cap, anything was refused, or charging got slower |
| `just check-lockdep-headroom` | Fail unless the lock-order checker booted active, reported no violation and stayed within the limits recorded for its pools |
| `just check-sched-spread` | Fail unless every online CPU can be given tasks |

Each of these but `check-fs-image`, like `check-test-count` above, boots the
test suite once and grades what it printed. The scripts behind them
(`scripts/check_*.sh`) take `--log <file>` to grade a saved capture of
`builddir/run_tests --raw --no-color` instead, which is how CI grades one run
with several of them.

### Remote control

| Recipe | What it does |
|--------|--------------|
| `just remote <command>` | Drive the paired SlopOS machine: `status`, `wait`, `run -- <argv>`, `sh <command line>`, `push`, `pull`, `klog`, `install` |
| `just remote-serve` | Run the broker the machine dials, offering the release kernel and a paired base to bootstrap it; `REMOTE_HOST` and `REMOTE_PORT` (default 7330) say where |
| `just remote-install [--commit]` | Build a paired base under a fresh build tag and install it on the machine; when the kernel changed, install it into the spare slot and boot it once |

[Remote control](/docs/self-hosting/remote-control) explains pairing and what
the machine lets the broker do.

### Debugging

| Recipe | What it does |
|--------|--------------|
| `just debug-gdb` | Interactive GDB attached to a kernel started by `just boot-debug` |
| `just debug-bt` | Backtraces of every CPU into `builddir/freeze-gdb.log` |
| `just debug-monitor` | Connect to the QEMU monitor socket |
| `just rr-record` | Record a deterministic test run to `builddir/replay.bin` (one CPU, no KVM) |
| `just rr-replay` | Replay the recording under interactive GDB. Its script's breakpoints on a program's fault and on a kernel exception are not set (GDB wants the functions' full Rust paths), so set them yourself |
| `just rr-gdb [<address>]` | Meant to replay to the fault unattended and, given an address, run backwards to the instruction that wrote it. At this commit it does neither: it never stops at the fault, and its script reads the fault's registers in C syntax GDB refuses in Rust code, and the watchpoint it would set (`wpva`'s) watches the wrong address. Do the same steps by hand under `just rr-replay` |

[Debugging with GDB](/docs/development/debugging-gdb-record-replay) shows
how to use them, and [Go backwards from a
crash](/docs/development/debugging-gdb-record-replay#go-backwards-from-a-crash)
gives the replay steps by hand.
