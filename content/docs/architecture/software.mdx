Everything SlopOS needs to boot, log you in and repair itself is in the
[base](/docs/architecture/base), a read-only image that is replaced as a
unit. Everything else comes in one of two forms. Software for everyone on
the machine, the toolchain, the editor and the other apps among it, is a
*package*: one sealed image that `pkgctl` installs and shows at
`/opt/<name>` (see [Packages](/docs/architecture/packages)). A program
you build for yourself is a file you copy into `~/.local` in your home, where
only you will run it. None of it needs a reboot.

Two promises follow from where software lives. A command a package provides,
or one in your `~/.local/bin`, can never take the place of a system tool you
run by name, because the system's directories are searched first. And a
library you put in `~/.local/lib` is never loaded into a program that holds
more power than you, because the loader does not look there for such a
program. What SlopOS does not offer is a shared directory everyone may
install into: there is no `/usr/local`.

The page walks through why software leaves the base, the apps SlopOS ships
as a package, and how programs and libraries are found.

## Where it comes from

The split between the system's own programs and everything else is
FreeBSD's, which keeps its base apart from what its packages install. Shipping
the software everyone shares as read-only images rather than files unpacked
into a shared tree is the model of systemd's system extensions and of
Android's APEX modules. `~/.local`, with programs in `~/.local/bin`, is the
per-user directory the XDG Base Directory specification and the UAPI group's
file hierarchy name. The loader's rule is glibc's secure-execution mode
carried one step further: glibc's loader ignores `LD_LIBRARY_PATH` for a
program the kernel marks `AT_SECURE`, and SlopOS's also skips your home.

## Why the base is not enough

The base is sealed: no program can change a file in it, and it is replaced
whole (see [Updating SlopOS](/docs/self-hosting/updating)). That is right for
init, privd and the compositor, which the security model rests on, and wrong
for an editor, which should be able to change on its own schedule. So
programs that need nothing from the system but the C library leave the base.

Leaving it raises two problems. First, a program built outside the base must
keep working when the base changes underneath it. SlopOS answers that with
one contract: such a program reaches the system only through `libc.so`,
whose exported functions and structure layouts are only ever added to (see
[Userland](/docs/architecture/userland#programs-outside-the-base)).

Second, a place everyone runs programs from must be one nobody but the
system can write. A shared directory the first person may write is a place
where they can replace a command the second runs, and a group allowed to
write it is no better, since everyone in the group can plant code for
everyone else. So software for everyone goes in as a package: `pkgctl`
checks it against its signature and what it declares, an administrator
approves it, and the kernel serves it read-only. A person's own builds stay
in their own home.

## The apps outside the base

The editor, the file manager, the image viewer, the widget gallery and
Breach are the crate `slopos-apps` (`apps/`). They are built the way a
person's own `cargo build` builds a program for SlopOS: against the target's
standard library, linked dynamically against `libc.so`. With their app
entries, icons and the editor's manual they ship as the image
`slopos-essentials`, which declares five commands and four apps (the widget
gallery has no dock entry), and appear at `/opt/slopos-essentials`.

The build stages the image's files in `builddir/apps`, with its
`.package/release` and `.package/declare`, and packs them through
`scripts/build_package.sh` into `builddir/slopos-essentials/`. The image's
version is a UTC time stamp that moves only when the staged files do
(`builddir/slopos-essentials.version`), so a root that already holds this
build passes a repeat over.

Every root is offered the image, the way it is offered the toolchain's:

| Way | Who installs | When |
|---|---|---|
| The host's image builders | `scripts/build_fs_image.sh` puts the image among the root's offered images | Every `just boot` and test image |
| The installer | `/bin/installer` offers the new root the medium's `images/` | Installing SlopOS onto a disk |
| Init on a live boot | init offers the medium's `images/` | Booting the install medium |
| `just install` | `pkgctl install`, which an administrator approves | Building the system on SlopOS |

An offered image goes in at boot without asking anyone, since only uid 0
can offer one ([Packages](/docs/architecture/packages#installing-a-package)
has the rules). `just install` installs the new image only when the running
`libc.so` is the one it was just built against. Otherwise it prints the
command to run once the new base is running, since a freshly built app may
call a function the running library does not export yet.

Two checks keep the apps honest. `xtask programs`, which
`build_package.sh` runs as it packs the image, fails an app that is
statically linked, names a loader other than `/lib/ld-slopos.so.1`, does not
list `libc.so` among the libraries it needs, or contains a `syscall`
instruction of its own, since a system call made in place would bypass the
one contract the base keeps. And `xtask lint app-deps` fails a crate under
`apps/` that depends on anything but the toolkit (`slopos-appkit`), the
editor's core and the image decoder, so no app reaches past the toolkit into
the kernel's interface. The toolkit itself reaches the system only through
`slopos-cabi`, a thin layer over functions `libc.so` exports.

### App entries

The dock (see [Desktop](/docs/architecture/desktop)) shows an app because a
file says it exists: `share/slopos/apps/<id>.app`, a few `key=value` lines.

```text
id=org.slopos.editor
name=Editor
exec=/opt/slopos-essentials/bin/editor
icon=org.slopos.editor.png
```

`id` must match the file name, `exec` is an absolute path, and `icon` names a
PNG in the same share's `slopos/icons/`, beside which a copy at twice the
size, `<icon>@2x.png`, waits for displays that need one. `boot=medium` marks
an app shown only when the system booted from the install medium. The dock
reads the entries at the start of a session from each package's share (only
the apps the package declares), then `/usr/share` (the base) and
`~/.local/share`, in that order, and an entry with the same id as an earlier
one replaces it, as XDG data directories rank. So a package's entry yields to
the base's and to yours, and you can override any app's entry with your own
in `~/.local/share/slopos/apps`. The shell keeps no list of apps; `PATH`
finds them.

The editor looks for its manual the same way, in `~/.local/share`, then
`/opt/slopos-essentials/share`, then `/usr/share`.

## How programs and libraries are found

The command search path puts the system first. A program started with no
`PATH` gets `/bin:/sbin:/opt/bin` (`slopos_abi::fs::DEFAULT_PATH`), the
same list `execvp` uses and the tools that search `PATH` share. A person's
session puts their own directory between the system's and the packages':

```text
PATH=/bin:/sbin:/home/user/.local/bin:/opt/bin
```

So nothing on a writable disk shadows a base tool, your own programs come
before the commands packages provide (`/opt/bin`, see
[Packages](/docs/architecture/packages#commands-apps-and-settings)), and
those come last.

The shell reads a command's completion rules, when `SHELL_COMPLETION_PATH`
names no directory, from the `share/shell/completions` of the package whose
command `/opt/bin/<command>` links to, then from the base's
`/usr/share/shell/completions`.

The loader (see [Userland](/docs/architecture/userland#the-loader)) looks for
a library by name in this order:

1. `LD_LIBRARY_PATH`, except under `AT_SECURE`;
2. the requesting object's `RUNPATH`, or else the `RPATH`s of the chain that
   loaded it (under `AT_SECURE`, only their absolute entries that don't use
   `$ORIGIN`);
3. `/lib`, then `/usr/lib`;
4. for a program of a package, that package's own `/opt/<name>/lib`;
5. `$HOME/.local/lib`, only for a process that is neither `AT_SECURE` nor
   running as uid 0.

One step differs from glibc: glibc tries an object's `RPATH` before
`LD_LIBRARY_PATH` (and its `RUNPATH` after, as here), while SlopOS's loader
always tries `LD_LIBRARY_PATH` first.

`AT_SECURE` is a flag the kernel sets for a program that starts holding any
gated [capability](/docs/architecture/authority), or running as other ids
than its starter's real ones, and for a program `exec` loads while the
caller's effective ids differ from its real ones. Every program of a
[package](/docs/architecture/packages) starts with it too, however it was
started, so it never loads a library from a home. Skipping `~/.local/lib`
for such a program, and for uid 0, means a library a person can write never
ends up inside a program that holds more than that person does. The loader
reads `HOME` from the environment the process started with and uses it only
if it is an absolute path.

## What it means in practice

- **Your own builds go in `~/.local`.** Copy the program into
  `~/.local/bin` and its libraries into `~/.local/lib`; that needs nothing
  from anyone. Your shell finds the program at once, since `~/.local/bin` is
  already on your `PATH`.
- **Software for everyone is a package.** Build it with
  `scripts/build_package.sh` and install it with `pkgctl install`, which an
  administrator approves ([Build a package](/docs/development/building-a-package)).
- **An app follows `libc.so`.** Link programs you ship outside the base
  dynamically, as `cargo build` does for SlopOS by default.

## How it is tested

`apps_test` starts each app from its path in the image and holds its window
to its dock entry, and checks that each of the image's programs links
`libc.so`. `dock_test` holds the dock to the entries the base and the image
ship. `dl_test` holds the loader to its search order.

## For contributors

- **The base keeps what the security model or a repair needs, and what makes
  private system calls directly.** Anything else belongs in a package. The
  lists are in `scripts/lib/base.sh`.
- **A program outside the base talks to `libc.so` alone.** If an app needs
  something new from the system, export it from `libc.so` (and record it with
  `just libc-exports --record`) and wrap it in `slopos-cabi`.
- **Nothing with power searches what people can write.** The loader leaves
  out home directories for a process that is `AT_SECURE` or uid 0's. A new
  search path, for commands or libraries, must keep the same rule.

## Further reading

- [*XDG Base Directory Specification*](https://specifications.freedesktop.org/basedir/latest/).
  Short. Defines `~/.local/bin`, `~/.local/share` and the precedence of data
  directories the dock follows.
- [*FreeBSD hier(7)*](https://man.freebsd.org/cgi/man.cgi?query=hier&sektion=7).
  The layout that keeps the base apart from what packages install.
- [*UAPI.9: Linux File System Hierarchy*](https://uapi-group.org/specifications/specs/linux_file_system_hierarchy/).
  The modern take on per-user directories, `~/.local/lib` among them.
- [*ld.so(8)*](https://man7.org/linux/man-pages/man8/ld.so.8.html). How
  glibc's loader searches for libraries and what secure-execution mode
  switches off.
