As an app author on SlopOS you get a window, the keyboard and pointer events
meant for that window, and nothing else. You can't draw on the screen
directly, you can't read another window's pixels, and you never see a key
that was typed into another app, a password field or a question the system is
asking. That is because the desktop is a set of ordinary programs, and one of
them, the *compositor*, owns the screen and the input devices. Every other
program draws its window into memory it shares with the compositor, says
which parts changed, and receives the events the compositor sends it.

Each person's desktop has a compositor of its own, running as that person.
This page explains how a program finds it, hands it pixels and receives
input, and how the compositor itself comes to own the screen. What the
desktop looks like, and the apps that ship with it, are on the
[Desktop](/docs/architecture/desktop) page.

## Where it comes from

The design is Wayland's, the display system most Linux desktops now use.
SlopOS doesn't speak the Wayland protocol, but it makes the same split
between one compositor and its clients, and hands over pixels the same way:
shared memory whose file descriptor travels over a Unix socket, as Wayland's
`wl_shm` does. A window's role, its size limits and the way the compositor
proposes a new size follow xdg-shell, Wayland's protocol for desktop windows,
with two differences described below.

## Why the compositor owns the screen

If every program could write to the screen and read the keyboard, nothing
would stop two programs drawing over each other, a program from reading what
you type into another, or a program from drawing a fake password prompt over
the real one. Someone has to decide which window is on top, which one the
keys go to, and what the pointer is over, and that decision is only safe if
the same program draws the result. So the compositor is the only program that
holds the screen and the raw input, and it hands each client only what belongs
to that client's windows.

## How a program gets a window

A program finds its compositor through a Unix socket named `compositor` in its
*runtime directory*, `/run/user/<uid>`, which init creates for each person
with mode 0700 and names in `XDG_RUNTIME_DIR`. So a program reaches its own
person's desktop and no one else's. (The login screen is a compositor too,
but it opens no socket and serves no programs.)

The first exchange is a version check. The compositor says which protocol
version it speaks, the program answers with its own, and if they differ the
connection ends with an error: a program built against another version must
be rebuilt. Then the program asks for a *surface* (a rectangle it can draw
into), gives it the *toplevel* role that makes it a window, and names it with
a title and an *app id* such as `org.slopos.editor`, which is how the dock and
the menu bar know which app the window belongs to. It can also state the
smallest and largest size it can be laid out at.

The window appears the first time the program commits a frame for it. That
is when the compositor places it: an app's first window opens centred in the
space between the menu bar and the dock, and each later window of the same
app opens one title bar's height down and to the right of the previous one,
wrapping back to the top before it would cross the dock. A window larger than
that space is shrunk to fit, and the program is told its new size.

## How pixels reach the screen

Sending every frame's pixels down the socket would copy a whole window's worth
of memory every time. Instead the program creates a block of shared memory (a
*memfd*, an anonymous file that exists only in memory), draws into it, and
the first time it uses that block it sends the file descriptor itself over
the socket. A Unix socket can carry an open file from one program to another
(`SCM_RIGHTS`), so the compositor maps the same memory, and from then on both
programs see the same pixels without copying anything between them.

<WindowBuffers />

A window has two such buffers, so the program never draws into memory the
compositor might be reading. It draws a frame into one and *commits* it
("show this now"); it draws the next frame into the other. When the second is
committed, the compositor hands the first one back. The windowing library
also tracks how old each buffer's contents are, so a program that redraws
only what changed knows what a recycled buffer has missed (its *age*: how
many frames ago it was last shown).

### Redrawing only what changed

Every commit carries *damage*: the rectangles the program changed. The
compositor gathers the damage from every window, works out from the topmost
window down which parts of each are visible (a window hidden behind another
needs no painting), and repaints only those. Moving, raising or closing a
window counts as damage too, because it uncovers what was underneath.

The compositor runs a pass about every 16 ms and paints only when something
changed. It draws into a buffer of its own and hands the kernel the damaged
rectangles, which the display driver copies to the screen. On Intel graphics,
when the driver can set aside a second buffer for the screen (the boot log
says `XE-PRESENT: tear-free double-buffered scanout (pipe A)`), it switches
to the new frame only between screen refreshes, so you never see half of one
frame and half of another. Under QEMU's virtio-gpu the pointer is drawn by
the device's cursor plane rather than painted into every frame.

A program that animates can ask to be told when its last frame reached the
screen and draw the next one then, instead of drawing frames nobody sees.

### Resizing

When you drag a window's edge or press its zoom button, the compositor tells
the program the new size (a *configure*, in xdg-shell's words) and the program
draws at that size and commits. Unlike xdg-shell there is no acknowledgement
step: until the new frame arrives, the compositor draws the frame at the new
size and fills whatever the old buffer doesn't cover with the theme's surface
colour. During a drag it sends a new size every 100 ms, so the content keeps
up with the edge.

The size limits a program states are enforced, where xdg-shell leaves them
as hints. A drag stops at them; zoom fills the space between the menu bar and
the dock or, when the limits don't allow that, gives the window the nearest
size they do allow, centred. A window whose largest size equals its smallest
can't be resized at all, and its zoom button does nothing. The compositor
also keeps every window at least 200 × 150 unless the window's own maximum is
smaller.

## How input reaches a program

The keyboard and pointer drivers in the kernel turn every keyboard into one
keyboard state and every mouse, touchpad and tablet into one pointer
([Drivers](/docs/architecture/drivers) explains how). Each key event carries
the key's position on a USB keyboard (its *HID usage*, the same whatever the
layout), the character the layout makes of it, and the state of Shift, Ctrl,
Alt and the rest. All of it goes into one queue that only the holder of the
input *seat* (below) can read: the compositor in front.

The compositor then decides who gets each event, in this order:

1. **The lock and login screens.** Ctrl+Alt+Delete always reaches the
   compositor and locks the desktop (on the login screen, it starts the login
   screen over), and while the lock or login screen is up it takes every key
   and the pointer. This is a *secure attention key*: no program can
   intercept it, so the password prompt you get after pressing it is really
   the system's. [Sessions and login](/docs/architecture/sessions) explains
   locking.
2. **A question.** While privd's consent dialog, or a question such as
   *Power off the computer?*, is on screen, it takes the keyboard and the
   pointer, and keys pressed into it stay away from every program, their
   releases and repeats included. [Privileged actions](/docs/architecture/privd)
   describes how the dialog guards what you type.
3. **The compositor's own menus.** The system menu and the network and clock
   panels take the keys while they are open.
4. **Windows.** Key events go to the window that has *focus*. Pointer events
   go to the window whose content is under the pointer, in coordinates
   relative to that window, with an enter event when the pointer arrives and
   a leave event when it goes. A press on a window's content holds the
   pointer to that window until every button is up, so a drag that strays
   outside still ends where it started.

Focus follows simple rules. A new window takes focus when it first appears.
A click on a window raises it and focuses it; a click on the empty desktop
leaves focus where it was, so the next key still lands. When the focused
window closes or is minimised, the topmost remaining window gets focus. The
compositor moves a window when you drag its title bar, or its content while
holding Super.

The compositor also checks requests that only make sense after the person did
something. A program that has merely connected can't read the clipboard or
replace it: a copy or paste must quote the serial number of a key event the
compositor sent to a focused window of that program. Changing the pointer's
shape needs the serial of the pointer entering the window. The clipboard the
apps and the terminal copy to and paste from is the compositor's, so each
person's desktop has its own and two people's desktops never share one. (The
kernel also keeps a clipboard per session, which
[Sessions and login](/docs/architecture/sessions) describes; the apps don't
use it.)

The keyboard layout is applied in the kernel rather than in each program, so
a Swiss German keyboard types the same characters in a console, in the
terminal and in every app, and dead keys work everywhere. `keymap` shows the
layout and `keymap de_CH` switches it for everyone;
[Drivers](/docs/architecture/drivers) explains layouts.

## Who may own the screen

The kernel hands out the screen and the raw input queue as two *seats*. A
program must hold the display seat to put a frame on the screen and the input
seat to read input, and taking either needs a capability (`DisplaySeat`,
`InputSeat`) that init delegates to the compositors it starts, and the display
one also to `/bin/roulette` ([Capabilities](/docs/architecture/authority)). A
seat is held through a descriptor that can't be duplicated or passed on, and
the kernel takes it back when its holder exits, so a crashed compositor
doesn't leave the screen locked.

Several people can be logged in at once, each with a desktop, but only one
desktop is *in front*. A compositor init starts never takes a seat itself:
init hands both to it, and later moves them to another compositor, with a
call only init may make (`seat_switch`), which also routes all input to the
new holder; the desktop that goes behind stops drawing and locks.
[Sessions and login](/docs/architecture/sessions) explains switching.

There are two seat ranks. Compositors hold the lower one. The higher one
belongs to the kernel's own log and to `/bin/roulette`, the Wheel of Fate
that runs at boot, so either can always take the screen back from a stuck
compositor. Asking for a seat that is held at the same or a higher rank
fails with `EBUSY`. Below the seats, the kernel picks which display driver
shows the frame: Intel graphics, virtio-gpu in QEMU, or the plain framebuffer
the firmware left behind ([Drivers](/docs/architecture/drivers)).

## What it means for an app

Most apps should use **appkit**, SlopOS's toolkit: it connects, picks the
buffers, lays out and draws its components in the theme, routes keys to the
focused control and redraws after each message. [Write an app](/docs/development/writing-an-app)
walks through one, and the [Desktop](/docs/architecture/desktop) page
describes what the toolkit gives every app.

A program that draws every pixel itself, as the terminal does, uses the
windowing library (`slopos-windowing`) directly: it connects, makes the
window and its two buffers, and hands over the events. Either way:

- **Rebuild when the protocol changes.** The apps outside the base are built
  against one protocol version, and a compositor of another refuses them with
  "the compositor speaks another protocol version: rebuild this program".
- **Expect to be told your size.** Draw at whatever size the last configure
  named. The compositor may shrink a window that doesn't fit when it first
  appears.
- **A malformed message ends the connection**, as in Wayland: the compositor
  sends an error naming why and disconnects the program.
- **The compositor moves and resizes windows itself.** There is no request
  for a program to start a move or a resize.
- **Shared memory is scarce.** The kernel holds at most 64 memfds at once,
  across every process, each sized once and at most 64 MiB, and every window
  holds two of them. So no buffer can be larger than a 4096 × 4096 window at
  four bytes a pixel, and a program that leaks memfds starves every other
  program's windows.

The messages are listed in [Window protocol](/docs/abi/window-protocol).

## How it is tested

`protocol_test` starts a compositor and holds it to the handshake: a client of
its version is served and draws a frame, any other version is refused with
the reason, and so are a request before the handshake, a reused surface id and
an unknown message. `seat_test` checks seat ownership through the real system
calls. `apps_test` starts each app against a stand-in compositor and checks
that it names its window as its dock entry does. The parts that need no screen
are host-tested with `just test-host`: window placement and the menu bar's
state (`chrome-core`), keyboard handling (`keymap-core`) and the terminal's
grid and key encoding (`terminal-core`).

## For contributors

- **The protocol has one version at a time.** A change to any message, field
  or tag is a new `PROTOCOL_VERSION`, and `protocol_test` pins the current
  version's tags and handshake encoding, so an unannounced change fails.
- **Buffer mappings are keyed by window, surface generation and buffer
  slot,** never by descriptor number: a recycled surface slot or a reused
  descriptor can't alias an old mapping. Damage is cleared only for surfaces
  whose frame reached the screen; a commit that lands after the frame's
  snapshot carries into the next frame.
- **Visibility is computed from the top down,** subtracting each opaque
  frame, so a lower window's shadow never paints over a window above it.
- **Input-driven requests are checked against serials,** and a pointer grab is
  keyed to the surface's generation, because surface slots are reused.
- **Keep logic out of the compositor's crate.** It builds no host tests, so
  placement, the menu bar, the lock screen's and the system menu's models
  live in `chrome-core`, where `just test-host` reaches them.

## Further reading

- [*The Wayland Protocol*](https://wayland-book.com/) by Drew DeVault. The
  best introduction to the compositor model; its chapter on
  [shared memory buffers](https://wayland-book.com/surfaces/shared-memory.html)
  explains the same handover.
- [*Wayland architecture*](https://wayland.freedesktop.org/architecture.html)
  on wayland.freedesktop.org. A short comparison with X11 showing why the
  compositor owns both the screen and input.
- [xdg-shell](https://wayland.app/protocols/xdg-shell). Wayland's desktop
  window protocol: configure, window states and size limits, which SlopOS
  follows without the acknowledgement and with the limits enforced.
- [`memfd_create(2)`](https://man7.org/linux/man-pages/man2/memfd_create.2.html)
  and [`unix(7)`](https://man7.org/linux/man-pages/man7/unix.7.html). The
  Linux manual pages for anonymous shared memory and for passing descriptors
  over a socket.
