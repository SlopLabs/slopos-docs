title: "Resource limits"
description: "What the kernel limits for each program, why it refuses memory up front, and what happens when memory runs out anyway."
---

SlopOS keeps any one program from filling the tables every program shares.
Each program has a budget for open files, threads, child processes, address
space, disk space and some kinds of kernel memory, and everything a person
runs shares one ceiling on processes and threads, so one person's runaway
program can't stop anyone else from starting programs. A call that would go
over budget fails with the error it already uses when that resource runs out
(`ENOMEM`, `EMFILE`, `EAGAIN`, `ENOSPC`), so programs written for Linux need
no changes. RAM is not divided up this way: it has one ceiling for the whole
machine, so one program can still use most of it. But it is handled more
strictly than on Linux: SlopOS refuses memory when a program asks for it, so a
program that runs out almost always gets an error it can handle and is not
killed. The main exception is `fork`, and when a forked child does run the
machine out of memory, the kernel ends one process, chosen by a rule
described below.

The budgets for open files, processes, address space and pinned memory are
Unix resource limits, read with `getrlimit` as on Linux. Refusing memory at
the time it is promised is what Linux calls *strict overcommit accounting*,
an option there and the default here.

## What is limited

| What | Counts | When it runs out |
|---|---|---|
| Open files | Descriptors in the program's table | `EMFILE` |
| Kernel objects | Pipes, sockets and other kernel objects the program created | `ENFILE` |
| Descriptors in flight | Descriptors the program sent over a Unix socket that nobody has received yet | `ENFILE` |
| Threads | Threads in the program | `EAGAIN` |
| Processes | Processes the program forks, their own forks, and so on down | `EAGAIN` |
| Address space | Memory the program has mapped or reserved | `ENOMEM` |
| Pinned memory | Memory that must stay in RAM, such as buffers registered for direct I/O and mapped files | `ENOMEM` |
| Kernel memory | Kernel memory used on the program's behalf: thread stacks, page tables | `ENOMEM` |
| Disk blocks | Blocks the program has allocated on a mounted disk | `ENOSPC` |

The process limit counts grandchildren too. If it counted only direct
children, each child of a fork bomb would start its own children against a
fresh budget. A program started with spawn begins a budget of its own instead,
but it still counts against its person's share, described next.

The disk limit applies to blocks a program allocates while it runs. A file it
wrote stays on disk after it exits and is charged to nobody, so this is not a
disk quota. A program holding the capability to write raw disks, or the one
to install extensions, has no disk limit at all: the installer fills a whole
root in one process, and an extension's installer stores whole images
([Capabilities](/docs/architecture/authority)).

The pinned-memory limit is set at boot to an eighth of the machine's usable
RAM, the share of the file-mapping cache one program may hold, because a
compiler's shared libraries already go past a smaller fixed default before it
starts and a linker maps every input at once.

The kernel also counts each process's *resident* memory (the RAM it holds
now) and *committed* memory (the private memory the kernel has promised to
back) without capping them per process. Committed memory has a ceiling for
the whole machine, [described below](#why-slopos-refuses-memory-up-front).

## Each person's share

On a machine several people use, a per-program budget isn't enough: one
person running many programs, or a program that spawns rather than forks, can
still fill the process and thread tables everyone shares. So the kernel keeps
an account for each person (each uid in the people's range, 1000 to 59999; see
[Users and file permissions](/docs/architecture/users)). Every process started
to run as that person is counted against it, and so is everything those
processes fork, each new thread included. The account allows a quarter of the
machine's processes and a quarter of its threads, for all of that person's
programs together. When one person's programs reach it, their next `fork`,
spawn or thread fails with `EAGAIN`, while the other three quarters stay free
for everyone else and for the system.

A zombie keeps its thread charged to its person until its parent reaps it,
rather than to the parent's own budget, so a person who leaves thousands of
children unreaped spends only their own share. Ending their session ends
every process that carries its login tag, a fork bomb included, and gives
back what they held ([Sessions and login](/docs/architecture/sessions)).
The accounts are made as each person first runs something, for the first
sixteen people in a boot; anyone after that shares the system's account.
Memory isn't divided this way: it stays the machine's, under the one commit
ceiling below.

Linux reaches for the same goal with `RLIMIT_NPROC`, which it counts for each
real user id rather than for each process tree. SlopOS keeps both: the
per-program limit that `getrlimit` reports, counted over the program's forks,
and the per-person share above it, which no program can raise or lower.

## Why SlopOS refuses memory up front

When a program gets memory from `mmap` or `brk`, no RAM is used yet. Each page
is filled in the first time the program touches it (see
[Memory](/docs/architecture/memory)), so the kernel can say no either when the
memory is requested or when it is touched.

Linux by default mostly says yes at the request. If programs then touch more
memory than the machine has, no call is left to fail, so Linux kills a
process, which may not be the one that asked for too much.

SlopOS keeps a running total of the private memory it has promised. Each
request (by `mmap`, `brk`, `exec`, or an `mprotect` that makes a reserved
range usable) is added to it and refused with `ENOMEM` if the total would pass
the ceiling, which by default is all of the machine's usable RAM. Memory
already accounted for elsewhere, such as a shared file mapping or a memfd,
isn't counted twice.

So a `malloc` that can't be backed fails in `malloc`, with an error the
program can report. `exec` is checked before the old program is thrown away,
so a program too large to fit gets `ENOMEM` and keeps running the old one.

A program that will use only a little of a large reservation, such as a
language runtime that reserves a gigabyte of address space, can map it with
`MAP_NORESERVE`. That memory is counted a page at a time as it is used, which
brings back the risk described next.

## Why `fork` is the exception

`fork` gives the child a copy of its parent's memory, shared until one of them
writes to a page (see [Memory](/docs/architecture/memory)). If `fork` had to
promise that memory again, a 2 GiB build tool running a one-line shell command
would need another 2 GiB promised for the moment between `fork` and `exec`.
Unix software assumes `fork` is cheap, so SlopOS never refuses it for want of
promised memory: the commit ceiling doesn't see a fork at all.

Instead the child is charged a page at a time, as it writes a page and gets
its own copy, so a child that calls `exec` straight away costs almost
nothing. A child that writes to every page needs memory nobody promised,
though, and a memory write can't return an error. Forked children, stacks
growing into new pages and `MAP_NORESERVE` memory are the only ways a SlopOS
program can use more memory than it was promised.

## What the out-of-memory killer does

When one of those writes finds no memory, because the commit ceiling is
reached or RAM is full and nothing can be reclaimed, the kernel ends a process
to make room and retries the write. This is the *out-of-memory killer* (OOM
killer). It chooses a victim like this:

1. It considers only processes that hold no capability the writer lacks,
   the capability half of the test `kill` applies (see
   [Capabilities](/docs/architecture/authority#who-may-signal-whom)),
   so an ordinary program's memory use never takes down the compositor or a
   system service. Unlike `kill`, it doesn't look at user ids: the process it
   picks may belong to another person. Init and kernel threads are never
   chosen.
2. Of those, it picks the one holding the most of what ran out: promised
   memory if the ceiling was reached, RAM if RAM was. Shared memory counts
   against its owner, so mapping someone else's doesn't make you look bigger.
3. It ends that process with `SIGKILL`, waits for its memory to be freed, and
   retries the write. Nobody picks another victim while one is dying, and if
   the victim still holds its memory five seconds after the kill, it stops
   holding back the choice of the next one.

If nobody is eligible, the writer itself dies with `SIGKILL` (not the
`SIGSEGV` of a crash), and the kernel log says it ran out of memory with
nothing left for the OOM killer to take. Only init's write may take any
process, because the machine can't run without init.

## How a program sees its limits

Programs read their limits with `getrlimit` or `prlimit`, which both use the
`prlimit64` system call, as does `ulimit` in bash (which comes with the
toolchain; the base's own shell has no `ulimit`). These standard limits are
supported:

| Limit | What it controls |
|---|---|
| `RLIMIT_NOFILE` | Open files |
| `RLIMIT_NPROC` | Processes |
| `RLIMIT_AS`, `RLIMIT_DATA` | Address space |
| `RLIMIT_MEMLOCK` | Pinned memory |

Any other limit fails with `EINVAL`, so a program can tell "not supported"
from "unlimited". The soft and hard limits are always equal. A program may
lower its own limits, naming itself as pid 0 the way `getrlimit` and
`setrlimit` do, but can't raise them or change another process's (`EPERM`).

A build driver deciding how many jobs to run can call `sys_info` for the
commit ceiling, how much of it is promised, and the OOM killer's count of
victims since boot and its last one. Any program can call `process_memory`
for every process's resident memory now and at its peak, which is what the
System Monitor's process list shows ([Desktop](/docs/architecture/desktop)).

We set the default limits by measuring real workloads. Two settings on
[Boot options](/docs/abi/boot-options) change the policy: `quota=` turns
enforcement off or into warnings, for measuring what a workload needs, and
`mem.commit=` sets the commit ceiling as a percentage of RAM or turns it off.

## What programs can rely on

- **A successful `mmap`, `brk` or `exec` is backed.** Touching the memory
  won't get the program killed, unless it was mapped with `MAP_NORESERVE`.
  Stack the program grows into past what `exec` gave it is charged as it
  grows.
- **`fork` is never refused at the commit ceiling**, but a child that writes
  much of its parent's memory can trigger the OOM killer.
- **Limits fail with the errors programs already handle.**
- **The OOM killer never takes a process holding a capability the writer
  lacks.**
- **One person's programs can't use up the processes or threads of another.**

## How it is tested

Kernel tests charge and refund every kind of resource and check each refusal's
error, and the OOM killer's tests cover each rule in its choice of victim. A
userland test starts a fork bomb as one person and checks that it stops at
their share, with their unreaped children counted against it, while another
person's session keeps starting programs. An in-kernel audit cross-checks
the running totals against the memory they describe. The ledger's arithmetic
has a machine-checked proof, as a sequential state machine (see
[Proofs](/docs/verification/verus-status)); the per-row atomics and account
release are covered by the audit, KernMiri and tests.

## For contributors

**Charges are tokens.** Each process has a row in a fixed arena in `.bss`,
under a kernel-owned root. `try_charge` debits the row and every ancestor and
returns a linear `Reservation`, which the charged object's constructor turns
into a `Charge` that its `Drop` refunds. Only the trusted core can build one,
so nothing can forge, copy or skip a charge. Refunds touch only atomics in
`.bss` and must stay legal in an interrupt handler, under a spinlock and
during a dying task's unwind. Tokens are unique by type, but only
`ledger_audit` can catch wrong totals.

**Kinds** live in `slopos_abi::quota` with their unit, refund point, scope and
errno. `Process` and `CommitPages` count the whole subtree, the rest one
process.

**The account tree** has its own parent edge, separate from the wait parent,
so a process whose parent dies keeps spending its original budget. A fork's
edge is its parent's account; a spawned process's edge is its person's row
(`quota::person_account`, keyed on the real uid) or the root. A person's row
bounds everything charged through it, as the root does, and only for
`Process` and `Task`. The edge carries the parent's generation so a reused row
is never credited by mistake. Chains stop at `MAX_ACCOUNT_DEPTH`; deeper
processes debit through their nearest ancestor with room, which keeps every
walk bounded.

**Tasks are charged where they are made.** A spawn, a fork and a thread
(`charge_clone`) each charge one task to the account of the process the new
task belongs to. When the last task of a person's process exits, its charge
moves onto the zombie leader, held by the person's row
(`ChargeSlot::bequeath_into`), and is refunded at the reap. A memfd's charges
move too when its sizer dies (`ChargeSlot::bequeath`), to the root, which is
never released.

**Commit classes** decide how each memory region is charged. A class never
moves back; only `Unreserved` changes, the first time a protection lets its
pages be populated.

| Class | Regions | Charged |
|---|---|---|
| `Unreserved` | Shared memfd, SlopRing share, shared file mappings, read-only private file mappings, `PROT_NONE` reservations | Nothing |
| `Extent` | Lazy anonymous memory, writable private file mappings | Whole span at creation |
| `Frames` | The loader's eager segments, the stack and its growth range, `MAP_NORESERVE` | A page at a time as each is placed |
| `Forked` | A fork's copy of a region its parent had charged | A page from the moment the child owns it |

**The OOM path** (`mm::oom`) weighs `CommitPages` when the ceiling refused the
page and `ResidentPages` when the frame allocator was empty after reclaim.
The victim unwinds through the kill flag in its own context (see
[Scheduling and waiting](/docs/architecture/scheduler-wait-protocol)); a
writer with nothing to take dies with `TaskFaultReason::UserOom`. Kernel
writes for a task take the same path where they may block; where they can't,
a user copy returns `EFAULT` and a failed signal frame push ends in `SIGSEGV`.

## Further reading

- [*Swapping: Mechanisms*](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys.pdf),
  chapter 21 of *Operating Systems: Three Easy Pieces* by Remzi and Andrea
  Arpaci-Dusseau. What a kernel does when memory is short. SlopOS has no swap,
  but the chapter covers the page faults and memory pressure behind this page.
- [*Overcommit accounting*](https://docs.kernel.org/mm/overcommit-accounting.html)
  in the Linux kernel documentation. Linux's three overcommit modes on one
  page. SlopOS's default is close to strict mode, with `fork` handled
  differently.
- [*Taming the OOM killer*](https://lwn.net/Articles/317814/), LWN (2009). Why
  choosing a victim is hard.
- The man page for [`getrlimit(2)`](https://man7.org/linux/man-pages/man2/getrlimit.2.html),
  the limits interface programs use, including `prlimit`.
