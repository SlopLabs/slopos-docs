An ordinary program on SlopOS can do anything its user may do with files, open
sockets, start other programs and draw windows. It can't power the machine off,
mount a disk, set the clock, write to a disk directly, take on another user's
identity or take over the screen, and running as uid 0 changes none of that.
Each of those powers is a *capability*: a named bit in a mask the kernel keeps
for every process and checks before the system call runs. A process gets
capabilities only from the process that started it, which must hold them
itself, and it loses every one of them when it `exec`s another program.

So when a person powers the machine off, the program they ran asks privd, the
privilege broker init starts at boot. privd checks its policy and starts a
fresh copy of the program holding exactly the capabilities that action names
([Privileged actions](/docs/architecture/privd) explains how it decides). The
rest of this page lists the capabilities and who holds them, and explains how
they pass from one process to another and how they shrink.

## Where the idea comes from

Linux split root's single power into named capabilities long ago:
`CAP_SYS_BOOT` to reboot, `CAP_DAC_OVERRIDE` to bypass file permissions,
`CAP_SYS_NICE` to raise a priority, and so on. SlopOS uses the word in that
sense, a privilege attached to a process, and takes Linux's rule for `exec`: a
process that isn't root, running a program that carries no capabilities of its
own, loses the capabilities it held (unless it set some aside as *ambient*,
which SlopOS has no equivalent of). What SlopOS leaves out is the shortcut that
makes Linux's root powerful again. On Linux a process with uid 0 regains its
capabilities when it runs a program, unless a securebit (`SECBIT_NOROOT`) says
otherwise. On SlopOS a uid is only an identity
([Users and file permissions](/docs/architecture/users)), and no program gains
a capability by being run, whatever its path, owner or mode bits.

seL4 and Capsicum use the word for something else: an unforgeable handle to one
object, such as a descriptor that carries its own rights. SlopOS keeps Linux's
system call interface, which names things by number and path, so most of its
capabilities belong to the process rather than to an object. Where an operation
does name an object (an open file, a socket, a seat), the object is the
authority and no capability is checked.

## Why not uid 0, or a list of trusted programs

Unix's own answer is that uid 0 may do anything. Then a service that needs one
small power, such as setting the clock, holds all of them, and any bug in it is
a bug with every power. Linux's capabilities exist to fix that, but one of
them, `CAP_SYS_ADMIN`, covers so much that its manual page says it "can
plausibly be called 'the new root'".

The other easy answer is the one SlopOS used while every program ran as uid 0:
the kernel kept a table from a program's path to the powers it got when it
started, so `/bin/halt` got `Power` whenever a shell started it. Each row of
that table was a setuid program by another name. The shell conferred powers it
didn't hold itself, and every guarantee rested on nobody getting a different
program to one of those paths.

SlopOS now has a single rule instead: authority flows only from a holder. The
kernel gives init everything, and every other process holds what its spawner
chose to hand it out of what the spawner held.

## The capabilities

The table lists every capability the kernel checks. Init holds all of them.
The last column says who else holds each one on a running system; a program
named there holds it only when privd starts it for an action that names it
(see [privd actions](/docs/abi/privd-actions)), except where init starts it
directly.

| Capability | Allows | Also held by |
|---|---|---|
| `Power` | Rebooting, halting and powering off; reading and writing the boot loader's EFI variables and SlopOS's own; changing CPU frequency settings | privd; `halt`, `bootctl`, `cpufreq set`, the installer |
| `ProcSignal` | Signalling any process but init, past both halves of [the signal rule](#who-may-signal-whom) | privd, which passes a requester's signals on to its mechanism; `endtask` |
| `SysInspect` | The diagnostic console's informational commands (`kconsole(2)`) and steering the sampling profiler (`prof_ctl`) | privd; `kconsole`, `prof`, what `priv` runs |
| `DisplaySeat` | Taking the screen | Every compositor, the login screen's included; `/bin/roulette` |
| `InputSeat` | Taking the raw keyboard and pointer stream | Every compositor |
| `SeatSwitch` | Moving both seats from the session in front to another one | Init alone |
| `ConsoleConfig` | Loading the console font and keyboard layout; `vhangup`, which hangs up the caller's terminal and every process of the session on it | privd; `keymap`, what `priv` runs |
| `Mount` | `mount` and `umount` | privd; the installer, what `priv` runs |
| `RawBlock` | Reading and writing disks and partitions directly, re-reading a partition table, reading and erasing crash records; it also lifts the per-process disk-space limit | privd; `bootctl`, the installer and the e2fsprogs programs it starts |
| `Clock` | Setting the wall clock | privd; what `priv` runs |
| `NetAdmin` | Changing the network: interfaces, addresses, routes, the resolver and DHCP; seeing which process owns every socket | privd; `ip`, what `priv` runs |
| `Seal` | Setting or clearing a file's immutable flag (what `chattr +i` sets) | privd; `users`, `extctl`, the installer |
| `BootEntry` | On top of `Power`, the firmware's boot manager entries: `Boot####`, `BootOrder`, `BootNext` and `BootCurrent`, and no other firmware variable | privd; the installer |
| `SetId` | Taking a user or group id the process doesn't already hold, setting supplementary groups, and starting a child as someone else or with a login tag | privd |
| `DacOverride` | Reading and writing any file whatever its permission bits, and giving any file to any owner | privd; `users`, the installer, what `priv` runs |
| `SchedHigh` | Starting a program at the `High` scheduling tier, and setting a nice value below both zero and the task's current one | Init alone, which starts the compositor at `High` |
| `BaseUpdate` | Making another archive the running base | privd; `bootctl base install` and `base rollback` |
| `ExtensionUpdate` | Activating and deactivating extensions; it also lifts the per-process disk-space limit | privd; `extctl` |
| `TestHarness` | The test-only system calls, which do nothing unless the kernel booted with `tests=on` | The copy of init that runs the tests |

Three more capabilities are *universal*: every program holds them, and nothing
yet hands them out more finely.

| Capability | Allows |
|---|---|
| `ConsoleIo` | Writing to the kernel log without a descriptor |
| `ClipboardGlobal` | Copying to and pasting from the kernel's clipboard for the caller's session (the desktop's apps use their compositor's clipboard instead) |
| `Fate` | Spinning the Wheel of Fate and reporting its result |

They protect nothing today. They are capabilities rather than plain system
calls so that taking one away later, once the clipboard is a descriptor or the
wheel is something init hands `/bin/roulette`, is a visible change. Every
other capability is *gated*: a program holds it only if something handed it
over.

An extension's services may also hold `Power`, `Mount`, `RawBlock`,
`NetAdmin`, `ConsoleConfig`, `SysInspect`, `Clock`, `DacOverride` or
`SchedHigh`, and its actions any of those but `SchedHigh`, if the machine's
owner granted them when installing it. That list is the base's ceiling for
extensions, and no grant can name anything outside it
([Extensions](/docs/architecture/extensions)). The rescue shell that an
install medium offers holds everything privd can give.

## How a process gets its capabilities

The kernel starts one program itself, `/sbin/init`, as uid 0 holding every
capability. Every other process starts from a spawn, SlopOS's one-step call to
start a program ([Processes and signals](/docs/architecture/processes)), and
the spawner says which gated capabilities the child should hold. The kernel
checks that each one is a capability the spawner holds; if any isn't, the
spawn fails with `EPERM`, and a bit that names no capability at all is
`EINVAL`. The child then holds what was asked for, plus the universal
capabilities the spawner still holds, and nothing else. Nothing about the
program it runs adds to that.

The same call can ask for the child to run with other user and group ids or to
carry a session's login tag, and either takes `SetId`. A child that holds any
gated capability, or runs with ids other than its spawner's real ones, starts in
*secure mode* (`AT_SECURE`, the flag Linux sets for setuid programs). In secure
mode the dynamic loader ignores `LD_LIBRARY_PATH`, `$ORIGIN` and relative
directories, and doesn't search `/usr/local/lib` or `~/.local/lib`, so nobody
can slip a library into a program that holds more than they do.

`fork` copies the parent's capabilities, and the threads of a process share
them. Because `exec` drops gated capabilities (see
[below](#how-capabilities-shrink)), forking and then `exec`ing hands a new
program nothing; the spawn call is the only way capabilities reach a new
program.

### What init hands out

Init starts each program it supervises with what its service table names and
nothing more. privd gets every capability an action may name, and `SetId`.
Each compositor, a person's desktop or the login screen, gets `DisplaySeat`
and `InputSeat`, and the Wheel of Fate gets `DisplaySeat`. A boot-time job
gets what its one job needs, and an extension's service what it declares
within its grant. What init starts as a person (their terminal, a console
login's shell, `remoted`) and the console's login prompt hold nothing gated.
[Init and services](/docs/architecture/init#what-init-starts-and-in-what-order)
lists every program init starts, as whom, and holding what.

An action may name any gated capability but the seat capabilities,
`SeatSwitch`, `SchedHigh`, `SetId` and `TestHarness`, so nothing privd starts
holds those. privd holds `SetId` only to start a mechanism as someone other
than uid 0: an extension's own user, or the person who asked.

### Example: powering off from a terminal

When you type `halt` in a terminal, your shell starts `/bin/halt` as you,
holding nothing gated, so `halt` can't call `reboot` itself. Like the base's
other mechanisms, it notices that and asks privd instead: it connects to
`/run/privd` and sends its own arguments, which privd matches to the action
`org.slopos.power.poweroff`. The policy lets a person run that one
unasked while nobody else is logged in. privd then starts a second `/bin/halt`
as its own child, as uid 0 holding `Power` and no other gated capability, and
that one powers the machine off. The first `halt` waits for it and exits with its
status.

Two things keep this safe. privd can only hand over what it holds itself, which
is less than init holds. And the second `halt` takes nothing from your shell
but the descriptors it reads and writes, which privd passes it, with an
environment privd writes, so your environment and your libraries never reach a
program holding `Power`.

## How capabilities shrink

Once a process is running, its capabilities stay the same or get fewer:

- **`exec` keeps only the universal capabilities**, in every thread of the
  process. A program holding `Power` that `exec`s another program hands it
  nothing. The one exception is init re-executing the base's own `/sbin/init`
  as its only thread, which loads nothing but init and so gains nothing.
  A program that does need to hand its whole mask to the programs it runs,
  such as the rescue shell or `priv`, spawns them instead of `exec`ing them.
- **`caps_drop(mask)` gives capabilities up for good.** It takes them from
  every thread of the calling process, including one being created at that
  moment, and returns what the process still holds, so `caps_drop(0)` is how
  a program asks what it holds. It has no error to forget to check. A service
  that needs a capability only while it starts should drop it afterwards.

Nothing can take capabilities away from another running process, and nothing
adds any. That keeps every check down to one read of the caller's own mask.
The drop is process-wide on purpose: threads share their memory, so a thread
that gave up a capability while its sibling kept it would protect nothing.

## Seats for the screen and input

Only one program at a time may draw to the screen, and only one may receive the
raw stream of keyboard and pointer events. SlopOS calls these two resources
*seats*. A program holding `DisplaySeat` or `InputSeat` may ask for the
matching seat, and if it gets it, it receives a descriptor it needs for drawing
or reading input. A request succeeds if the seat is free, if the caller already
holds it (asking twice is harmless), or if the caller outranks the holder.
There are two ranks: a compositor's, and the kernel console's, which
`/bin/roulette` also uses. The console outranks every compositor, so the
kernel log can always take the screen back from a compositor that has hung. An
equal rank is refused, so two compositors can't trade the screen back and
forth.

When several people are logged in, each person's desktop has its own
compositor, and they all have the same rank. Init decides which one the person
at the machine sees: it moves both seats from the compositor in front to
another with `seat_switch`, which needs `SeatSwitch` (init's alone) and works
only on a target holding both seat capabilities. A compositor that init starts
never asks for a seat itself; it waits for init to hand them over.
[Sessions and login](/docs/architecture/sessions) describes switching between
people.

A seat descriptor can't be duplicated or passed to another process, so the
kernel always knows who holds a seat. When the holder exits or `exec`s, the
kernel takes the seat back, and a descriptor left over from an earlier holder
stops working.

## Who may signal whom

Signals need no capability of their own. Instead the kernel compares sender and
target, and a signal goes through only if both of these hold:

- **The uid rule**, POSIX's: the sender's real or effective uid is the target's
  real or saved uid. This keeps one person from signalling another's programs
  ([Users and file permissions](/docs/architecture/users) covers the ids).
- **The capability rule**, SlopOS's: the sender holds every capability the
  target holds. This keeps a person's programs from stopping or killing a
  process privd started for them, which runs as uid 0 or as them but holds
  more.

Holding `ProcSignal` waives both. `SIGCONT` to a process in the sender's own
POSIX session (the processes sharing a terminal, which `setsid` starts) needs
neither, so a shell's `fg` can resume a job that holds more than the shell.
Nobody may signal init (`EPERM`), and naming a kernel thread gives
`ESRCH`, as if it didn't exist. A signal aimed at a whole group skips the
members the sender may not signal.

Linux's `kill` checks only the uid rule, and its `CAP_KILL` waives it; the
capability rule is SlopOS's addition. The same two rules decide whose nice
value a process may change, and the capability rule alone decides which
processes the out-of-memory killer may end on a writer's behalf
([Resource limits](/docs/architecture/resource-accounting)).
Anyone may ask what any process holds with `caps_get(pid)`, as anyone may read
another process's capabilities with Linux's `capget`.
[Processes and signals](/docs/architecture/processes) explains signals
themselves.

## Why a forgotten check is a compile error

In most kernels each system call has to remember its own permission check, and
a forgotten one is a silent hole that only a reviewer can catch. In SlopOS
every system call declares, where it is defined, which capability it needs, or
which of three reasons it needs none: it acts only on the caller, only on a
descriptor the caller holds, or on a relationship between caller and target
that it checks itself (parent and child, the same POSIX session). A system call
without a declaration doesn't compile, and the dispatcher checks the declared
capability before the handler runs, so the handler can't forget it. SlopRing,
the asynchronous interface, declares every operation too, and none of them may
need a capability, so a program can't use a ring to do anything it couldn't do
directly.

Capabilities still belong to the calling process and are compared against plain
numbers and paths in the arguments (capability systems call this *ambient
authority*), so SlopOS isn't a pure capability system. What the declarations
guarantee is that every use of that authority is checked.

## What it means in practice

- **To give a program a power,** decide who starts it. Something init runs at
  boot gets it from init's service table; something a person or a service asks
  for gets an action in privd's policy; an extension's program gets it from its
  declaration, within what the owner granted. There is no setuid bit, and no
  file, path or owner gives a program anything.
- **If a program gets `EPERM` from a gated call,** it lacks the capability.
  The base's own mechanisms (`halt`, `bootctl`, `ip`, `keymap` and the rest)
  ask privd by themselves. For another system command that needs `Mount`,
  `NetAdmin`, `ConsoleConfig`, `SysInspect`, `Clock` or `DacOverride`,
  `priv <command>` runs it as you holding those, if you are allowed to
  ([Privileged actions](/docs/architecture/privd)).
- **Running as uid 0 doesn't help.** It makes a process the owner of the
  system's files and nothing more. Test for the capability a call needs, or
  just try the call, rather than comparing `getuid()` with 0.
- **To see what a process holds,** call `caps_get(pid)`, or `caps_drop(0)` for
  the caller itself.

## Limits

- Several capabilities stand in for objects that don't exist yet: `Power`
  could be a descriptor handed to init, `Mount` an operation on a directory
  descriptor, `Clock` a clock device's descriptor, and the seat capabilities
  would fold into the seat descriptors. Each one's definition records the
  change that would retire it.
- `RawBlock`, `Mount` and `DacOverride` can each rewrite or cover the root
  filesystem, so a holder of any one of them can take over the machine. They
  are separate to keep each one's holders few, not because one alone is safe.
- `BootEntry` reaches only the four boot-manager variables, never others such
  as the Secure Boot keys, but whoever holds it can change which loader the
  firmware starts.

## How it is tested

Kernel tests check that every system call is classified, that an ordinary task
is refused `Power`, that `exec` drops every gated capability and only init
re-executing itself keeps its mask, that a spawn can't hand over a capability
its spawner lacks, that `caps_drop` reaches every thread of a process, and that
`BootEntry` alone reaches no firmware variable. A userland test checks the same
between real processes, including that no base program gains a capability by
its path and that a person's session holds nothing gated. A machine-checked
proof covers the arithmetic: no step widens a mask, `exec` leaves only the
universal capabilities, a spawn is bounded by its spawner, and a drop is
total. A build-time check over the linked kernel makes sure that every system
call that can reach the power-off code either needs `Power` or is on a
reviewed list that says why (the Wheel of Fate's result, which may restart the
machine, is one).

## For contributors

**Every handler declares its class.** `define_syscall!` requires a `cap(...)`
clause:

```rust
define_syscall!(syscall_clock_settime
    (ctx, clock_id: u64, ts: UserPtr<Timespec>) cap(Clock)
    -> Result<(), Errno>
{
    // ...
});
```

The macro emits the handler and its class as one constant, so a dispatch slot
can't pair one handler with another's class. Compile-time checks require every
slot to be classified and the count per class to match a recorded table
(`CAP_COUNTS`), so a new entry point fails the build until someone re-records
it and says why in the commit. The ungated classes (`NoneSelf`, `NoneFd`,
`NoneRelation`) stay separate because a single "none" class would drift toward
everything being marked none.

**Finer checks read the same mask.** A handler that needs a capability for part
of its work asks `SyscallContext::holds`, or takes a witness, `Cap<'_, R>`, from
`ctx.require_cap::<R>()` (`efivar_set` asking for `BootEntry`, the flags
`ioctl` asking for `Seal`). Only the authority module can mint a witness, and
it can't be copied, cloned, sent to another thread or kept past the request.

**Capability bits are ABI.** A mask crosses the system call boundary in
`caps_drop`, `caps_get` and `SpawnAttrs`, so `abi/src/caps.rs` states the bits
once and a compile-time assert holds the kernel's `Capability` enum to exactly
those. A new capability also needs a decision in `priv-core`: whether an action
may name it (`DELEGABLE`), whether `priv` may (`REQUESTER_CEILING`), and whether
an extension never may (`NEVER` in `extension-core`).

**Nothing else carries authority.** `task.flags` says where and how a task
runs, never what it may do; a spawn naming a flag bit that isn't defined is
`EINVAL`. Kernel threads hold no capability, so a gate a kernel thread must
pass (the raw block devices, the ext4 reserve) names kernel threads itself. A
check that reads a flag, a path, a task id or a uid where a capability fits is
a second source of authority, and review should refuse it.

**Signals resolve once.** `resolve_signal_target` returns a `Signalable` that
holds a reference to the task it checked, so nothing can name the target by id
after the check and reach a stranger who took over the number.

**Gates.** `scripts/check_authority_reachability.sh` (run by
`just check-framekernel-gates`) fails unless every handler that can reach a
power primitive in the linked kernel is classified `Power` or allowlisted with
a reason. Indirect calls are invisible to it, which is why the kernel's own
power callers (the diagnostic console, the test harness, panic) are a tracked
list. `verification/proofs/authority.rs` proves the mask arithmetic over any
grant, but not the memory ordering of the mask or that the dispatcher consults
it; see [Proofs](/docs/verification/verus-status).

## Further reading

- [*CAP_SYS_ADMIN: the new root*](https://lwn.net/Articles/486306/), LWN
  (2012). Start here. A short account of how one Linux capability grew into a
  catch-all, which is why SlopOS keeps its capabilities narrow.
- [*Capsicum: practical capabilities for UNIX*](https://www.usenix.org/legacy/event/sec10/tech/full_papers/Watson.pdf)
  by Watson, Anderson, Laurie and Kennaway, USENIX Security 2010. How to add
  object capabilities to Unix without throwing out its interface, the
  direction SlopOS's seats point in.
- [Redox: Security](https://doc.redox-os.org/book/security.html). A different
  answer from a Rust system: per-process namespaces of schemes, and
  capabilities as file descriptors that carry their actions.
- The manual pages [`capabilities(7)`](https://man7.org/linux/man-pages/man7/capabilities.7.html),
  Linux's capability sets and how they pass across `exec`;
  [`capget(2)`](https://man7.org/linux/man-pages/man2/capget.2.html), reading
  another process's capabilities; and
  [`getauxval(3)`](https://man7.org/linux/man-pages/man3/getauxval.3.html),
  which describes `AT_SECURE`.
